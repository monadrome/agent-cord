# 01 · 定位与设计哲学

> **状态：设计定稿，代码未实现。** 本文及本方案文档集中的所有机制均为设计方案，尚未有可运行实现；凡涉及实现细节的表述，均指设计意图而非现状。
>
> 读者：第一次接触本项目的外部开发者。本文不假设你读过任何其他材料。

**本章回答什么问题**：agent-cord 为什么存在？它观察到哪两个结构性事实？由这两个事实能推出哪些不可回避的设计公理？项目明确做什么、不做什么？——读完本章，你应当能独立判断后续所有设计决策的必然性，而不只是记住一批结论。

## 1. 五类被反复观察到的成本

在 AI 辅助开发的典型工作方式中，以下五类成本被反复观察到。它们不是从工具对比里推出来的，而是从真实项目过程中观察到的：

| # | 痛点 | 具体表现 |
|---|---|---|
| P1 | 碎片化交互成本高 | 人与 AI 反复分步交互，大量时间消耗在需求对齐和等待输出上 |
| P2 | 前期对齐负担重 | 接手新需求需与产品、设计、后端、测试逐一对齐，常以天计 |
| P3 | AI 输出校验负担重 | 长周期运行产出体量大，全量 review 不现实，且存在幻觉 |
| P4 | 需求变更无统一载体 | 变更散落在私聊和群聊中，极易遗漏 |
| P5 | 上下文切换成本高 | 多会话、多沟通群之间来回切换，重复粘贴历史信息 |

这五类成本有一个共同特征：**它们都不是"写代码慢"，而是"共识没有被当作对象来管理"**。需求对齐的产物散在会议和私聊里，变更没有载体，结论没有证据，因此每次都要重新对齐一次——P1 到 P5 是同一个病根的五种症状：共识不可见、不可查、不可复核、不可累积。

## 2. 第一性原理：两个结构性事实

### 2.1 事实一：验证环节已高度自动化，共识环节没有

在当前的研发流程中，验证侧已经基本被工具化了：单元测试、集成测试、截图与设计稿比对、e2e 录制回放、CI 流水线——这些环节的产出是机器生成的、可重复的、可以无人值守得到信号。**而共识侧没有任何机制承载**：它的定义是「人脑中的业务模型与代码现实对齐」，实现方式至今仍是开会、私聊、逐人通知、靠某个人记得。

由此得到本项目最重要的一条投入方向判断：

> **大部分项目时间实际消耗在共识上，而不是消耗在编码或验证上。因此再提高编码速度的边际收益有限，把共识变成可管理的对象才是瓶颈所在。**

由事实一继续推出三条子推论，后续所有设计都能回指到它们：

1. **已有的验证信号要复用，不自建**：共识机制只做协议与机制的增量，测试、截图比对、CI 这些成熟能力直接接入（机制复用原则，见 §6）。
2. **共识必须有载体、有留痕、有度量**：没有度量就没有管理。一个"感觉一致"的结论无法被审计、无法被复用、也无法被推翻——它只会随人离职而消失。
3. **人的时间应花在机器判断不了的地方**，而不是信息搬运：从"逐人通知变更"变成"系统列出受影响清单，人做取舍"。

### 2.2 事实二：LLM 的错误是系统性相关的

第二条事实来自 2024–2025 年的一批实证与理论研究。它不是本项目的假设，而是已被量化的事实：

| 证据 | 结论 | 对本项目的含义 |
|---|---|---|
| [Correlated Errors in LLM](https://proceedings.mlr.press/v267/kim25e.html)（Kim et al., ICML 2025，350+ 模型大规模实证） | **两个模型都答错时，60% 的情况错在同一个答案上**；共享架构/供应商是错误相关性的驱动因素；**更大更准的模型即使跨架构、跨供应商，错误相关性依然很高** | 「多找几个 AI 看看」不能替代证据；异构只是缓解，不是解药 |
| [Should we be going MAD?](https://arxiv.org/abs/2311.17371)（Smit et al., ICML 2024） | 多 agent 辩论在系统 benchmark 上**不能稳定跑赢** self-consistency / 多路径集成，且对超参敏感 | 共识形成选盲评投票，不选辩论（成本还更低） |
| [Which Yields Better Decisions in Multi-Agent LLMs?](https://arxiv.org/html/2508.17536v1)（NeurIPS 2025） | 理论证明辩论诱导的信念轨迹是鞅，**辩论本身不改善期望正确率** | 「让它们讨论出真相」在期望意义上是无效的 |
| [When Self-Consistency Backfires](https://arxiv.org/abs/2608.11403)（Bahuguna et al., 预注册研究） | GPQA Diamond 难题上，多数投票使 **56.6%（Qwen2.5-7B）/ 65.7%（Llama-3-8B）的题目准确率反而下降** | 投票必须前置难度门；难题上的一致是危险信号而非健康信号 |
| [LLM Evaluators Favor Own Generations](https://arxiv.org/abs/2404.13076)（Panickssery et al., NeurIPS 2024） | LLM 评委系统性偏爱自己模型的输出（self-preference bias） | 判定 agent 与生成 agent 必须异构 |

由此得到的判断是：**AI 之间的一致不等于真相**。一致只说明"这次采样收敛了"，而采样收敛在两类情况下毫无价值——模型共享同一个盲区（相关错误），或者决策点本身超出模型能力（难题上系统性趋向错误）。因此：

1. **证据优先于票数**：结论必须挂可机验的证据锚点，无锚点的结论不许入账；
2. **一致但锚点同源 = 疑似同源错误**：两个 agent 结论一致、证据锚点却重合，视为同一个错误被复现两次，强制升级人工，不许自动确认；
3. **语义类决策即使全票一致也不自动确认**：语义理解无法被机器信号兜底，落 `needs_verification`；
4. **最终兜底只能是证据锚点 + 独立于共识的验证信号源**（如真实流量回放、灰度对比）——这条也是本项目承认的边界：测试用例本身源自共识，共识错则测试全绿，那是一种更强的幻觉。

### 2.3 由两个事实导出的三条设计公理

两条结构性事实合起来，导出了本项目的三条设计公理。后续每一章的设计都是它们的展开：

**公理 A：共识必须物化为带证据锚点的结构化对象。**

"共识"在本项目中有一个刻意收紧的定义：关于「系统应该怎么表现」、**被证据支撑、可被独立复核**的结论。它是可审计的对象，不是感觉一致。物化形态是仓库内的共识快照文件夹（`cord/<req-id>/`），由快照文档（最新层）、共识账本（机判层）、事件流（历史层）、git（版本化权威）四层组成（完整定义见 [`./02-requirements.md`](./02-requirements.md) §3.1）。判定一律查事件流/账本，显示层不参与判定。

**公理 B：AI 参与共识的方式是独立盲评，而不是辩论。**

k=2~3 个异构模型各自独立探索、独立提交、不共享中间推理；难度门只放行"非重点 + 可机验 + 可逆"的决策点；锚点独立度检查与判定/生成异构作为两道补丁堵住"一致但同盲"。2/2 一致且锚点可机验才允许 `confirmed`，语义类即便 2/2 也落 `needs_verification`，2:1 分歧落 `needs_verification` 并保留少数派理由（少数派可能才是对的，没有理由留痕，人无法判断）。

**公理 C：人只在机器共识不可靠处介入，且介入给选择题不给论述题。**

人做四类事——兜底、补充事实与上下文、决策、纠偏（定义见 §4）。系统对人的输出是一条条带选项与影响说明的问题，而不是一份需要通读的材料。介入次数上升是平台的隐性死法，因此"跨角色介入总负担"是被监控的指标（见 [`./02-requirements.md`](./02-requirements.md) §1.3）。

三条公理与机制的对应关系：

| 公理 | 机制落点 |
|---|---|
| A 共识物化 | 共识账本（条目 schema + 状态机 + 无证据不入账）、证据锚点三层（符号锚点/commit SHA/行号显示层）、事件流 append-only、块级防腐钩子 |
| B 独立盲评 | 通用投票（k=2~3、难度门、锚点独立度、判定异构）、非对称模型分配（生成弱/判定强）、门禁校验器 |
| C 人只做四件事 | 介入点三分类（事实补充/价值判断/风险仲裁）、阶段摘要、触发式升级、Issue 密度仪表盘 |

## 3. 理论底色：这个方案的思想来源

agent-cord 不是从零发明的。它的两条主要思想来源各贡献了一半的问题意识。

### 3.1 《再见SDD》：按生命周期拆分知识载体

一篇系统批评 Specification-Driven Development（SDD，规格驱动开发）的文章（[《再见SDD——Spec驱动开发为何不适合大多数项目》](https://juejin.cn/post/7667842166610247726)）给出了本项目最重要的几条设计警告。以下是其中直接影响本方案的要点：

1. **不要用一份统一 Spec 承接所有知识，要按生命周期和验证方式拆分载体**：当前任务的目标/计划/发现进任务文件（可恢复、可删除）；产品目标与验收边界进 PRD（有明确 Owner）；重要且长期的技术决策进 ADR（记录"为什么"）；契约进 OpenAPI/Schema；稳定业务行为进自动化测试；当前实现进代码。文章引述的 Birgitta Böckeler（Thoughtworks）对 SDD 的三层划分是 Spec-first（一次性上下文技巧）/ Spec-anchored（长期文档治理制度）/ Spec-as-source（改 Spec 即改代码）——三者是完全不同的工程契约，被混为一谈是概念滑坡。
2. **上下文腐化（context rot）**：错误信息因为被反复引用而获得权威，模型在错误前提上生成越来越完整、越来越自洽的实现。挂着"Source of Truth"牌子的过时文档，比普通的过时文档更危险。
3. **认知洗白**：从代码反推得到的是"当前实现的近似描述"，无法区分业务规则、Bug、临时兼容和死分支；把这类内容整理成格式漂亮的文档，等于把值得怀疑的历史偶然重新命名为正式需求。**调查结论在得到证据前应保持临时身份。**
4. **循环论证陷阱**：如果 agent 同时负责理解代码、维护 Spec、再依据 Spec 改代码，Spec 就只是它自己判断的中间产物，不能作为独立证据。文章还指出统一 Spec 的现实结局往往是"六份材料变七份"，并且"文档的价值不在覆盖面积，而在保存那些重要、稳定、无法从现状可靠推导的知识"。

agent-cord 的继承与修正：

- **继承**"按生命周期拆分载体"——快照文档（最新层）/ `ledger.yaml`（机判层）/ `events.jsonl`（历史层）/ git（权威）四层分工，正是把不同生命周期的信息放进不同物理层。
- **修正**其中被本项目否决的一支：**不做 Spec-as-source，也不维护统一规格**（ADR-0005）。共识的载体是分布式证据条目集合，权威在事件流与证据锚点，不在任何一份自然语言文档。
- **用独立证据破循环论证**：证据锚点必须指向代码、用例或知识条目，且判定 agent 与生成 agent 必异构（ADR-0007）——不允许同一个 agent 既产生结论又裁决结论。

### 3.2 群聊中的两个经验论断：认知黑盒论与 spec forge 教训

项目协作群在立项前的讨论里沉淀了两个直接被写进设计的论断：

**认知黑盒论**——「模型不知道自己不知道，我不知道模型不知道，甚至有时候还有些我不知道自己知道的东西。人机协同中最核心的是共同认知基础与"已知/未知的黑盒效应"。在复杂的业务系统里，不解决这个问题，任何自动化都是在制造定时炸弹。」这段论述的落点是：**PRD 天然模糊，不经澄清无法收敛到明确边界**，所以"零人工全自动"不是路线选择问题，而是逻辑上不成立——这正是 ADR-0001 的直接依据。

**spec forge 教训**——协作群成员复盘过一次失败的工具推广：「曾经在我们组内强制试用了一段时间，后来逐渐不用了。原因一是流程太硬了、不自由，小需求杀鸡用牛刀，大需求不适配；二是并没有真的脱离人工；说的狠一点就是，**我多花一分心智去适应一个新系统新模式，但这新模式并没有解决我那 20% 的卡点，反而把另外 80% 的自由度还限制住了**。」维护方也承认「那个工具我们也感觉有点重了，要求强 review（很强的人工干预）才能有好效果」。这条教训直接推出了两条决策：**默认轻量通道 + 触发式升级**（ADR-0002），以及**不把公司内部 SDLC 绑进基座**（ADR-0008）。

群成员对"共识管理"路线的期望也被明确记录：「流程平台要做的不是给已有的自由度加限制，而是替用户挡掉不必要的流程，让走流程的感知成本低于手动协调。」

## 4. 定位声明：共识是目标本身

> **ADR-0001 ｜ 定位为人机协作的效率放大器，不做激进全自动**
> - 决策：平台明确区分人与 AI 的职责边界。人只做四类事——**兜底、补充事实与上下文、决策、纠偏**；其余环节由框架协同完成。
> - 理由：需求天然模糊，不经澄清无法收敛到明确边界；不解决"模型不知道自己不知道"的问题，自动化程度越高，错误被放大得越大。
> - 状态：**accepted**（设计定稿）

**agent-cord 的定位是人机协作的效率放大器，而不是自动化替代品。** 这里有一个刻意的口径选择：**共识是目标本身，不是"省时间"的副产品**。缩短对齐时间、降低校验负担是共识被管理之后的自然结果，而不是项目的追求方向——把口径定在"省时间"上，会把设计推向削减人介入次数的竞赛，最终复刻 spec forge 的死法。

人的四类职责在全方案中的含义如下，后续每一个介入点都必须落回这四类之一：

| 人的职责 | 含义 | 在系统中的形态 |
|---|---|---|
| 兜底 | 机器共识不可靠时给出最终判断 | 锚点重合/分歧/不可逆动作被升级时，人看并列证据选题 |
| 补充事实与上下文 | 答案不在任何数据源中，只能由人提供 | 事实补充型介入点：填空或短选择题 |
| 决策 | 多个合理选项之间的取舍 | 价值判断型介入点：A/B/C 选项 + 各自影响说明 |
| 纠偏 | 纠正方向性错误、推翻错误共识 | 推翻流程（留痕、全文保留、不追责） |

同时，本项目有两条跨全方案的安全与权限底线（第一阶段即生效）：

- **agent 全程只产 Draft，合入永远人工**——人工合入的载体是 diff/PR，这也是"存储必须是文本文件"这类技术选型的硬约束来源；
- **判定与生成必异构**——不允许同一个模型既生产结论又裁决结论。

## 5. 做什么 / 不做什么

### 5.1 做什么

第一阶段（原型）的核心是**可扩展的开源基座**：任何团队都能定义自己的 agent 和门禁节点、热插拔自己的工作流，基座只含通用能力，不含任何公司内部业务逻辑。

| # | 能力 | 一句话说明 | 设计依据 |
|---|---|---|---|
| 1 | agent 定义 | 注册式定义角色：知识源、能力声明、模型档位、异构约束、兜底联系人；新增 agent 零代码 | ADR-0011 / ADR-0016 |
| 2 | gate 定义 | 工作流节点上的可插拔检查点：自定义"什么角色、在什么时机、执行什么校验、结果写回哪里"；新增 gate 零代码 = 组合已有校验器 | ADR-0014 |
| 3 | session / 共识快照 | 单需求一个快照文件夹：快照文档（最新层）+ `ledger.yaml`（机判层）+ `events.jsonl`（历史层）+ git（权威） | ADR-0003 / ADR-0010 |
| 4 | 事件路由 | 群聊输入 → 结构化事件 → 角色 agent；单机器人路由，统一 `NormalizedEvent`；纯 CLI 也是一个适配器 | ADR-0004 / ADR-0012 |
| 5 | 通用投票 | agent 间协作的第一个标准化协议：独立盲评、难度门、k=2~3、锚点独立度检查、判定与生成异构 | ADR-0006 / ADR-0007 / ADR-0013 |
| 6 | 上下文剪裁 | 把几十上百份仓库文档压成两层最小上下文包（前置高信号层 + 定位符层） | 见 [`./02-requirements.md`](./02-requirements.md) §4 R2 |
| 7 | 自进化知识库 | 知识条目（KB-xxxx）候选→生效→过期/废止的生命周期，bad case 回流，Issue 密度随需求序号衰减作为飞轮证据 | ADR-0015 |
| 8 | dogfooding | 平台自己的第一个需求就是管理平台自身的开发（协作群即平台的交互捕获层） | ADR-0008 |

### 5.2 不做什么

不做什么和做什么同样重要——每一条"不做"都对应一次具体的失败经验或一条已论证的边界：

| # | 不做 | 为什么 | 替代路径 |
|---|---|---|---|
| 1 | 绑定公司内部 SDLC / 内部研发平台 | 内部流程是实现层的事，绑进基座就失去了"任何团队可复用"的前提 | 内部 SDLC 作为**示例插件**（示例实现可对接 DevMaster（某公司内部平台）等内部系统），基座只定义协议（ADR-0008） |
| 2 | 激进全自动 / 零人工开发 | PRD 天然模糊；模型不知道自己不知道（认知黑盒论） | 人只做四件事；agent 只产 Draft，合入永远人工（ADR-0001） |
| 3 | 绑定特定厂商 / IM / 模型 | 可选性就是生存率：绑定即锁定用户的技术栈决策 | 三层薄接口——AgentDriver（驱动 CLIs）、ProviderAdapter（模型直连）、IM 适配器（统一事件）（ADR-0011/0012/0013） |
| 4 | 跨需求并发编排 | 第一阶段作用域刻意收窄为单个需求，共识机制先在一个需求内跑通 | 第二阶段议题（ADR-0003 作用域；演进预留接口） |
| 5 | 统一大 Spec 文档 / 统一规格 | 会制造"六份材料变七份"的同步负担，且 Spec 无法充当独立证据 | 共识账本：分布式证据条目集合，有失效机制（ADR-0005） |
| 6 | 重型固定流程模板 | 默认重型 + 用户可以逃 = 逃的人多了平台就死了（spec forge 教训） | 默认轻量通道 + 触发式升级，降级不需要理由（ADR-0002） |
| 7 | 把群聊记录或文档 frontmatter 当判定依据 | 群聊非结构化、易失、有噪声；frontmatter 会与真实历史漂移 | 群聊只是交互捕获层；**判定一律查事件流/账本**（ADR-0003/0010） |
| 8 | 把事件流塞进 LLM 上下文 | 完整历史进 prompt 会稀释注意力，反而降低判断质量 | 事件流只给人审计和程序查询用；agent 只消费投影（快照文档 + 上下文包） |

## 6. 设计原则

1. **务实落地优先**：每个功能必须对应一个可指认的真实痛点，不做概念设计、不做没有消费者的机制。
2. **可插拔**：流程节点、门禁、模型、IM、校验器均以配置或插件形式提供，无强制绑定；新增 agent / gate 零代码。
3. **机制复用优先**：已验证的现有能力（测试、截图比对、检测流水线、AGENTS.md 约定、git 工作流）直接接入，本方案只做协议与机制的增量——例如"diff 与证据锚点求交"这一套索引，同时服务文档防腐与上下文剪裁两个消费者。
4. **默认轻量、触发式升级**：小需求走快速通道，出现高风险信号（契约变更、跨仓库、投票分歧、锚点失效等）系统才提议升级，且升级提议必须携带触发器与命中证据；降级不需要理由。
5. **显示层不参与判定**：文档 frontmatter、代码行号这类"给人看"的字段只做展示，任何判定只查事件流与账本。这条原则统一适用于快照文档版本戳与证据锚点的行号层。
