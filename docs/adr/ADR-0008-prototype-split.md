# ADR-0008 ｜ 原型两分：开源基座 + 内部 SDLC 示例实现

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0001（定位与边界）、ADR-0016（分发与插件，官方插件集与冷启动）、ADR-0002（默认轻量）
- 来源：方案提案 §0 已形成共识第 4/5 条、§7 原型规划；工作清单 W1/W2；落实确认点 CP-10（已确认）、CP-24（已否决）、CP-33（暂缓）

## 背景

原型要同时服务三个彼此拉扯的目标：

1. **通用性**：定位声明里明确「不绑定特定公司、特定协作工具」。若原型长满某个组织的内部逻辑，通用能力就无法被外部复用，开源基座的价值归零。
2. **真实性**：只有通用机制的原型无法被验证——机制的价值必须在真实流程里体现，而在只有玩具示例的情况下，「机制能不能跑通」永远是推测。
3. **可参考性**：外部团队接入时的最大障碍不是机制看不懂，而是「不知道怎么把机制接到我的工具链上」。缺少可抄的样例，接入成本会把新用户挡在门外。

同时已有一条明确的共识：**本项目协作群本身就是平台要实现的东西**——平台的第一个需求就是管理自己的开发。这让「真实场景」不必外求：dogfooding 既是验证手段，也是叙事。

## 备选方案

### 方案 A：纯开源基座（只做通用能力，不含任何真实接入）

- **是什么**：只实现通用机制（agent 定义、门禁、session 存储、投票、上下文剪裁），用抽象示例与假数据演示；真实工具链接入留给使用者。
- **优点**：通用性最强；无脱敏问题；对外表述最干净；维护面最小。
- **缺点**：机制无法被真实验证——「门禁能不能拦住真实变更」「投票在真实决策点上是否有效」都停留在假设；没有可抄的接入样例，第三方团队的接入成本高；且无法完成自我验证的演示（平台的第一个需求就是管理自己的开发，这个叙事落不了地）。

### 方案 B：纯内部实现（直接把本团队的 SDLC 打通，不做通用层）

- **是什么**：以打通本组织内部研发流程为目标，机制与内部工具链耦合实现。
- **优点**：落地快；真实价值立刻可见；不需要为通用性做抽象。
- **缺点**：违背定位声明（不绑定特定公司工具）；机制与内部实现焊死，无法开源复用，也无法验证「可插拔」这个核心卖点；内部流程一变就要改机制本身。
- **不可逆**：耦合一旦形成，拆解成本远高于一开始就分层。

### 方案 C：两分——开源基座 + 内部 SDLC 示例实现

- **是什么**：原型拆成两部分。**A. 可扩展基础架构（开源基座）**：任何团队都能定义自己的 agent 和门禁节点、热插拔自己的工作流，只含通用能力、不含内部业务逻辑。**B. 内部 SDLC 打通（示例实现）**：用基座的 agent/gate schema 配置本团队的实际门禁与角色 agent，把「需求进入 → 对齐 → 执行 → 验证 → 合入」打通，作为参考实现。
- **优点**：
  - 通用能力与社区可复用性由 A 保证；真实场景验证与可参考接入样例由 B 提供；
  - B 完全用 A 的 schema 与插件协议写成（不允许开后门），因此 B 的存在本身就是对 A 可扩展性的测试；
  - 其他团队可以照抄 B、替换自己的工具链接入即可复用；
  - dogfooding 天然成立：平台管理平台自身的开发。
- **缺点**：需要维护两层边界——必须明确哪些改动属于基座、哪些属于示例，否则示例会不断向基座渗透；示例的验证仍受限于单一团队的真实场景（通用性在单例上无法被完全证明）。

## 决策

**采用方案 C。原型 = 可扩展基础架构（开源基座）+ 内部 SDLC 打通（示例实现，含内部工具链接入）。**

- **基座（A）**：包含 agent 定义最小 schema、gate 定义最小 schema、全局 session 存储、事件路由、通用投票机制、上下文剪裁；只含通用能力，不含任何内部业务逻辑。对标同类 harness 工具的可扩展性，**差异点 = 多 agent 协作协议 + 自进化能力**。
- **示例实现（B）**：用基座的 schema 配置本团队的实际门禁（契约校验、代码评审、测试门禁）与角色 agent（审查/前后端/测试）；其他团队参考此示例替换工具链接入。
- **首个端到端 Demo 形态 = 打通本项目自己的开发流程**：本项目协作群作为交互捕获层，平台管理平台自身的开发（已确认共识第 4 条）。
- **示例实现不得使用基座之外的私有扩展点**：基座提供的插件协议是唯一的扩展面，示例实现必须与第三方插件走同一套协议。

## 理由（第一性原理推导）

1. **从「开源基座的生死线是贡献者」反推**：平台的扩展性依赖社区贡献配置与插件。若基座里混入某组织的内部逻辑，外部贡献者无法理解也无法测试，贡献意愿会直接消失。因此内部逻辑必须在物理上分层出去。
2. **从「机制必须被真实验证」反推**：门禁、触发式升级、投票、防腐钩子都依赖真实变更信号与真实决策点才有意义。用假数据只能验证代码能跑，不能验证机制有效。示例实现是让机制接触真实世界的最小代价。
3. **从「接入成本是采用率的主要摩擦」反推**：新团队面对一份只有抽象 schema 的基座时，第一个问题永远是「我的 CI、我的需求单、我的截图工具怎么接」（相关待决问题已在工作清单中列出）。一份可抄的接入样例把这个问题从「设计题」降级为「替换题」。
4. **从「平台管理自身开发」这一共识反推**：既然第一个用例已经确定为管理本项目自身的开发，那么「示例实现」与「首个用例」是同一件事——不需要额外编造一个有说服力的示例场景，也不需要为此承担额外的脱敏成本。
5. **从「可插拔必须被证明」反推**：如果示例实现能访问基座内部 API，那么「可插拔」就只是一句宣言——因为它自己就没走插件协议。强制示例走同一套协议，使 B 成为 A 的持续测试：只要 B 需要绕过协议，就说明 A 的扩展面不完整。
6. **从使命与边界反推**：定位声明要求「优先适配本地开发工具链，不依赖未发布的云端能力」。示例实现正是这条边界的现实检验——它必须在内部工具链的既有能力上跑通，不能靠尚未发布的平台能力兜底。

## 被否方案的否决理由（逐一）

- **方案 A（纯开源基座）**：否决于机制无法被真实验证、缺可参考接入样例、且无法兑现 dogfooding 叙事。它的合理内核（通用性、无脱敏风险）由方案 C 的 A 部分完整保留。
- **方案 B（纯内部实现）**：否决于违背「不绑定特定公司、特定协作工具」的定位，且把核心卖点（可插拔、可复用）变成无法验证的宣言。耦合一旦形成不可逆。
- **「先做内部实现、再抽出基座」**：否决于抽离成本与时序风险。事后抽象会把内部耦合当作既定事实，抽出的通用层往往带着内部假设（例如把某个内部平台的字段结构当成通用模型）。基座先行、示例其后，是唯一能保证通用层干净的顺序。
- **「用脱敏后的外部业务示例代替内部示例」**：不作为替代方案。外部示例缺少真实风险信号（真实契约变更、真实测试失败），机制验证强度低；且需额外的脱敏设计。**脱敏范围问题本身被暂缓**（CP-33：先不考虑，原型阶段后重启，非关闭）——本 ADR 不改变这一处置。
- **「示例实现允许使用基座内部 API 以加速落地」**：否决于会使「可插拔」无法被证明，且基座与示例之间的边界会迅速消失。示例必须走公开插件协议。

## 关键实现注意点

1. **两层边界要可机械校验**：基座包不依赖示例包的代码；示例只通过公开协议（agent/gate 定义、插件协议）与基座交互。可在 CI 加一条依赖方向检查，防止反向依赖悄悄出现。
2. **示例与基座分仓或分目录，明确归属**：示例中的门禁配置、角色 agent 定义与工具链适配器都可被替换；基座中的 schema、协议、引擎不可被示例改动。
3. **接入样例必须包含三类最难接的东西**：需求单系统（需求 id ↔ session 关联）、CI/测试信号源（作为门禁校验器）、IM 平台（作为 ingress 适配器）。这三类是外部团队接入时的主要摩擦点。
4. **内部平台在开源材料中一律以 DevMaster（某公司内部平台）的形式出现**，不出现真实组织名称、人名与业务数据；开源基座不含任何业务逻辑或业务数据。
5. **示例实现就是官方插件集的一部分**（与 ADR-0016 的冷启动策略衔接）：平台管理自身开发所需的全部校验器与适配器，必须以第三方插件同等的 IPC 协议实现，并为官方插件集 v1 的成员。这条把「dogfooding 即冷启动第一步」落成结构。
6. **Demo 剧本 = 本项目自身 SDLC**（原「用某个业务需求作为 Demo 剧本」的提议已否决）：评审 Demo 时以「本项目的一个真实需求能否全程在协作群内驱动完成、所有决策可否回溯到证据锚点」作为判据。
7. **验收标准以工作清单的 DoD 为准**：新增一个 agent、一个 gate 均只需配置不需改代码；一个真实需求走完「进入 → 共识 → 计划 → 执行 → 验证 → 防腐 → 上线回流」七步；至少一轮 bad case 回流入知识库并被后续需求实际引用。示例实现是这些标准的执行现场。
8. **里程碑用相对时间表述，不写死日历**：M1 = 方案定稿后一周（方案定稿、评审通过、现状计时基线启动）；M2 = 方案定稿后第 2–3 周（基座最小闭环可运行 Demo：agent/gate/session/路由/投票）；M3 = 方案定稿后一个月（示例实现自举跑通：一个真实需求全流程在群内完成）；M4 = 方案定稿后六周（实验出数、指标仪表盘首版、自进化闭环演示一轮）。
