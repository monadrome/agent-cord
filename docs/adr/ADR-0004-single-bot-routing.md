# ADR-0004 ｜ 单机器人路由：角色 agent 做后端 worker

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0003（共识载体）、ADR-0012（事件与 IM 适配）、ADR-0014（门禁定义，命令的挂载点）
- 来源：方案提案 §5.4 翻译层（单机器人路由）、§0 已形成共识第 4 条；协作群讨论结论（每角色一个机器人前期繁琐）；Q1 多 agent 框架调研与 Q9 安全调研的交叉结论

## 背景

三层架构的中间层（翻译层）要回答一个具体问题：群里出现几个机器人？

方案的交互捕获层把协作群当圆桌：人与各角色 agent（审查、前端、后端、测试……）同席。直觉上「每个角色一个机器人」最贴近圆桌隐喻——产品找产品 agent、测试找测试 agent，职责清晰。但协作群里出现了直接反对意见：**每个角色都要创建一个机器人，前期也会有点繁琐**。这与另一个更根本的问题叠加：

- 人的认知负担：群里出现 N 个机器人时，人需要先判断「这条消息该 @ 谁」，这是在自动化之前先增加了一道人的决策；
- 部署与维护成本：每个机器人要独立的凭证、权限、上下线、人格化配置，角色数量增长时成本线性上升；
- 一致性：多机器人各自维护会话状态时，「当前结论是什么」在群里出现多个版本，与本项目要解决的共识漂移同病。

同时另有一条必须处理的架构事实：多 agent 系统的失败模式实证（MAST）显示，**agent 之间自由对话是失败高发区**——错位类失败（一方不知道另一方已改方案、对话被重置）直接源于无中介的自由对话。生产级系统收敛出的拓扑是「编排者-工作者」：编排者拆解任务、派发子任务，工作者各自独立探索后把发现交回编排者汇总，**工作者之间从不直接对话**。

于是问题从「几个机器人」升级为「群里的对话拓扑是什么」。

## 备选方案

### 方案 A：每角色一个机器人（多入口）

- **是什么**：为每个角色创建独立的机器人账号，各带独立权限与会话，人在群里 @ 对应角色。
- **优点**：职责边界直观；每个机器人的权限面天然收敛在该角色的能力范围内；单个机器人故障不影响其他角色；与「角色统一入口」的长期方向在语义上一致（角色即入口）。
- **缺点**：前期部署繁琐、维护成本随角色数线性增长（协作群已有明确反馈）；人需要承担「路由」这一决策，与「减少人不必要的工作」的目标反向；多机器人各有会话状态时，群里会出现多个并行的「当前结论」，共识反而更分散。
- **风险**：多个机器人同时在群里发言会造成信息噪声，人需自行判断谁说的算。

### 方案 B：无机器人（纯 CLI / 人肉中转）

- **是什么**：平台只在命令行侧工作，群里没有任何机器人；需求变更由人手工同步进工具。
- **优点**：零 IM 适配成本；权限面最小（不进群即不需要群权限）；实现最快。
- **缺点**：放弃最自然的交互入口。协作群是所有人（含产品、设计、测试）已经在的地方，要求他们切换工具才能参与，等于要求人配合流程——而「流程平台的死因常是要求人配合」（方案 §9.7 行为改变假设）。
- **不可扩展**：跨角色介入（产品直接对机器人说需求、测试直接触发校验）是本项目的核心价值之一，没有群入口就退化成「开发代为转述」，中转损耗回到原状。

### 方案 C：单机器人路由 + 角色 agent 做后端 worker

- **是什么**：群里只出现一个机器人。它按消息内容与 @ 对象，把结构化事件路由给对应的后端角色 agent；agent 的产出经它翻译回群里（摘要或选择题）。角色 agent 不出现在群界面上。
- **优点**：
  - 部署与维护成本收敛为一；人只需面对一个对象，认知负担最小；
  - 与业界收敛拓扑一致：agent 不直接互聊、统一经结构化共享状态中介、由单一路由/编排层调度；
  - 路由层天然是权限收敛点：它能对「谁能给谁派活、结果写回哪里」做统一声明式约束；
  - 上游/下游对称：向下解析输入为结构化事件，向上把 session 状态推回群（摘要/选择题），两个方向的翻译集中在同一处实现。
- **缺点与风险**：
  - **路由机器人是单点**：它的解析错误、进程崩溃、权限被滥用，全部后果由它承担；
  - 解析不确定时若「猜」，错误会被结构化地写进账本，比说错话更贵；
  - 需要解析置信度的工程化机制，而不只是提示词约束。

## 决策

**采用方案 C。群里只出现一个机器人做入口路由，角色 agent 作为后端 worker 不暴露在群界面。**

配套决定：

1. **解析不确定时反问，不猜**。低置信度或候选理解接近时，强制走反问（列出候选理解让人点选），反问本身也是一条事件，留痕。
2. **权限范围：只读路由 + 白名单代写**。路由机器人可读群与 session、可写 session；禁止触碰 git 与外部系统；门禁所需写权限按每个门禁的声明最小化，而不是给机器人一个整体开关。
3. **平台不注册独立命令**。slash command、@ 提及只是门禁的触发入口；命令没有独立身份，不携带自己的状态与顺序（防「命令脚本集合」退化）。
4. **CLI 也被实现为一个适配器**，与 IM 适配器实现完全相同的 ingress / 归一化接口，向上只暴露统一 `NormalizedEvent`——「同一事件模型」由类型系统强制，而不是靠纪律维持。

## 理由（第一性原理推导）

1. **从「谁承担路由」反推**：路由原本由人承担（@ 对谁）。人的注意力是稀缺资源，把路由交给机器人是净收益，且这笔收益随角色数增长而增长——角色越多，多入口方案的人的成本越高，单入口方案越划算。
2. **从失败数据反推**：MAST 的错位类失败证明「无中介的自由对话」是结构性缺陷；生产级系统的编排者-工作者拓扑证明「工作者不直接对话、统一经中介」可行。单机器人路由是这一结论在 IM 层的具体形态：群是唯一的人类入口，agent 之间不经群对话，只经结构化状态交换。
3. **从「错误后果不对称」反推**：解析错误的后果不是「说错话」，而是「把错误结构化地记进账本」。账本一旦写错，后续的投票、门禁、防腐都会基于错误事实运行，纠错成本远高于一次反问。因此在置信度不足时，反问的成本远低于猜测的期望损失——这是一笔明确的不对称。
4. **从「权限必须收敛」反推**：如果把路由机器人设计成「可以代发消息、可以代触发写操作」的全能入口，它就成了凭证与写入的超级单点；若设计成纯只读，它又无法把结果写回 session。答案只能是**按声明最小化**：读范围固定（群 + session），写范围由每个门禁字段显式声明，git 与外部系统一律禁碰。这与「授权必须在执行层强制」的原则一致：权限由平台校验，不靠机器人自觉。
5. **从「防退化」反推**：如果命令是一等公民，团队会堆出几十个命令，命令间的隐含顺序靠文档口口相传——这就是自由堆积在交互层的翻版。唯一的结构性解法是让命令没有独立身份，只能是某个门禁的触发入口字段（可多个命令指向同一门禁）。
6. **从「单点的正面利用」反推**：既然入口必须唯一，那就把这个唯一性变成资产——所有解析决策（原文 → 结构化结果 → 置信度）都作为事件入账，于是「路由到底错在哪」变成可回放、可统计的实验数据，而不是事后猜测。这直接服务方案中的回放实验设计。

## 被否方案的否决理由（逐一）

- **方案 A（每角色一个机器人）**：否决于部署维护成本与人的认知负担双向恶化，且多机器人各持会话会造成「当前结论」在群里出现多个版本，与共识目标冲突。它的合理内核（权限按角色收敛）被方案 C 中的「按门禁声明最小权限」吸收。
- **方案 B（无机器人 / 纯 CLI）**：否决于要求人改换工具才能参与，命中「流程平台死于要求人配合」的已知死因；且跨角色直接介入的核心价值无法兑现。纯 CLI 的形态不被否决——它作为**适配器之一**保留（见决策第 4 条），只是不能是唯一入口。
- **「多机器人 + 一个总调度机器人」**：否决于同时继承两边的成本。多机器人的部署与认知负担照付，而调度机器人又成为额外一层，群里还是会出现多个机器人发言；这比方案 A 更贵，不比方案 C 更简单。
- **「路由机器人可代发消息、可写 git」**：否决于凭证集中风险。写入范围一旦包含 git 与外部系统，一次解析错误就可能造成不可逆的仓库副作用；而「agent 只产 Draft、合入永远人工」的边界要求写路径必须收敛在 session 层（ADR-0001、ADR-0016）。
- **「命令注册为一等公民（每个 command 一个 handler）」**：否决于退化路径。命令必须降级为门禁的触发入口字段，否则平台会长出无状态、无顺序、无统一写回约定的命令集合。
- **「解析不确定时按最高概率猜并标注低置信度」**：否决于错误后果不对称。低置信度标注在账本里不会自动阻止错误结论被引用；反问的成本是一次交互，猜测的成本是一整套基于错误事实的下游机制。

## 关键实现注意点

1. **解析置信度工程化（落到机制，不止提示词）**：① 意图枚举收敛为有限集合（路由目标只能是已注册的角色/门禁），LLM 只做受限分类（结构化输出约束），不自由生成；② 低置信度或 top-2 概率接近时强制走反问卡片；③ 全部解析决策（原文 → 结构化结果 → 置信度）作为事件入账，可回放、可被实验消耗；④ 与权限结论叠加后，解析错误的最大后果被压到「说错话/记错账」，账本机制可容忍并纠正。
2. **CLI 与 IM 必须实现同一接口**：stdin 一行消息 → `NormalizedEvent`（actor=human, source=cli）；选择题统一为结构化 Choice 事件（选项 id + 超时 + 默认兜底），渲染层各自翻译（卡片 vs 编号输入）。「推回选择题不给论述题」由此获得单一实现点。
3. **单点的可用性防护**：路由机器人进程崩溃不得导致事件丢失——ingress 先落盘（写事件流）再分发（ADR-0012）；解析失败的任务可重放，因为原始消息与解析结果都在事件流里。
4. **IM 平台的处理时限**：飞书长连接模式要求收到事件后 3 秒内处理完成，因此路由必须「先 ACK、后异步处理」；解析耗时不能阻塞 ACK。
5. **幂等与去重**：以平台消息 id 作为幂等键；同一条消息被重投时只产生一个结构化事件，避免重复派活。
6. **群内可见性的设计**：角色 agent 的中间推理不进群；群内只出现结论、摘要与选择题。这既是降低噪声，也是盲评隔离的一部分（ADR-0006）——投票 agent 之间不共享中间推理，群更不能成为它们的中介。
7. **门禁权限声明的最小集**：路由机器人可读群与 session、可写 session；禁碰 git 与外部系统；每个门禁自带的写权限声明独立生效且取交集。这是第一阶段的安全边界，读权限面与凭证面仍需单独设计（已知缺口）。
8. **多 session 并发**：每个需求一组 session/文件夹/事件流，路由按 session_id 分区处理，天然无跨需求锁；watcher 侧需防抖与 hash 比对，避免「自己写文件触发自己」的回路风暴。
9. **不做的事**：路由机器人不做业务判断、不做投票判定、不做状态机流转判定——它只做「解析 → 路由 → 翻译回群」。所有判定逻辑在门禁与账本层，路由保持可替换（这也是「不绑定特定 IM」的兑现方式）。
