# ADR-0002 ｜ 默认轻量通道 + 触发式升级

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0001（定位）、ADR-0014（工作流与门禁定义语言）
- 来源：方案提案 §2.3 设计原则 4、§4.3 流程门禁；落实确认点 CP-07、CP-08（待确认）与 Q5 门禁设计调研的补全结论

## 背景

平台在流程节点上配置门禁（gate）：定义「什么角色、在什么时机、执行什么校验、结果写回哪里」。门禁的**默认严格程度**决定了平台能不能活下来：

- 定得太严，用户会绕开流程走手动模式，平台就成了摆设；
- 定得太松，共识错误与变更遗漏又无法拦截，平台就失去了存在理由。

同时有两个现实约束：AI 已经解决了大部分编码效率问题，所以任何新流程给用户带来的**净感知**如果是「限制」，用户退回无流程的手动模式是理性选择；而「严格」的收益（避免一次共识错误）是概率性的、滞后的，人不会为它付出日常成本。因此严格度的默认值不能靠用户自觉选择，必须由系统按信号提议、由人确认。

另一个必须提前处理的问题是：门禁结果不能只有「通过/不通过」二态。现实里存在大量「本应提醒但不该阻断」的情形，如果强行二态，团队会把校验整体关掉，或者养成一律点确认的习惯。

## 备选方案

### 方案 A：默认重型流程（可逃逸）

- **是什么**：默认所有需求走完整重型流程（多级评审、强制契约冻结、多角色确认），提供逃逸开关供紧急情况使用。
- **优点**：安全上限最高；流程完备性容易论证；对审计友好的场景（合规）几乎是唯一选择。
- **缺点**：这是重型流程平台的典型死法——**默认重型、用户可以逃，逃的人多了平台就死了**。逃逸开关会成为默认路径，而流程本身只贡献了摩擦；更糟的是逃逸行为通常不留痕，事后无法区分「真紧急」与「嫌麻烦」。
- **不可逆性**：先严后松会让老用户对平台形成「又一套审批」的印象，回撤需要重新教育用户，比一开始就轻更难。

### 方案 B：无门禁（纯工具，全凭自律）

- **是什么**：平台只提供 agent 协作与记录能力，不设任何可配置的检查点，流程严格度完全由团队自律。
- **优点**：摩擦为零，接入成本最低，短期采用率最高。
- **缺点**：放弃共识防腐的核心价值。方案的三级提交前置校验、推翻流程、契约冻结等机制都需要一个「卡点在流程里」的挂载点；没有门禁，账本会退化成一份没人看的记录，证据锚点也就失去触发时机。
- **事实依据**：无校验的规范文档会快速过时、决策变更不同步，这正是本项目要解决的问题之一。

### 方案 C：默认轻量通道 + 触发式升级（系统提议，人确认）

- **是什么**：默认走轻量通道；当变更触碰契约、跨仓库边界或验证信号显示高风险时，系统**自动提议**升级为重型流程并说明理由，人一键确认即可。降级不需要理由。
- **优点**：日常摩擦低，严格度只出现在真正需要的地方；升级提议自带触发器命中证据，人做的是确认而非判断；「降级无需理由」把不对称做进机制——平台永远偏向轻量，严格是例外。
- **缺点**：依赖触发器清单的完整性（漏掉关键触发器会导致该升级时没升级，CP-07）；依赖提议的证据质量（如果提议只是「建议升级」而不给命中证据，人会成为一律点确认的橡皮图章）。
- **结构要求**：触发器必须是声明式配置而非硬编码；每条升级提议必须携带触发器 id 与命中证据。

## 决策

**采用方案 C。默认轻量通道，触发式升级。**

- 流程严格程度由系统根据信号**提议**升级，人确认即可；**降级不需要理由**（非对称设计）。
- 门禁是流程节点上的可配置检查点，四要素为「角色 × 时机 × 校验 × 放行条件」，并为防退化补三个声明式字段：触发器、结果语义、最小权限声明（门禁 schema 见 ADR-0014）。
- 门禁结果**至少三态**：`pass`（放行）/ `block`（拦截）/ `warn-and-continue`（告警放行，必须留痕）。
- 门禁超时按「升级人工」处理，而不是静默放行。
- 平台给分档模板（默认配置），团队可覆盖，组织可强制最低集。
- 平台**不注册独立命令**：slash command 等交互入口只是门禁的触发入口别名，不构成流程本体（防「命令脚本集合」退化）。

## 理由（第一性原理推导）

1. **从用户理性选择反推**：用户面对「走流程」与「手动协调」两个选项时，比较的是**感知成本**，不是真实风险。因此设计目标不是让流程「更正确」，而是让走流程的感知成本低于手动协调。这直接决定了默认值必须轻，且严格必须是例外而非常态。
2. **从平台死因反推**：历史上流程平台的失败模式有两种——没人用（摩擦过高）与用了但空转（一律点确认）。前者由默认真轻解决，后者由「升级提议必须带命中证据」解决。二者合起来才是完整的机制设计。
3. **从不对称反推**：升级带来的成本是确定的（多一步确认、多一轮评审），收益是概率性的（挡住一次可能的共识错误）。因此升级必须由具备全局信息的系统提议（系统能算触发器命中），而人只需承担一次低成本确认；降级则相反——降级只减少成本、只放弃概率性收益，因此不需要论证。
4. **从三态语义反推**：二态门禁会把「提醒」逼成「阻断」，团队只能整体关闭或一律放行。三态让「提醒」成为合法结果，且 warn 必须留痕，使「提醒但未处理」可事后审计——这是把「确认疲劳」转化为可观测数据的最小代价。
5. **从防退化反推**：如果命令是平台的一等公民，团队会自然长出几十个命令，命令之间的隐含顺序靠文档口口相传，状态散落在各处 handler 里——这就是「命令脚本集合」，自由堆积的翻版。唯一的结构性解法是让命令**没有独立身份**：它只能是某个门禁的触发入口，门禁本身才持有状态、时机与写回目标。
6. **从超时语义反推**：如果门禁超时默认放行，那么「让门禁超时」就成了绕过机制的最短路径，与「授权必须在执行层强制」的工程原则冲突；若默认阻断，则一次挂起会阻塞整条流程。按「升级人工」处理把两者都规避：既不放行，也不无限挂起，而是转成一道要求人来处置的介入点。

## 被否方案的否决理由（逐一）

- **方案 A（默认重型 + 可逃逸）**：否决于逃逸开关必然成为默认路径，且逃逸不留痕使机制不可观测。先严后松的路径不可逆——用户印象一旦形成，回撤成本高于从未建立。
- **方案 B（无门禁、全凭自律）**：否决于放弃共识防腐的挂载点。没有门禁，账本条目不会被「被变更触碰时要求确认」所激活，证据锚点也就没有触发时机；平台退化为一份更好的会议记录。
- **「门禁一律阻断 + 人工一律确认」**：否决于确认疲劳。人一旦成为一律点确认的橡皮图章，门禁的拦截能力就归零，而流程成本照付——比没有门禁更差，因为它产生了「已经把关」的虚假安全感。
- **「slash command 作为一等命令注册」**：否决于退化路径（见理由 5）。命令可以存在，但必须降级为门禁配置上的 `command` 触发入口字段，且可多个命令指向同一门禁。
- **「门禁结果二态（通过/不通过）」**：否决于会迫使团队整体关闭校验。三态中的 `warn-and-continue` 必须留痕，否则它等价于放行（见关键实现注意点）。
- **「升级由人主动申请」**：否决于方向搞反了。人主动申请升级的前提是人已经知道风险，而那恰恰是平台应该告诉他的信息；由系统提议、人确认才是效率放大器的工作方式。

## 关键实现注意点

1. **触发器清单必须声明式且可穷举**（CP-07 的落地口径）。三类原始触发器补全为 9 类：契约变更、跨仓库边界、高风险验证信号（测试失败率突变 / 验证 agent 低置信度）、投票分歧、推翻率高的知识区域、需求中途变更、敏感路径清单、diff 规模超阈值、锚点失效。原则：每个触发器都要能回答「为什么这次升级」。
2. **升级提议必须携带触发器 id + 命中证据**。只写「建议升级」而不给证据，会把人变成橡皮图章，ADR-0002 就此失效。证据本身是一条事件，写入事件流，可回放、可实验校准。
3. **`warn-and-continue` 必须留痕且可被检索**。放行 + 留痕；未处理的 warn 进入仪表盘的待办计数，成为「我们的校验到底在拦什么」的原始数据。
4. **超时默认按升级处理**，超时时长在门禁配置中声明、有默认值；不允许「静默放行」这一选项，也不允许无限挂起。
5. **模板分档**：平台提供轻量/标准/严格三档默认配置供直接启用；团队可覆盖任意字段；组织级可声明不可覆盖的最低集。这套「模板 + 可覆盖 + 组织强制最低集」的形态有成熟先例（见证据来源中的 CI 平台实践）。
6. **门禁配置自身的变更要走门禁**：修改流程定义文件的提交命中「流程定义」敏感路径，自动挂重型门禁，并强制 prevent self-review——改流程的人不能自批自己的改动，否则 agent 或人能自改流程自放行。
7. **权限按门禁声明最小化**：每个门禁字段声明它所需的最小写权限（例如只允许写 session，不允许代发群消息），而不是给人/机器人一个粗粒度的「可读/可写」开关。
8. **误伤率是必须观测的指标**：命中门禁但实际无需处理的比例（CP-19）上限必须有明确阈值并持续测量；误伤率过高会复刻「流程税」，用户会绕过钩子。压缩误伤的手段见 ADR-0010 的锚点设计与豁免清单。
