# ADR-0005 ｜ 共识账本 = 证据条目集合，不做统一 Spec

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0003（共识载体）、ADR-0006（投票，投票记录写进账本条目）、ADR-0010（存储格式）
- 来源：方案提案 §6.1 共识账本、§6.3 推翻率；落实确认点 CP-11、CP-12（待确认）

## 背景

共识被定义为「关于系统应该怎么表现、且被证据支撑、可被独立复核的结论」。定义清楚了，但要决定的是**它的组织形态**——是维护一份承诺完整覆盖的规格文档，还是维护一组各自带证据的条目。

这个决定直接关系到项目的失败模式。项目已经识别出一个具体风险：如果平台再加上一份新的统一规格文档，团队日常要维护的文档就从六份变成七份，同步负担增加而可信度不增加——因为那份规格文档同样会过时，而且它会让「文档更新」这件事重新变成人的义务，而不是机制的副产品。同时另一个风险是单向的**迁就**：实现与共识冲突时，如果共识以文档形态存在，「顺手改文档让它一致」是最省事的路径，无人能看出留痕与否。

还有一个现实约束：本阶段的共识只覆盖**被变更触碰的切片**。需求是边进行边迭代的，不可能在开始前把所有结论一次性写全；能做的只是在每次变更触碰时，把被触碰的那部分结论确认或推翻。

## 备选方案

### 方案 A：统一 Spec 文档（一份承诺完整覆盖的规格）

- **是什么**：为每个需求维护一份统一的规格文档，声称完整描述「系统应该怎么表现」，所有结论集中在这一份文件里。
- **优点**：单一阅读入口，对人友好；完备性可作为目标被检查（覆盖率可定义）；与业界流行的规格驱动开发（spec-driven development）形态一致，团队有熟悉度。
- **缺点**：
  - 制造同步负担：需求边进行边迭代，规格要持续维护，与已有的 prd/adr/plan/findings 形成重复；
  - 完备性承诺不可兑现：一旦声称完整，任何未写入的结论都变成「文档外的隐性共识」，反而更难发现；
  - 无法表达信任度：一份文档里的结论有的被代码验证、有的只是投票一致、有的待验证，形态上无法区分；
  - 无法表达失效：条目被推翻时整份文档的可信度一起下降。
- **粒度问题**：改一行触发全文评审，或干脆全文不评审——两种极端都会发生。

### 方案 B：无结构化账本（散文文档 + 口头共识）

- **是什么**：不做账本，结论写在文档里，共识靠人与 agent 的记忆和对话维持。
- **优点**：零机制成本；写作自由度高。
- **缺点**：机判逻辑全部无法落地——投票记录、锚点独立度检查、推翻状态机、门禁放行判定都需要精确字段；「无证据的结论」无法被拒绝入账，因为根本没有入账这个动作；指标（证据覆盖率、推翻率）无法自动采集。
- **事实依据**：现状正是如此，且已被列为痛点（规范文档无校验、文档快速过时、决策变更不同步）。

### 方案 C：共识账本 = 带证据的条目集合

- **是什么**：共识以账本条目形式组织，每条自带证据锚点与状态机；账本是「架构决策记录（ADR）的字段增强版」，不是新文档类型。账本只覆盖被变更触碰的切片，不声称单一事实来源（证据才是）。
- **优点**：
  - 加的是字段不是文档类型——团队已有的 ADR 书写习惯直接复用，学习成本接近零；
  - 条目的状态、信任度来源、投票留痕、推翻记录都是**字段**，因此可机判、可统计；
  - 失效机制精确到条目：一条被推翻不影响其余；
  - 支持「无证据不入账」这样的硬门槛，把「凭感觉的共识」挡在门外。
- **缺点**：条目化会丢掉全局叙事——「整个系统大概是怎么回事」需要靠快照文档（prd.md 等）承担，账本与文档需要保持引用关系；入账有摩擦，可能抑制记录意愿（CP-11 的权衡）。

## 决策

**采用方案 C。共识账本 = 证据条目的集合，不做统一 Spec。**

条目 schema（草案）：

```yaml
id: C-002
需求: <需求id>
结论: <一句话结论>
证据:                          # 硬门槛：无证据锚点不许入账
  - {类型: 代码, 锚点: "<符号锚点>", 快照: {commit: <sha>, 行范围: "<a-b>", 内容hash: "<hash>"}, 说明: "..."}
  - {类型: 知识库, 锚点: "KB-0017", 说明: "..."}
状态: confirmed                # 状态机：临时（provisional）→ confirmed → overturned（单向流转）
置信度来源: 人确认             # 枚举：代码验证 / 投票一致 / 人确认
投票记录:                      # 完整留痕（见 ADR-0006）
  决策点: <结构化选项集 A/B/C>
  各票: [{agent, 结论, 证据锚点[]}, ...]
  少数派理由: null | {结论, 理由, 证据锚点[]}   # 2:1 分裂时必须非空
推翻记录: []                   # 空是健康信号，非零也是
关联动作: [<依赖本条目的用例/检查点>]   # 只有 confirmed 才允许驱动不可逆动作
```

三条写入规则：

1. **无证据不入账**：每条结论必须带至少一个证据锚点（代码符号锚点、用例 id 或知识条目 id），禁止无锚点结论。
2. **状态机单向流转**：临时（provisional）→ confirmed → overturned，只能前进；回退必须附新证据走推翻流程。
3. **临时（provisional）身份默认**：调查结论在得到证据前不晋升为事实——防止把历史偶然性「认知洗白」为正式需求。

## 理由（第一性原理推导）

1. **从「共识必须可独立复核」反推**：可复核的最小单元是「一条结论 + 它的证据」。文档不是可复核单元——读者无法知道文档里哪一句有证据、哪一句是推测。因此组织形态必须落在条目上，而不是文档上。
2. **从「无证据不入账」能否成立反推**：这条硬门槛要求入账动作是一个**可拦截的写操作**。文档编辑无法拦截「无证据的句子」（句子不携带结构）；条目可以（缺少 `证据` 字段即拒绝写入）。选条目形态，是这条门槛成立的前提。
3. **从「防迁就」反推**：实现与共识冲突时，最省事的路径是改共识去迁就实现。若共识是文档，改动表现为一次普通编辑，不留痕；若共识是条目，改动必须经过状态机流转（附新证据、走推翻流程），并且推翻记录被保留——「被推翻的结论本身也是知识」。机制上把省事路径堵掉，比靠纪律更可靠。
4. **从同步成本反推**：任何新增的权威文档都会增加同步负担，而负担只有在其承载的信息无法由已有载体推导时才值得付。账本不声称完整覆盖，只覆盖被触碰的切片——所以它不需要与 prd/plan 逐条对齐，同步成本有上界。统一 Spec 没有这个上界。
5. **从「ADR 生态的成熟度」反推**：决策记录入仓、带 supersede 链接、状态机流转，已经有数十年的实践（MADR、adr-tools、log4brains）。本项目要做的是在 ADR 字段上补三样东西——证据锚点、投票记录、推翻记录——而不是发明一种新文档类型。这也是「账本不是新文档类型」这一表述的由来，它直接降低了团队的心智负担。
6. **从指标可采集性反推**：三指标（证据覆盖率、独立一致度、推翻率）中，前两个必须从条目字段直接读出；推翻率需要「条目从 confirmed 变成 overturned」这一状态迁移事件。文档形态下这些都要靠人工统计，指标会自然腐烂。

## 被否方案的否决理由（逐一）

- **方案 A（统一 Spec）**：否决于同步负担无上界 + 完备性承诺不可兑现 + 无法表达信任度与失效。它的合理内核（全局叙事）由快照文档承担，两者是分工而非替代。
- **方案 B（无结构化账本）**：否决于机判逻辑无载体。投票、锚点独立度、状态机、门禁放行四类机制全部依赖精确字段，没有账本它们无法落地；且现状已经证明散文文档会过时、会不同步。
- **「账本 + 统一 Spec 双轨」**：否决于双写漂移。两个载体都声称权威时，必然出现「Spec 说 A、账本说 B」的状态，而判定规则无处安放。项目已明确：判定一律查事件流/账本，Spec 不是判定源。
- **「无证据也可入账，但标低置信度」**：否决于门槛会失效。允许无证据入账后，无证据条目会被引用、被积累，最终形成一批无法复核的「常识」；而「临时」状态的语义就是在有证据前不晋升为事实——所以正确做法是保留在临时态，而不是入账后降级标注。
- **「状态机允许 confirmed 静默回退」**：否决于会摧毁防迁就机制。若能静默回退，「改共识迁就实现」重新变成省事路径，整个推翻留痕设计失效。
- **「把知识条目也写进账本」**：否决于作用域混淆。账本条目是「按需求组织的结论」，知识条目是「跨需求复用的规则」；混在一起会让 session 无限膨胀，也违反上下文窗口需剪裁的实证结论。两者分离、以锚点互链（账本引 KB，KB 引证据）。

## 关键实现注意点

1. **写入路径唯一**：账本的所有变更（新增条目、状态流转、追加投票记录、写入推翻记录）必须经单一 `append_event` 通道，再由投影同步进 `ledger.yaml`。绕过通道直接编辑 `ledger.yaml` 会破坏事件流与现状的一致性，建议加确定性检查命令（fold 事件流 vs 实际账本）并纳入 CI。
2. **证据锚点三层结构**：条目 `证据` 字段不使用单一 `文件:行号`——行号在重构下漂移，既会漏检也会误伤。改为「符号锚点（活，参与判定）+ commit SHA 与内容 hash（存档）+ 行号（仅显示层）」，具体见 ADR-0010。
3. **`投票记录` 是 ADR-0006 的落地容器**：字段结构（决策点 / k / 各票 / 统计 / 判定 / 少数派理由）在 ADR-0006 中定义；2:1 分裂时 `少数派理由` 必须非空，且随判定一并推给人。语义理解类决策（不可机验，不满足投票队列硬条件）不进投票队列，直接落 `needs_verification` 交人工；配置性参考投票的结果也不落地 `confirmed`。
4. **`关联动作` 是上游索引**：只有 `confirmed` 条目才允许驱动不可逆动作；测试失败时可用它反查来源条目，这是推翻率的三个自动采集来源之一。
5. **推翻率按原因分类采集**：证据不足 / 语义理解错 / 需求变更 / 外部依赖变化。三个采集来源都要回链条目 id：测试失败反查用例来源条目、线上问题归因时关联需求 id、后续需求探索时提交推翻申请（附新证据）。原条目改 `overturned` 并**保留全文**。
6. **零推翻率是警报而非满分**：说明验证信号太弱或观察期太短。推翻不追责是文化约定（CP-17），否则指标会被博弈（条目被标低置信度逃责）。
7. **条目 id 与需求 id 都要稳定**：条目 id 发放后不改（防引用断链）；跨需求引用只引 id，不引文件名。
8. **入账摩擦的观测**：CP-11 的权衡需要数据——记录「被拒绝入账」的次数与原因，若摩擦显著抑制记录意愿，应在不放弃硬门槛的前提下改进入账工具（例如从 diff 自动抽取候选锚点），而不是松开门槛。
