# ADR-0001 ｜ 定位为人机协作的效率放大器，不做激进全自动

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0002（默认轻量 + 触发式升级）、ADR-0008（原型两分）
- 来源：方案提案 §2 定位、§9.5 权限与安全模型；落实确认点 CP-01、CP-02（已确认）、CP-29（权限最简模型，待确认）

## 背景

当前 AI 辅助开发的典型工作方式中，以下五类成本被反复观察到：

| # | 痛点 | 具体表现 |
|---|---|---|
| P1 | 碎片化交互成本高 | 人与 AI 反复分步交互，大量时间消耗在需求对齐与等待输出上 |
| P2 | 前期对齐负担重 | 接手新需求需与产品、设计、后端、测试逐一对齐，常以天计 |
| P3 | AI 输出校验负担重 | 长周期运行产出体量大，全量 review 不现实，且存在幻觉 |
| P4 | 需求变更无统一载体 | 变更散落在私聊和群聊中，极易遗漏 |
| P5 | 上下文切换成本高 | 多会话、多沟通群之间来回切换，重复粘贴历史信息 |

其中有一个结构性事实决定了投入方向：**验证环节（测试、截图比对）已经高度自动化，而共识环节（人脑中的业务模型与代码现实对齐）没有**。大部分项目时间实际消耗在共识上，而不是消耗在「把代码写出来」上。

这个事实把问题变成两个必须同时回答的追问：(1) 平台的目标到底是「少写代码」还是「少在错误的对齐上打转」？(2) 人和 AI 的职责边界画在哪，才既不放任错误放大、又不把人变回瓶颈？

## 备选方案

### 方案 A：激进全自动（端到端无人值守）

- **是什么**：需求进来后由多 agent 全自动完成澄清、设计、实现、验证、合入，人只在最终产物交付时出现。
- **优点**：理论上人力投入最低；叙事最吸引人；省去所有介入点设计。
- **缺点**：需求天然模糊，不经澄清无法收敛到明确边界；平台无法解决「模型不知道自己不知道」的问题——自动化程度越高，错误被放大得越大。共识错误还会被自动化验证放大：测试用例源自共识，共识错则测试全绿，形成更强的幻觉闭环（方案 §9.2 风险）。
- **外部事实**：多 agent 系统的失败模式已有系统实证，错位类与验证缺失类失败直接源于缺乏人工兜底与中介（见证据来源 MAST）。

### 方案 B：纯效率工具（不定义人机边界，能自动就自动）

- **是什么**：不做职责边界声明，把能力堆上去，谁能自动就自动，出现问题再打补丁。
- **优点**：不预设结论，形态更灵活；对早期用户不附加任何流程约束。
- **缺点**：无法定义「介入点」——介入点设计需要知道「什么必须由人做」，没有边界就只能靠事后救火；平台会退化成人肉审核队列（所有产出都推给人看），反而增加人的负担，与 P3 的痛点同向恶化。
- **指标后果**：没有边界就导不出正确的度量取向。若以「节省写代码时间」为指标，会鼓励提高自动化比例、压低人工确认次数，恰好走向风险更大的方向。

### 方案 C：人机协作效率放大器（明确划出四类人工职责）

- **是什么**：平台是协作放大器，不是替代者。人只做四件事——**兜底、补充事实与上下文、决策、纠偏**；其余环节由框架协同完成。平台主动声明自己不做什么。
- **优点**：边界清晰且可检验：任何新功能都能回答「它是在替代这四类事，还是在放大这四类事的效率」；介入点可以按职责类型分类设计（事实补充型 / 价值判断型 / 风险仲裁型）；度量取向自然导出为「共识质量 + 人介入负担」两组指标。
- **缺点**：需要显式设计介入点，无法靠「人总会看一眼」兜底；对「人能容忍多少选择题」有依赖（选择题疲劳是平台的隐性死法）。

## 决策

**采用方案 C。本项目定位为人机协作的效率放大器。**

明确区分人与 AI 的职责边界：人只做四类事——兜底、补充事实与上下文、决策、纠偏；其余环节由框架协同完成。不做零人工介入的全自动开发。

同时声明平台**不**做什么（边界声明）：

- 不追求零人工介入的全自动开发；
- 不绑定特定公司、特定协作工具（通用能力优先）；
- 不强制固定流程（可插拔，团队自定义适配）；
- 优先适配本地开发工具链，不依赖未发布的云端能力。

权限与安全按同一取向收敛：**agent 全程只产 Draft，合入永远人工**（第一阶段最简安全模型，见 ADR-0016 与关键实现注意点）。

## 理由（第一性原理推导）

1. **从投入方向反推**：既然验证已自动化、共识没有，那么把算力投在「自动化更多实现步骤」的边际收益远低于投在「让共识可复核、可度量」。定位必须服务于后者。
2. **从失败结构反推**：需求天然模糊 + 模型不知道自己不知道 = 未经澄清的自动化必然放大错误。要打破这个结构，只有两条路：让机器获得更强的独立验证信号（成本高、部分场景不可得），或引入人的兜底与纠偏（可得且便宜）。本平台选后者作为底线，同时用证据锚点与独立验证信号持续抬高前者。
3. **从「人为什么不得不出现在流程里」反推**：人介入的真实原因只有四类——机器无法兜底的风险、数据源里不存在的事实、多个合理选项之间的取舍、以及执行偏离目标后的纠正。把这四类之外的所有介入都设计掉，就是「效率放大器」的可操作定义。
4. **从度量反推**：目标若定为「省时间」，指标会奖励压低确认次数；目标定为「建立共识」，指标才落在证据覆盖率、独立一致度、推翻率、Issue 密度上。后者与安全方向一致，前者与安全方向冲突。
5. **从安全边界反推**：只要承认人负责兜底与决策，第一阶段的权限最简模型就是自然的——agent 只产 Draft、合入永远人工。这与业界主流 coding agent 的默认权限取向一致（见证据来源），不需要额外论证。

## 被否方案的否决理由（逐一）

- **方案 A（激进全自动）**：否决于错误放大结构与验证幻觉闭环。共识一旦错，自动生成的测试会把错误固化；且平台无法提供独立于共识的真值源来兜底（方案 §9.2 已列为风险，CP-27 要求引入独立验证信号源）。「不做」是安全决策，不是保守偏好。
- **方案 B（纯效率工具、不定义边界）**：否决于介入点不可定义、度量取向错误。没有边界就无法判断哪些环节该找人、找谁；且以「省时间」为指标会系统性地奖励减少人的介入，与本方案的安全取向反向。方案 B 的形态自由是伪优点——自由度最终会由用户在用歪之后自行收回，代价是平台信誉。
- **「先做全自动、再往回加人」的渐进路径**：否决于不可逆性。自动化先行会吸引以吞吐为目标的用法，等发现共识错误率高时，用户的工作方式已经绑定在吞吐上，回撤会直接导致弃用。反过来（先人机协作、再逐步自动化）是可逆的：每次减少一个介入点都可以独立验证安全性。

## 关键实现注意点

1. **度量取向由本 ADR 锁定**：共识质量侧 = 证据覆盖率、独立一致度、推翻率；人介入负担侧 = Issue 密度、单介入耗时、跨角色介入总负担。任何新指标提案必须归入这两组之一，不允许再引入「节省小时数」类单轴指标替代它们。
2. **介入点的判据**：设计任何新流程节点时，逐一回答「这一步属于兜底 / 补充事实 / 决策 / 纠偏 中的哪一类」。答不出来说明该步骤不应由人做，应交回框架；答得出来则按类型选择形态（填空或短选择题 / A-B-C + 影响 / 分歧理由与证据并列）。
3. **只给选择题，不给论述题**：人的每个介入点必须是有限选项 + 默认兜底 + 超时策略，长文自由输入只能是选项之外的补充通道，不能是唯一通道。
4. **Draft-only 是硬边界**：agent 的写权限收敛在「产出草稿」上，合入、发布、契约冻结一律人工。实现层对应的是权限白名单与 IPC 插件的凭证注入策略（ADR-0016），不是靠提示词约定。
5. **不绑定厂商的落地口径**：「不绑定」指的是核心机制（事件模型、账本、门禁、投票协议）不依赖某家能力；具体 provider 与 IM 各自有适配器，替换成本收敛在单个适配器文件（ADR-0011、ADR-0012、ADR-0013）。
6. **「不强制固定流程」的落地口径**：平台只提供默认轻量通道与分档模板，团队可覆盖，组织可强制最低集（ADR-0002、ADR-0014）；不存在「必须走某条流程才能用」的前提。
7. **本 ADR 不覆盖的空白**：读权限面、凭证面与网络面不由本 ADR 决定（安全模型单列设计），Draft-only 只覆盖「写」这一根轴；这是已知缺口，不允许在实现中默认「已经安全」。
