# ADR-0013 ｜ 投票执行器：ProviderAdapter 直连模型 API，不复用 coding CLI

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0006（盲评投票规则）、ADR-0007（判定与生成异构）、ADR-0011（生成侧走 CLI 驱动）、ADR-0005（投票记录写入账本）
- 来源：本方案技术选型调研（2026-09，内部调研纪要）——通用投票机制的实现

## 背景

角色 agent 已定为「驱动现有 coding CLI」执行任务（ADR-0011）。但投票 agent 是**判定者**而不是**生成者**：按非对称模型分配，它需要的是「能确定性地产出『结论 + 证据锚点[] + 置信度』的一次受控调用」，而不是「一个能改代码的 agent 内核」。

因此本决策点要回答五个工程子问题：

1. **投票 agent 的模型执行器用什么**：多 provider 路由走代理（LiteLLM 类）/ 各家原生 SDK 直连 + 薄抽象层 / 复用 coding CLI 本身 / 托管网关。
2. **盲评隔离怎么工程实现**：k 个异构投票 agent 之间不共享中间推理，且不能共享位置偏置（需要 per-agent 选项随机化）。
3. **证据锚点独立度检查怎么算**：两个 agent 结论一致但锚点重合 → 疑似同源错误 → 强制升级人工。
4. **投票记录 schema 与共识账本 `投票记录` 字段如何衔接**。
5. **难度门怎么判定**：只投「非重点 + 可验证」的决策点。

关键约束：开源基座、不绑定厂商、异构跨 provider、成本可核算（token 是噪声级成本但需可采集）、可复现（temperature=0、锁模型版本、记录 prompt hash）。

## 备选方案

### 备选 A：LiteLLM（SDK 模式或 proxy 模式）

- **是什么**：用 OpenAI 兼容格式统一 100+ provider 的代理层，自带 failover、成本追踪、预算控制、虚拟 key。
- **优点**：接入新 provider 成本极低（改一个 model 字符串）；成本/用量追踪开箱即用；社区活跃。
- **缺点**：① 作为 **proxy 进程**引入一个常驻有状态服务，是本平台的又一个单点（单机器人路由已是单点，平台原则是「默认轻量」）；② 生产规模下的性能/内存问题有公开记录，而投票是低频调用，用不上它的路由/failover 高级特性；③ 抽象层对各家差异（思考参数、推理强度、结构化输出细节）的抹平是「最小公分母」，而异构投票恰恰需要**暴露**差异；④ 若基座不是其宿主语言则整体不可用。
- **契合度**：中。适合作为「provider 适配加速器」，不适合作为架构核心。

### 备选 B：原生 SDK 直连 + 薄抽象层（`ProviderAdapter` 接口）

- **是什么**：自定义接口 `complete(VoteRequest) → VoteResult`，每 provider 一个 50~150 行适配器；能用 OpenAI 兼容端点的（多家国内外厂商与多数开源网关）共用一个适配器，差异大的（Anthropic、Gemini）单独写。
- **优点**：① 零常驻基础设施，纯库依赖；② 能精确暴露投票需要的全部控制面——temperature=0、模型版本锁定、system prompt 注入、结构化输出约束、逐次 usage 与成本字段；③ 不绑定任何中间件，「适配器就是全部绑定面」，替换成本一目了然；④ 与基座技术栈一致（不强迫引入第二种语言运行时）。
- **缺点**：每接一个 provider 要写/维护一个适配器（OpenAI 兼容族约等于零成本，长尾 provider 有成本）；没有内置 failover——但投票场景不需要 failover，失败重试是编排层几行代码。
- **契合度**：高。控制面完整匹配盲跑协议的全部要求。

### 备选 C：复用 coding CLI 作为投票执行器

- **是什么**：投票 agent 就是各家 CLI 各起一个 headless 实例，复用已定型的 CLI 驱动层。
- **优点**：① 完全复用已有抽象，新增角色零成本；② 订阅制计费下边际成本近零；③ 天然异构（不同 CLI = 不同模型家族）。
- **缺点（对本场景是致命的）**：① **确定性失控**——headless CLI 不暴露采样参数与模型版本锁定（CLI 跟随服务端灰度），「temperature=0、锁定模型版本」的可复现性无法满足，而回放校准实验恰恰依赖可复现；② **输出契约弱**——CLI 输出的是会话 transcript，不是 `{选项, 证据锚点[], 置信度}` JSON，需要解析层 + 重试层，且 CLI 有项目级配置、记忆、权限提示等隐式上下文注入，**盲评的「净输入」不可审计**（净输入审计脚本在 CLI 上很难做彻底）；③ 每次投票是一个完整 agent loop（工具调用、文件读写），比一次受控补全贵一个数量级，还引入写权限风险；④ 批量自动化投票的用量配额/条款不友好，且成本无法按次精确采集；⑤ CLI 的 session 状态（记忆、历史）是盲评隔离的污染源，需额外清理。
- **契合度**：低。作为角色 agent（生成侧）执行器合理，作为投票执行器错配。

### 备选 D：托管路由网关（OpenRouter 类 / 云厂商网关）

- **是什么**：由第三方托管做多 provider 路由。
- **优点**：接入快、模型全。
- **缺点**：引入外部托管依赖，与「不绑定特定厂商 / 本地工具链优先」的边界冲突；请求经第三方与凭证/安全模型冲突。
- **契合度**：否决。

## 决策

**采用备选 B（原生 SDK 直连薄抽象层）为核心；备选 A（LiteLLM SDK 模式）作为可选加速件而非依赖；盲评隔离、锚点独立度检查、难度门全部由编排层以纯工程手段实现。**

1. **接口**：`ProviderAdapter.complete(VoteRequest) → VoteResult`；`VoteRequest` 含 `{model_id@version, temperature, system_prompt, user_prompt, response_schema}`；`VoteResult` 含 `{parsed_json, raw_usage, latency, request_id}`。
2. **`model_id` 必须带版本后缀**，并写入投票记录；否则回放实验的可复现性落空。
3. **OpenAI 兼容族共用一适配器**（覆盖多家），差异大的 provider 各一；新 provider 接入 = 新增一个适配器文件 + 配置，零平台代码改动（满足「零代码可扩展」原则在 provider 维度的延伸）。
4. **重试/超时在编排层做**：判定失败重试 1 次仍失败 → 该票记 `abstain`，不阻塞整体（与「证据不足」兜底项语义一致）。
5. **LiteLLM 只作为写适配器的加速件**：若团队自行选用，接口必须仍是平台自己的 `ProviderAdapter`，**不把第三方类型泄漏到平台核心**。
6. **CLI 驱动层保留给生成侧角色 agent**（ADR-0011）；判定侧走本 ADR。一个平台对两侧使用不同执行器，是「非对称模型分配」在执行器层的对应物。

## 理由（第一性原理推导）

1. **投票的本质是 k 次受控、可复现、可审计的判定调用**，不是 k 个通用 agent 任务。它需要的控制面（采样参数、版本锁、结构化输出、用量计量、净输入审计）只有直连 API 能给全（B）；CLI 给不全（C）；proxy 给得全，但附带不必要的基础设施重量（A）。
2. **平台的第一死法是流程税与基础设施重量**（ADR-0002 的精神）。投票是低频调用（回放实验量级在数百次），failover / 负载均衡 / 缓存这些 proxy 的核心价值对本场景全部无效——为一个几行重试能解决的问题养一个常驻有状态服务，不划算。
3. **异构是投票机制的命根**（ADR-0006）。异构要求暴露 provider 差异而非抹平差异；薄适配器把「绑定面」收敛到每 provider 一个文件，比代理的黑盒映射更可控、更可审计。
4. **CLI 复用的真正价值在生成侧**（角色 agent 需要工具使用与长程编辑），与投票侧的需求正交。把两侧混用会同时得到「投票不可复现」与「生成不够灵活」两个坏结果。
5. **成本不构成给 C 辩护的理由**：token 是噪声级成本（约占人力基线 2% 以内；换算口径：按配套调研（2026-09）Q8 的成本模型，把每需求的 token 费用按当时费率折算为等效人力分钟数，再除以人力基线），「省订阅费」不成立；而可精确逐次计量的直连 API 反而服务于成本核算与验收要求。
6. **从「盲评的净输入必须可审计」反推**：盲评的可信度取决于「每票看到的东西完全可控」。CLI 会注入项目配置、记忆与权限提示，这些是隐藏输入，无法声明式地穷举，因此 CLI 在结构上无法满足净输入可审计的要求——这不是实现难度问题，是形态问题。

## 被否方案的否决理由（逐一）

- **备选 A（proxy 模式）**：否决于常驻有状态服务 = 额外单点 + 运维面，与「默认轻量」冲突；投票低频场景用不上其路由特性；生产规模下的性能/内存问题有公开记录。**SDK 模式部分采纳**：允许团队用其 SDK 作为写适配器的加速器，但接口必须是平台自己的 `ProviderAdapter`，第三方类型不进入平台核心。
- **备选 C（CLI 作为投票执行器）**：否决于五条同时命中核心约束——确定性不可锁定（无法 temperature=0 / 锁版本）、盲评净输入不可审计（隐式上下文注入）、输出契约需脆弱解析、成本不可逐次核算、session 状态污染隔离。
- **备选 D（托管网关）**：否决于外部托管依赖违反「不绑定特定厂商、本地工具链优先」，且数据经第三方与凭证/安全模型冲突。
- **「用同一 provider 的不同模型做异构」**：允许但标注为弱形态——同一 provider 内部模型的错误相关性高于跨 provider，「判定与生成必须异构」的约束不接受同家族的不同型号作为充分条件（详见 ADR-0007）。
- **「投票 agent 用与生成同一个 CLI 但不同模型参数」**：否决于本 ADR 的全部理由（CLI 侧无法锁定这些参数，所谓「不同参数」不可验证、不可复现）。
- **「为投票单独建一个常驻投票服务」**：否决于额外单点与部署面，且投票无需常驻状态——每票的输入输出都落在事件流与账本里，服务本身无状态可重放，没有必要独立成服务。

## 关键实现注意点

**模型路由层**

1. `VoteRequest` 必须显式携带 `model_id`（带版本）、`temperature`（投票固定为 0）、`response_schema`（结构化输出约束）与 `system_prompt`；`VoteResult` 必须回传 `raw_usage` 与 `request_id`（供成本采集与溯源）。
2. 适配器不得对「模型不可用 / 版本下线」静默降级到其他模型——降级必须显式记录为该票异常，否则投票记录的 `model_id` 会与真实执行不符，可复现性被破坏。
3. 重试次数与超时在编排层统一定义，不同 provider 的策略集中在配置里，不散落在适配器中。

**盲评隔离（工程实现）**

4. 每票 = 独立进程 + 独立临时目录，进程间无共享内存与文件；编排层只通过 IPC 收集最终 JSON。
5. 上下文注入由编排层预组装：**只读 git worktree（detach 到指定 commit）+ 仅挂载该票可见的文件白名单**，从机制上杜绝「读到其他票输出」的可能，而不是靠提示词约束。
6. **per-agent 选项随机置换 + 决策点顺序随机化**，置换记入投票记录（供事后反查位置偏置）。
7. **盲评审计脚本常态化**：作为门禁的一个校验器——净输入中出现其他票输出或人工结论关键词 → 该票作废重跑。这一步把「禁止互见中间推理」从提示词升级为编排层强制。

**证据锚点独立度检查**

8. 锚点采用三层结构：**符号锚点（活）+ commit SHA（存档）+ 行号（仅显示）**。独立度比较**只比规范化后的符号锚点**（文件路径 + 顶层符号路径），行号不参与（漂移 + 巧合重合都会污染）。
9. 重合度计算：对两票的锚点集合算 Jaccard 相似度；**重合度 ≥ 0.5 或一方集合是另一方子集**且结论一致 → 标记疑似同源错误 → 该决策点强制升级人工，投票记录中记 `independence_flag: anchor_overlap`。阈值 0.5 为初值，校准输入来自回放实验的锚点重合度统计。
10. 只需处理「一致 + 重合」这一个危险象限：结论一致而锚点完全不同才是独立验证的健康信号，不需要额外规则。

**投票记录与账本衔接**

```yaml
投票记录:
  决策点: {id, 结构化选项集, 难度桶, 可机验性: true|false}
  k: 3
  各票:
    - {agent_id, provider, model_id@version, prompt_hash, option_permutation,
       结论, 证据锚点[], 置信度, usage, request_id}
  统计: {原始一致率, fleiss_kappa, gwet_ac1, anchor_overlap: <值>}
  判定: confirmed | needs_verification | escalated_anchor_overlap
  少数派理由: null | {结论, 理由, 证据锚点[]}   # 2:1 时必填，随 needs_verification 推给人
```

11. 写回规则：判定为 `confirmed` 且账本条目 `置信度来源: 投票一致` 时，投票记录整体嵌入账本条目；语义类决策（`可机验性: false`）不满足投票队列硬条件、不进队列，直接落 `needs_verification` 交人工（ADR-0006）；配置性参考投票的结果也不落地 `confirmed`。

**难度门判定**

12. 决策点入投票队列前过三个硬条件（门禁配置，非代码）：① **非重点**——不在重点决策点清单内；② **可机验性**——证据锚点类型 ∈ {代码, 用例}（存在可机器执行的验证信号）；③ **可逆性**——不在「不可逆动作清单」内。不满足任一条件者不进队列，直接落 `needs_verification` 交人工。
13. 软信号（触发式升级同款哲学）：决策点标签 ∈ {契约, 跨模块语义} → 即使可机验也强制 k=3 而非 k=2；历史推翻率高的标签类别 → 自动降置信度并强制投票（推翻率回流机制的消费端）。
14. 判定逻辑本身是门禁 schema 的一个校验器实现（`checks: [难度门]`），新增判定规则 = 改配置，符合零代码原则。
