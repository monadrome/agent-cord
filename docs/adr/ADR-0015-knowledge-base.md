# ADR-0015 ｜ 知识库：Markdown 为唯一 SSOT，FTS5 为派生索引

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0003（共识载体）、ADR-0005（账本条目与知识条目的分离）、ADR-0006（复述检验复用投票协议）、ADR-0010（派生索引边界）
- 来源：本方案技术选型调研（2026-09，内部调研纪要）——自进化知识库的存储与检索；方案提案 §6.7 自进化能力

## 背景

知识条目 = 跨需求沉淀的规则 / 术语 / 踩坑（状态机：候选 → 生效 → 过期/废止）。本决策点在四大约束下展开：

1. **SSOT = 快照文件夹 + git**：知识库是同一 SSOT 的一等公民，不是另一个系统；
2. **人永远是合入者**（Draft-only）：知识条目的「生效」必须走人工背书，生命周期机制必须能落在「配置化门禁 + 人工确认」上，零代码；
3. **最小上下文包已定型为两层**（前置高信号层 + 定位符层，agent 直读）：知识条目如何进入上下文包已有挂载点，选型必须服务这个接口而非另造注入协议；
4. **证据锚点体系已定型为三层**（符号锚点 + SHA 快照 + 行号显示层）：知识条目既是锚点的消费者（条目引用代码证据），也是锚点的生产者（`KB-xxxx` 被账本条目引用）——双向可审计是硬要求。

条目规模按 dogfooding 估算是**百级到千级**，远未到「向量库才扛得住」的量级。这是量级判断，后面所有推导都从这里出发。真正要回答三个子问题：**(a) 条目存哪；(b) 检索起步走符号/词法还是 embedding；(c) 生命周期与复述检验怎么工程化成门禁。**

## 备选方案

### 备选 1：纯 Markdown 文件 + frontmatter（无独立索引）

- **是什么**：每个条目一个 `.md`，frontmatter 携带 `id / status / source_anchors / confidence / created / supersedes` 等元数据；检索靠 agent 用读文件/glob/grep 自主导航（定位符 + 即时拉取模式）。
- **优点**：零基础设施；git 天然版本化与审计；人可直接读改（符合「先有可读可改的事实来源，再谈索引」的业界共识）；无索引漂移问题；与 SSOT = 文件夹的总架构同构。
- **缺点**：纯 grep 检索质量差——无相关性排序、无字段过滤（「只查生效条目」要逐文件解析 frontmatter）、中文分词缺失；每次检索的 token 成本由 agent 自主导航效率决定，弱模型任务上不划算。
- **契合度**：作为**存储层**极高；作为**唯一检索层**不足。它是源，不是引擎。

### 备选 2：SQLite + FTS5 全文检索（文件为源 + 索引为加速层）

- **是什么**：Markdown 文件保持为唯一 SSOT；一个由文件确定性生成的 SQLite 库做检索加速——FTS5 提供相关性排序的全文本检索，普通表存 frontmatter 元数据，SQL 做结构化过滤（如 `WHERE status='active' AND confidence>0.7`）。索引是**派生产物**，可随时全量重建，不进 git 或进 git 作缓存均可。
- **优点**：单文件、零部署、嵌入应用内；FTS5 是 SQLite 内置扩展，无额外依赖；结构化过滤 + 全文排序一个引擎搞定，恰好覆盖「按状态/置信度过滤 + 按内容排序」的生命周期检索需求；索引可确定性重建，漂移有工程解；与「驱动现有 CLI」的架构兼容。
- **缺点**：FTS5 默认分词器不切中文，中文全文需用 trigram 分词（SQLite 3.34+）或外挂分词——真实但不大的坑；索引新鲜度需要写路径兜底（本方案有天然优势：条目**只经门禁写入**，写入钩子里同步更新索引即可准实时，不需要轮询或增量索引树）。
- **契合度**：作为**检索层**高度契合。它把备选 1 的唯一短板补掉，同时不引入任何与「SSOT = 文件夹」冲突的东西。

### 备选 3：向量数据库 / embedding RAG

- **是什么**：条目切块 → embedding → 向量库，语义相似度召回。
- **优点**：语义召回强（「踩坑记录里那个没说名字的坑」也能召回）；对同义词/改写鲁棒。
- **缺点**：① **可审计性弱**——向量是黑箱，「这条知识为什么被召回/被注入」无法向人解释，与「证据锚点双向可审计」冲突；② **索引保鲜成本**——条目由 agent 高频写入时，embedding 流水线（分块、模型、增量同步）成为写入路径的拖累，需要复杂的增量索引机制；③ **防上下文腐化更弱**——错误条目 embedding 语义相近会被一起召回，恰恰放大「错误信息被反复引用获得权威」这一要防的问题；④ 规模不匹配——千级条目用向量库是杀鸡用牛刀。
- **契合度**：起步低；后续有明确升级需求时可作**可选插件**补语义召回（FTS5 + 向量 + 混合排序已是成熟模式），但不应是 v1 底座。

### 备选 4：知识图谱 / 图数据库

- **是什么**：条目为节点，`supersedes / contradicts / applies_to / derived_from` 为边，图遍历检索。
- **优点**：条目间关系（替代 / 推翻 / 适用范围）天然是图；推翻链条可视化对复盘友好。
- **缺点**：对百级–千级条目是重型依赖；图查询对「找相关踩坑」这种主要检索意图并不优于全文检索；边关系本身可以也应当以 frontmatter 字段 + 确定性脚本生成，不必上图库。
- **契合度**：否决为独立方案；其**有价值的一部分（条目间关系）被吸收进 frontmatter schema**，符号图倾向以「轻量链接」而非「图数据库」形态落地。

### 隐含的第五方案：把知识直接塞进全局 session / 账本

- **否决理由**：账本条目是「按需求组织的结论」，知识条目是「跨需求复用的规则」；混在一起会让 session 无限膨胀，也违反上下文窗口是稀缺资源的实证结论。两者保持分离、以锚点互链（账本引 KB、KB 引证据）才是已定型的实体关系。

## 决策

**Markdown + frontmatter 为唯一 SSOT（每条目一文件），SQLite + FTS5 为派生检索加速层（文件为源、索引为缓存）；检索起步走符号/词法路线（FTS5 相关性排序 + frontmatter 结构化过滤 + 条目间链接），embedding 推迟为可插拔的后续增强。**

配套决定：

1. **位置**：`conclave/knowledge/` 是唯一跨需求目录；需求归档后其 confirmed 条目的**抽取**（不是移动）入 knowledge。
2. **生命周期工程化 = 状态机 + 门禁复用，不新造机制**：
   - 候选 → 生效：满足三个条件自动晋升——(a) 复述检验通过、(b) 证据锚点机验有效、(c) **人工在 IM 侧点确认**（复用单机器人路由的「选择题推回」通道，合入永远人工的总边界在此自然落地，零代码）；
   - 生效 → 过期/废止：时间（`review_due` 到期）+ 信号（被引用时锚点失效、推翻记录命中、关联代码删除）双触发，走同款门禁 + 人工确认；废止留痕、全文保留。
   - **「双人确认」落地为「异构复述 agent + 人」**，不是两个真人——人工介入负担是平台的隐性死法，双人真审会变成收税点。
3. **复述检验 = 门禁校验器，是 k=2 异构盲评投票的直接复用**：
   - 复述 agent（与抽取 agent **异构**，防 self-preference）**只拿原始证据锚点指向的材料**，用自己的话重写该条目（来源盲写）；
   - 校验 = 结构一致性检查：两个 agent 对「该规则的适用条件 / 边界 / 例外」各答固定问卷（适用范围？何时失效？证据在哪？），逐项比对——这是「k=2 一致才 confirmed」协议的特例，证据锚点重合检查（一致但锚点同源 → 强制升级）原样适用；
   - 2/2 一致且锚点可机验 → 通过；分歧 → 升级人工并留痕；
   - 复述的产物（问卷答案对）写入条目 `verified_by` 字段并留档，让「怎么通过检验的」本身可审计；复述检验挂在「规则抽取」门禁上，新条目与重大修订都触发。
4. **注入上下文包复用两层 schema**：生效条目按「一句话结论 + 条目 id + 证据锚点」进入**层 1 前置高信号层**（计入 token 预算，条数设硬上限，如 ≤8 条）；候选/临时条目只进**层 2 定位符层**（由检索工具即时拉取，命中率进事件流（`events.jsonl`））。投票与探索 agent 一律经工具检索、不预载全库。

## 理由（第一性原理推导）

1. **SSOT 只能有一个，且它必须人可读**。SSOT 已是共识快照文件夹；知识库若另存数据库，立刻产生双写与漂移问题。业界同期也独立收敛到同一结论（agent 维护的纯 Markdown wiki 取代 RAG 流水线；把 Markdown 文件夹变成 agent 可读的开放标准）——「文件为源、索引为派生」已是事实标准方向。
2. **检索需求的主体是「过滤 + 精确召回」，不是「语义泛化」**。agent 查知识库的典型意图是「这个接口的约定是什么」「上次类似的坑怎么踩的」——意图明确、关键词明确，词法检索 + 状态/置信度过滤即可高质量满足。语义召回要解决的「我说不清但你知道我要什么」场景在本项目占比低（coordinator 负责把需求解析成结构化事件，查询本身是结构化的）。
3. **审计性优先于召回率**。知识条目注入上下文即获得权威，因此「为什么注入这条」必须可解释——词法检索的分数与命中词高亮是确定性的、可向人展示的；向量相似度不是。LLM 错误高度相关，知识库腐化会被 agent 间放大（锚点趋同），审计性不是洁癖而是防线。
4. **写入路径决定索引可行性**。通用 RAG 的索引保鲜难，是因为文档从任意入口变更；本方案条目**只经门禁写入**（门禁钩子内同步更新索引），索引新鲜度从「工程难题」降为「一条钩子」。这是把架构约束换成工程简单性的典型交换。
5. **嵌入成本与规模不匹配**：千级条目 + 自带 embedding 流水线，基建成本超过它解决的痛点；而固定建设成本才是真成本（token 成本是噪声级）。
6. **从「复述检验为什么能落地」反推**：复述检验的本质是「检验这条知识是否被独立理解」，而这正是 k=2 异构盲评投票要回答的问题。把它实现为投票协议的特例 + 门禁校验器，避免引入新机制，也自动继承了盲评隔离、锚点独立度检查、少数派留痕等全部已有保障。
7. **从「候选 → 生效必须有门槛」反推**：知识条目一旦生效就会被注入、被引用、被当作事实使用；若无门槛，错误条目会以「被引用次数」自我强化。三个晋升条件分别对应「可被独立理解」「有可机验证据」「有人背书」，缺一不可。

## 被否方案的否决理由（逐一）

- **纯向量库作为底座**：否。违背 SSOT 唯一性；审计性不可解释；agent 高频写入下的保鲜成本高；错误条目语义聚集会放大腐化，与「防错误信息获得权威」的机制防线直接冲突。保留为后续可插拔增强，不进 v1。
- **图数据库**：否。对百级–千级条目是过度工程；其核心价值（条目关系）用 frontmatter 链接字段即可表达，由确定性脚本在重建索引时解析成内存图，无需持久化图库。
- **纯 Markdown 无索引（备选 1 单独使用）**：否（作为唯一方案）。grep 无排序与过滤，弱模型任务上自主导航成本高，且「只检索生效条目」无法廉价保证——索引层的缺失会让生命周期机制形同虚设。
- **把知识塞进全局 session / 账本**：否。作用域混淆会导致 session 无限膨胀，违反上下文窗口是稀缺资源的实证结论；实体关系上两者应分离并以锚点互链。
- **「双人真审」作为生效门槛**：否。人工介入负担是平台隐性死法；「双人确认」的技术意图是「两个独立视角」，异构 agent + 人的组合能达到同等独立性而成本低一个数量级。
- **「复述检验用同族 agent」**：否。抽取与复述同源时，同源错误无法被发现，复述会变成「用自己的话重复自己的话」；必须与抽取 agent 异构。
- **「候选条目也进前置高信号层」**：否。未验证条目进高信号层即等于获得权威，会直接造成上下文腐化；候选条目只允许经定位符层按需拉取。

## 关键实现注意点

1. **frontmatter schema 要版本化**。字段清单与取值以 [docs/08-self-evolution.md §8.2.2](../08-self-evolution.md) 为权威：`schema_version / id / type(rule|term|pitfall|convention) / title / status(candidate|active|deprecated|retired) / confidence / tags / source_anchors[{kind, anchor}] / verified_by / supersedes / contradicts / applies_to / created / last_reviewed / review_due`；锚点字段统一为 `{kind, anchor}`，行号只作显示层、不写入 `source_anchors`。schema 变更走 ADR，解析器容忍缺省值。
2. **条目 ID 是锚点，必须稳定**。`KB-xxxx` 一旦发放终身不改；文件名可含标题但解析以 ID 为准（防重命名断链）；被推翻条目**保留全文**（软删除 = `status: retired` + 检索默认排除 + 注入永不允许）。
3. **中文分词**：FTS5 默认分词器不切中文，起步用 `trigram`（需确认 SQLite 3.34+）并验证跨平台编译选项；若召回不满意再换外挂分词——属于索引层内部替换，不动文件层。这正是「文件为源」架构的容错红利。
4. **索引即缓存**：全量重建必须是一条秒级命令且进 CI（防索引与文件漂移后静默劣化）；写入只走门禁钩子，**不存在第二条写路径**。
5. **候选 → 生效的三个条件必须都能机验**（复述检验通过 / 锚点机验有效 / 人工确认事件存在），否则晋升逻辑会退化为人工流程。
6. **推翻率高的条目自动降置信度、强制投票**：检索时 `confidence` 参与排序加权，**不硬过滤**（防「查不到旧结论」导致重复踩坑）。
7. **复述问卷的字段固定**：适用范围 / 何时失效 / 证据在哪——三项都必须可对照。问卷答案对写入 `verified_by` 并留档。
8. **注入层的硬上限与预算**：层 1 条数设硬上限（如 ≤8 条）并计入上下文包 token 预算；层 2 的检索命中率进事件流（`events.jsonl`），用于判断「知识库是否真的被用上」（自进化闭环的观测项之一）。
9. **规模护栏**：条目数过约 5k 或 trigram 召回质量实测不足时，再评估 embedding 增强（同库加向量列 + 混合排序）；升级只动索引层，frontmatter schema 与文件布局不变。
10. **版本兼容**：SQLite 文件格式跨版本稳定，但 FTS5 索引内容不可依赖跨大版本直接迁移——v1 就把全量重建做成独立命令，任何迁移路径都是「删库重建」而不是「转换索引」。
11. **自进化闭环的观测口径**：Issue 密度随需求序号衰减是飞轮生效的直接证据；新条目「下次被检索命中」的比例是规则抽取的质量指标；过期条目被引用次数趋零是知识保鲜的有效性指标。三者都要能被仪表盘采集。
