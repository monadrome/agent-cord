# ADR-0016 ｜ 分发与插件机制：npm CLI + 三层插件 + IPC 装载

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0009（语言与运行形态）、ADR-0011（运行时与权限白名单）、ADR-0014（gate 与 checker 注册表）、ADR-0008（官方插件集与示例实现）
- 补充：ADR-0019（IPC 插件协议落定：MCP over stdio，2026-09-24 拍板）
- 来源：本方案技术选型调研（2026-09，内部调研纪要）——分发与插件机制

## 背景

结合已定型的约束，本决策点收窄为四个子决策：

1. **分发形态**：平台本身以什么形态发布（npm CLI / pip / 单二进制），目标用户是开发者团队、要进 CI；
2. **扩展分层**：「新增 agent/gate 零代码 = 纯配置」与「新增校验器/适配器 = 写插件」的边界在哪——即「配置即插件」到底能覆盖什么、什么必须写代码；
3. **装载机制**：代码型插件用什么方式装载——进程内动态加载 / 编译期注册 / 外部进程 IPC；
4. **生态冷启动**：开源初期如何让第三方能扩展——模板市场 / 官方插件集 / 纯文档约定。

关键约束：平台通过驱动现成 AI CLI（headless）执行、不绑定厂商；核心是编排 + 文件读写 + IM 适配 + 门禁校验，计算负载在子进程而非本体；安全边界要求「agent 只产 Draft、合入永远人工」，而插件天然是跑凭证与网络的高危面。

## 备选方案

本决策点有四个相对独立的维度（分发形态 / 装载机制 / 生态形态，以及扩展分层——扩展分层的边界在「决策」一节直接给出），分别列出备选（每个：是什么 / 优点 / 缺点）。

### 一、分发形态

#### 备选 A：npm（Node/TypeScript）CLI 分发

- **是什么**：平台本体是 TypeScript 编写的 Node CLI，以 npm 包发布，`npx` 免安装可跑；非 Node 系的 AI CLI 用子进程驱动（headless 本来就是进程间调用）。
- **优点**：① 主流 AI CLI 的事实分发标准（Claude Code、Codex CLI、Gemini CLI 均走 npm），目标用户与 CI 镜像几乎必有 Node；② `npx` 零安装即跑，dogfooding 与 CI 集成摩擦最小；③ IM/平台 SDK 生态最强（Slack Bolt、discord.js、飞书官方 Node SDK）；④ 与配置型插件（YAML/JSON/markdown）同构，无跨语言序列化成本；⑤ Node 自身可打单文件 bundle 作为补充通道。
- **缺点**：运行时依赖用户侧 Node 版本（`engines` 字段可约束但管不住裸机）；启动/内存开销大于单二进制；供应链安全面（传递依赖）大于单二进制。
- **契合度**：高。平台本体是 I/O 密集编排器，不是 CPU 密集服务；SDK 生态与目标用户环境完全对齐。

#### 备选 B：Go/Rust 单二进制分发

- **是什么**：本体编译为单个静态二进制，GitHub Releases + Homebrew + Docker 分发。
- **优点**：零运行时依赖，运维/CI 最省心；spawn 子进程、长连接的稳定性与资源占用更好；单文件审计供应链容易。
- **缺点**：生态错位（AI CLI 生态在 Node，IM SDK 的插件作者生态弱）；**插件机制与单二进制根本冲突**——Go 官方 plugin 仅支持部分平台且有符号版本一致性陷阱，社区正在从动态链接插件迁向 IPC；开发迭代速度对早期节奏不划算。
- **契合度**：中。运维形态最优，但与「插件生态冷启动」目标相斥——插件作者没动力为一个新平台学新语言或直接写二进制协议。

#### 备选 C：pip（Python）分发

- **是什么**：Python 包 + 免安装运行器；把其他语言的 CLI 打成 wheel 已是成熟做法。
- **优点**：免安装体验可比 npm；数据/ML 团队渗透率高。
- **缺点**：AI 编排工具的主用户是前端/平台工程师，pip 环境碎片化（venv/conda/系统 Python）比 Node 严重；与被驱动 CLI 的宿主语言无协同；把 CLI 发到 PyPI 的工程复杂度（平台矩阵）高于直接发 JS。
- **契合度**：低–中。可作为远期「补一条分发通道」，不宜作主通道。

### 二、装载机制

#### 备选 D：进程内动态加载

- **是什么**：插件编译成宿主同语言的动态库/模块，运行时加载。
- **优点**：调用开销最低、可共享内存、理论可热更新。
- **缺点**：**反模式已被多社区证伪**——某语言的 plugin 仅支持特定平台 + 编译符号必须严格一致（宿主升级即插件全坏）；另一语言动态加载要自管 ABI；JS 动态导入虽可行，但一旦插件跑在宿主进程内，一次插件崩溃即平台崩溃，且插件直接持有 session 写权限，与权限分级冲突。
- **契合度**：低。对本项目（安全敏感、凭证面大、版本演进快）是最差选项。

#### 备选 E：编译期注册（全部内置）

- **是什么**：所有校验器/适配器作为官方代码编进主包，用户只配置开关。
- **优点**：版本一致性、质量可控、测试矩阵最小。
- **缺点**：与「开源基座、第三方可扩展」的定位直接矛盾；IM 适配器与内部 CI 适配器的对接需求是长尾的，全内置意味着官方成为瓶颈（同类平台早期即因动态加载能力缺失被诟病）。
- **契合度**：低，但**适合作为「官方插件集」的构建方式**。

#### 备选 F：外部进程 IPC 插件

- **是什么**：插件是独立可执行文件（任何语言），宿主通过 stdio/socket 与其交换 JSON 消息。已有成熟先例：主流 CLI 的 hooks（stdin 收 JSON、stdout 回 JSON 即可阻断/注入）与 MCP server；某服务端项目正把其插件架构整体迁向 socket IPC。
- **优点**：① 语言无关——插件作者用 Python/Go/Node 写校验器都行，CI 团队可把现有校验脚本直接包一层；② 崩溃隔离、超时隔离（门禁校验必须可设超时）；③ 权限天然最小化：子进程只拿到宿主显式注入的 stdin JSON 与环境变量，不共享 session 内存，与「agent 只产 Draft、凭证禁生产」的安全边界严丝合缝；④ 版本解耦——插件按协议版本声明兼容，宿主升级不炸插件；⑤ 协议可测试：fixtures JSON 进、JSON 出，回放测试可直接复用同一机制。
- **缺点**：序列化/进程管理开销（对门禁级毫秒–秒级校验可忽略）；协议设计成本前置（事件 schema、错误码、超时语义必须在 v1 冻结）；比进程内难调试（需协议日志）。
- **契合度**：高。与「驱动外部 CLI」的既有哲学同构——平台本来就靠 spawn 子进程驱动 AI CLI，插件只是同一模式的延伸。

### 三、生态形态

#### 备选 G1：模板市场（marketplace 清单仓库）

- **是什么**：marketplace = 含清单文件的 git 仓库，一条命令即注册；GitHub 就是注册中心，不需要自建注册中心。
- **优点**：冷启动成本极低；已是 AI CLI 插件分发的收敛形态，并有实证研究分析其共演。
- **缺点**：清单生态存在供应链投毒风险（已有安全分析指出）；对「新平台无用户」的冷启动问题本身无解。

#### 备选 G2：官方插件集

- **是什么**：官方仓库内置并随版本测试的一组插件（IM 三适配 + git 校验 + 主流 CI 校验），保证「开箱可用、质量背书」。
- **优点**：解决「新平台没有供给」的根本问题；官方先当最大的插件作者，用户第一天上手就有能力可用。
- **缺点**：官方维护成本；需刻意避免官方插件形成事实上的一等公民。

#### 备选 G3：纯约定（只定接口，插件全靠自发）

- **优点**：零官方成本。
- **缺点**：对新平台冷启动太陡，已被同类平台的早期实践证伪。

## 决策

**npm CLI 分发（TypeScript 本体）+ 三层插件体系（纯配置层 / 声明式 markdown 层 / IPC 进程插件层）+ 外部进程 IPC 装载 + 「官方插件集内置 + GitHub 模板市场」冷启动。**

1. **分发**：npm 全局安装 + `npx` 零安装路径 + Docker 镜像两条 CI 通道；`.nvmrc`/`engines.node` 声明版本并在 CLI 启动时自检；lockfile 提交；避免 `postinstall` 脚本（CI 安全扫描常拦截）；单二进制（`bun compile` 类）留作远期可选通道，不互斥。
2. **三层插件**：
   - **层 1 纯配置组合**：agent 定义、gate 定义（组合已注册的能力，零代码）；
   - **层 2 声明式 markdown**：角色提示词、评审问卷、工件模板等知识型扩展（不改代码就能调整 agent 行为）；
   - **层 3 IPC 进程插件**：新的校验器与适配器（新种类能力）。
3. **协议 v1 冻结**：IPC 插件只承诺三种消息——`check`（入：产物描述 + 锚点；出：`{result: pass|block|warn, anchors, reason, confidence}`）、`capabilities`（能力清单，供配置引用）、`health`。事件推送类（IM 适配器的长连接）单独定 `stream` 语义，不与门禁校验复用同一超时口径。握手先交换 `protocolVersion`。
4. **能力清单是配置与插件之间的唯一接缝**：配置层只写 `validator: <能力名>@<插件>` + 参数；宿主按清单在**加载期**校验引用是否存在、参数 schema 是否匹配，加载期报错而非运行期炸。
5. **超时与三态对齐**：插件子进程强制超时（默认如 60s，gate 配置可覆盖），超时按「升级人工」处理而非放行。
6. **凭证**：走环境变量/短时效 token，禁 stdin 明文长期密钥；插件进程按 gate 声明的最小权限集启动，同一插件在不同 gate 下拿到不同凭证。
7. **官方插件集也走同一 IPC 协议**，不允许官方插件开后门走进程内 API——保证协议不自欺，第三方与官方能力对齐。
8. **marketplace 清单只做发现不做执行**：清单只登记「插件名 + git 源 + 版本 + 能力摘要」；安装仍需用户显式 add 并锁定 commit/tag，防供应链投毒。
9. **dogfooding 即冷启动第一步**：平台管理自身开发所需的全部校验器与适配器就是官方插件集 v1，且必须全部以第三方插件同等接口实现（与 ADR-0008 衔接）。

## 理由（第一性原理推导）

1. **从「平台是什么」出发**：本平台的计算全部外置——生成/评审在 AI CLI 子进程，校验在外部工具链，本体只做事件路由、快照文件夹读写、IM 收发。这类 I/O 编排器的最佳宿主语言不是性能问题而是**生态对齐问题**：SDK（飞书/Slack/Discord）、目标用户环境（AI CLI 用户 = Node 用户）、CI 镜像全在 Node 侧。npm 是唯一让「安装平台」和「安装它要驱动的 AI CLI」同构的选项。
2. **从「插件要解决什么」出发**：本项目插件的真实需求只有两类——① 新的**校验信号源**（问某个外部系统「这个产物过没过」，返回布尔 + 证据锚点）；② 新的**适配器**（IM 平台、需求单系统）。两者都是「与外部世界对话」的薄壳，不是需要共享宿主内存的算法。共享内存无收益，进程隔离全是收益（崩溃隔离、凭证隔离、超时可控），所以 IPC 胜出不是因为它流行，而是因为需求面里**没有一项需要进程内**。
3. **从安全边界出发**：「凭证策略（禁生产凭证 + 短时效 token + setup 期注入）+ agent 权限分级」要求插件不能天然坐在 session 写权限上。进程内插件会让第三方代码直接获得这个位置；IPC 插件拿到什么完全由宿主协议决定，最小权限是结构保证而非约定。
4. **从「零代码新增 agent/gate」出发**：agent/gate 的定义（角色、知识源、门禁 = 角色 × 校验 × 放行）本质是**数据不是代码**——校验引用的是已注册校验器的名字 + 参数。所以配置层必须能引用 IPC 插件声明的能力清单，形成「配置组合、插件供能」的清晰边界：**配置只能组合已有能力，插件才能提供新能力**。
5. **从冷启动出发**：新平台没有第三方时，市场没有供给；没有供给就没有用户——破法只有官方先当最大的插件作者（内置三 IM 适配 + git/CI 校验），同时把 marketplace 仓库模板开源，让第一个外部贡献者只需 fork 模板加条目，而不是读懂 SDK。
6. **从「防退化」出发**：与「命令必须降级为门禁触发入口」同源——**插件入口必须挂在校验器/适配器两类能力上，不允许插件注册自由命令**，否则插件机制会把平台拖回「脚本集合」。

## 被否方案的否决理由（逐一）

- **Go/Rust 单二进制为主分发**：不是运维不优，而是它把插件生态逼进死路（动态链接插件是公认的坑，已有项目公开迁移）。本体从 Node 换成 Go 的收益（启动快、部署净）对本项目这种「99% 时间在等子进程和 API」的编排器约等于零，而 SDK 与插件作者生态的损失是实打实的。保留为远期可选：日后可补一个单文件通道，两者不互斥。
- **pip 主分发**：环境碎片化成本 > 免安装便利收益；目标用户主环境在 Node。远期可作第二通道。
- **进程内动态加载**：宿主升级即插件全坏、崩溃无隔离、权限面失控——三条全踩本项目约束。
- **全量编译期注册**：官方成为长尾适配的瓶颈，违背开源基座定位；仅保留给「官方插件集」这一子集。
- **独立命令/脚本式扩展**：与门禁的防退化结论一致——否掉「命令集合」退化路径，不允许插件注册自由命令。
- **纯约定生态（只定接口）**：对新平台冷启动太陡，已被同类平台的早期实践证伪。
- **「marketplace 清单直接触发安装与执行」**：否决于供应链风险。清单只做发现，安装必须显式确认并锁定版本；这是把便利性让位给可审计性。

## 关键实现注意点

1. **协议 v1 即冻结 + 版本协商**：握手交换 `protocolVersion`；v1 仅承诺 `check` / `capabilities` / `health` 三类消息；破坏性变更走 v2 并保留 N-1 兼容一个周期。
2. **超时与门禁三态对齐**：门禁结果三态 = `pass` / `block` / `warn-and-continue`（升级是 `on_fail: escalate` 的后续动作，不是第四种结果）+ 超时策略；插件子进程必须强制超时，超时按「升级人工」处理。
3. **能力清单是唯一接缝**：宿主在加载期完成存在性与参数 schema 校验；配置中出现未注册能力即拒绝加载（fail-fast），不允许运行期才发现。
4. **凭证注入走环境/短时效 token，禁 stdin 明文长期密钥**；插件进程按 gate 声明的最小权限集起进程，同一插件在不同 gate 下获得不同凭证。
5. **官方插件集走同一协议**：不允许官方插件使用进程内私有 API；可用 CI 检查「官方插件是否只依赖公开协议」来强制这条约束。
6. **marketplace 只做发现不做执行**：登记「插件名 + git 源 + 版本 + 能力摘要」；安装需显式 add 并锁定 commit/tag。
7. **npm 分发的坑**：声明 `engines.node` 并在 CLI 启动时自检；提交 lockfile；避免 `postinstall` 脚本；提供 `npx` 与 Docker 两条 CI 通道。
8. **声明式 markdown 层的边界要写清楚**：只允许扩展提示词、问卷、模板等知识型内容，不允许承载可执行逻辑（否则会变成第二种代码即配置）。
9. **协议可测试性**：插件以 fixtures JSON 进、JSON 出即可测试；回放实验复用同一机制，插件测试不需要真实 IM/CI 环境。
10. **多进程资源约束**：门禁与插件会同时起多个子进程，需在驱动层设令牌桶与并发上限（与 ADR-0011 的并发控制统一），避免与 AI CLI 子进程争抢资源。
11. **插件目录与快照文件夹的关系**：插件是平台侧资产（随平台安装），不进需求快照文件夹；需求文件夹只放该需求的数据与证据，避免把「工具」与「事实」混在同一 SSOT 中。
