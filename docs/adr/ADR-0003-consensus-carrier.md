# ADR-0003 ｜ 共识载体是结构化快照与事件流，不是群聊

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0005（共识账本形态）、ADR-0010（SSOT 存储与版本化，本 ADR 的物理实现）、ADR-0012（事件与通信）、ADR-0004（单机器人路由）
- 来源：方案提案 §0 已形成共识第 3/4 条、§4.1 上下文贯通、§5 三层架构；2026-09-24 晚项目协作群关于 SSOT 维护与共识快照的讨论结论

## 背景

方案提出了三层架构：交互捕获层（协作群 = 人机同席的圆桌）→ 翻译层（单机器人路由）→ 结构化状态层。三层里哪一层是事实来源，是这个项目最容易做错、也最贵的一个决定。

协作群确实是**最自然的入口**：人与各角色 agent 同席，文档、想法、调研都发进群，每条消息都是潜在的事件源；自定义 slash command 本身就是现成的命令协议。于是存在一个诱人的简化——「群里有全部信息，群记录就是 SSOT」。

但从协作群的日常工作过程中暴露了三个直接反证：

1. **需求变更散落在私聊和群聊里，极易遗漏**（痛点 P4 就是这个现状）。把群聊当档案，等于把现状制度化。
2. **开发过程实际是「边进行、边迭代」的，需求澄清的难点恰在于此**。群聊里同一话题的结论会被后续消息反复覆盖，没有哪一条消息是权威的。
3. **上下文是隐性的**：实际工作中团队没有标准，纯依赖体感；agent 只看最新的上下文和需求文档。多条消息叠加后，人和 agent 对「当前结论是什么」的理解会持续漂移。

由此在协作群讨论中收敛出几条明确的做法：必须**主动维护一份共识快照**——一个需求一份文件夹，主动清理原来的历史信息，内容包含 prd、adr、plan、findings 等；**为了避免隐性上下文的问题，文档必须支持版本**；工作流是一个预定义的有向图，节点出口要有里程碑文档；并且**需要一个只持有最新快照上下文的协调 agent**，以避免幻觉。

这里存在一个必须在设计阶段就化解的表面矛盾：**共识快照要求「主动清理历史」，而全局 session 的领域模型要求事件溯源（保留全部历史）**。两者是相反的物理形态。

## 备选方案

### 方案 A：群聊即档案（群记录就是 SSOT）

- **是什么**：不另设状态层，群消息本身就是事实来源；需要时把群记录作为上下文喂给 agent。
- **优点**：零额外机制；人不需要改变行为（发消息即记录）；对「只想知道发生了什么」的旁观者最友好。
- **缺点**：非结构化、易失（平台侧保留策略不可控）、有噪声（闲聊与结论混在一起）；无版本、无状态机、无法表达「这条结论已被推翻」；agent 消费全量群记录会把上下文窗口打满且引入噪声；更根本的是——它延续了 P4 的现状。
- **不可机判**：投票记录、锚点重合检查、推翻状态机、门禁放行判定都需要程序查询「谁、何时、对哪条、投了什么」。群消息做不到。

### 方案 B：单一权威文档（所有结论写进一份持续更新的文档）

- **是什么**：一份需求文档持续维护为最新视图，历史靠文档自身的历史版本（如文档平台版本功能）保存。
- **优点**：对人和 agent 都直观；版本由文档平台提供；单一入口。
- **缺点**：文档级更新粒度太粗——改一行触发全文评审，制造流程税；无法表达条目级状态机（某条结论被推翻而其余不受影响）；机判层缺失，与方案 A 同病。
- **粒度问题**：防腐机制要按证据锚点切分文档成块（块级粒度），单一文档在结构上不提供这个切分。

### 方案 C：结构化快照 + 事件流（分层承载）

- **是什么**：共识快照文件夹是全局 session 的物化形态——`cord/<req-id>/` 内含快照文档（prd.md / adr.md / plan.md / findings.md，即最新层，允许人工编辑与主动清理）+ 共识账本（`ledger.yaml`，机判层）+ 事件流（`events.jsonl`，append-only，历史层，永不清理）+ git（版本化权威）。群聊降为交互捕获层，其输入经翻译层解析为结构化事件。
- **优点**：
  - 与事件溯源的经典分层吻合：**事件流 = 只增不改的历史层；快照文档 = 主动维护的最新层**。两者冲突只发生在「同一层既当历史又当现状」时，分层即化解。
  - 主动清理历史没有心理负担——历史永远在事件流与 git 里；反过来，审计与回放有唯一可信来源。
  - 机判逻辑（投票、锚点求交、状态机、门禁）有结构化载体，且载体是可 diff、可 PR 评审的文本。
  - 协调 agent 的「只看最新快照」在机制上可实现：注入层剪裁为主、文件层只读副本为纵深、写操作必经路由为兜底。
- **缺点**：比纯编辑文档多一点协议（需要定义事件 schema 与投影规则）；append-only 事件流在 git 分支合并时有内容冲突，需要 merge driver（见 ADR-0010）；团队需要理解「显示层 / 机判层 / 历史层」三层分工。

## 决策

**采用方案 C。共识的载体是结构化快照与事件流，群聊等沟通介质只是交互捕获层，不是事实来源。**

具体口径：

1. **SSOT = 共识快照文件夹（`cord/<req-id>/`）**，它是全局 session 的物化形态。全局 session 是逻辑概念，其锚定单位 = 单个需求。
2. **三层分工固定**：快照文档 = 最新层（允许人工编辑 + 主动清理）；`ledger.yaml` = 机判层（共识账本）；`events.jsonl` = 历史层（append-only，永不清理）；git = 版本化权威。
3. **判定一律查事件流/账本**，frontmatter 只是显示层，不参与任何判定。
4. **事件流永不进 LLM 上下文**。协调 agent 与各角色 agent 只消费投影（快照文档 + 上下文包）。
5. **协调 agent（coordinator）只持有最新快照上下文**，采用三层隔离防御：注入层剪裁（主）/ 文件层只读副本（纵深）/ 协议层写操作必经路由（兜底）。
6. **工作流是预定义的有向图**：节点 = 阶段，节点出口 = 里程碑文档，节点上挂门禁。

## 理由（第一性原理推导）

1. **从「什么必须能被机器判」反推**：本方案区别于「更好的文档工具」的地方全在机判——投票留痕、锚点独立度、推翻单向状态机、门禁三态放行。散文与群消息不承载机判。所以必须有结构化层，且结构化层要可评审（合入永远人工，载体是 diff），最便宜的可评审结构化形态就是 JSONL/YAML。这一步排除了方案 A 与 B。
2. **从「主动清理」与「事件溯源」的矛盾反推**：矛盾的根源是「同一层既当历史又当现状」。分层即可化解，且分层后的语义各自干净——快照层可以放心瘦身（它是投影，不是证据），事件层可以放心只增（它不参与日常消费）。
3. **从「协调 agent 防幻觉」反推**：协调 agent 由现成 CLI 驱动，文件系统对它是开放的，物理隔离不可靠；唯一可靠的控制点是**它启动时被注入什么**。因此主机制必须放在注入层剪裁上；文件层只读与协议层路由是纵深与兜底，不是主防线。这一条同时决定了「事件流永不进上下文」不是洁癖，而是防幻觉结构的一部分：完整历史一旦进 prompt，幻觉的直接来源就回来了。
4. **从「文档要有版本」反推**：版本必须由权威源提供。快照文档自身携带的版本字段是**给人读的**（打开文档第一眼看到「本文档 v3、confirmed 条目 12」），不可能是权威——它与 git 真实历史可能漂移。权威只能是 git 与事件流。这与证据锚点中「行号只作显示层」的原则结构同构：**显示层不参与判定**。
5. **从「人是第一个消费者」反推**：快照文档要允许人工直接编辑，规范团队自己的编辑习惯（团队已经证明他们会主动维护快照）。但所有状态机流转、投票、门禁判定只能经写路径落事件流——这样既保留人的编辑自由，又不破坏审计链。
6. **从「本群就是第一个用例」反推**：平台的第一个需求是管理自己的开发。这要求协作群里的讨论能被解析成事件、能被账本承接。也就是说，群必须是**入口**，而这恰好与「群不是事实来源」互补：入口与来源是两个角色，一个负责捕获，一个负责权威。

## 被否方案的否决理由（逐一）

- **方案 A（群聊即档案）**：否决于机判层缺失与非结构化噪声。群消息无法承载条目级状态机，无法被程序精确查询，且平台保留策略不受控——审计链随时可能断裂。它把 P4（变更散落群聊）从问题变成了设计。
- **方案 B（单一权威文档）**：否决于粒度与状态机表达。文档级更新粒度会制造流程税（改一行触发全文评审），而条目级状态流转（一条被推翻、其余不受影响）在结构上无法表达。它作为「快照文档」的子集被保留在方案 C 中（`prd.md`/`adr.md` 等就是这类文档），但不再是唯一载体。
- **「群聊作为 SSOT + 定期导出结构化摘要」**：否决于导出时点不可控、导出规则无法覆盖状态机。摘要只能描述，不能承载「谁投了什么票、锚点是否重合」这类需要精确字段的机判数据；且导出是批处理，事件之间没有单调序，无法防错位。
- **「让协调 agent 持有完整历史以防遗漏」**：否决于幻觉与上下文腐化。完整历史进 prompt 会放大噪声、增加成本，且与「只持最新快照」的防幻觉设计直接冲突；需要历史时走查询（事件流是程序与人审计的接口），不走注入。
- **「快照文件夹放在独立仓库」**：否决于 clone 即拥有 SSOT 的开源体验与评审链一致性（详见 ADR-0010 的方案 D 否决理由）。

## 关键实现注意点

1. **目录布局与三层映射必须显式写在配置文件里**（布局版本记录在 `cord.toml`），不允许靠约定俗成——agent 与人要能零培训定位：`prd.md`/`adr.md`/`plan.md`/`findings.md`（最新层）、`ledger.yaml`（机判层）、`events.jsonl`（历史层，即事件流）、`votes/`（该需求的投票与回放产物目录；`findings.md` 是快照文档、不是目录）。派生索引 `cord/.index/` 置于仓库根、gitignore、可重建，不属于快照层。
2. **写路径收敛**：所有状态变化（CLI、git hook、IM 路由、agent 工具调用）必须汇聚到单一的 `append_event` 函数。这是脱敏、时间戳规范化、投影一致性不被某个入口绕过的前提。
3. **快照文档与事件流的边界**：快照文档允许人工直接编辑（这是「主动清理」的落点）；但凡状态机流转、投票、门禁判定，只能经 `append_event` 写入事件流，再投影/同步进 `ledger.yaml`。建议提供一条确定性检查命令：把事件流 fold 得到期望状态，与 `ledger.yaml` 实际状态比对，防漂移。
4. **协调 agent 的三层防御逐条落实**：(1) 注入层——只挂载上下文包（两层 schema：前置高信号层 + 定位符层），不给快照文件夹写权限，可给 JIT 读白名单；(2) 文件层——本地运行时以只读方式提供快照文件夹（只读挂载或只读 checkout 副本），kernel 级强制、无性能开销；(3) 协议层——任何动作必须经路由机器人写入。三层是纵深关系，不是三选一。
5. **frontmatter 只放显示性字段**（id、状态、版本戳、依赖文档 id），禁止放机判字段；CI 可加一条「frontmatter 与账本状态不一致即告警」的检查——显示层漂移可以容忍，但必须可见。
6. **里程碑文档 = 节点出口产物**：文档类型用封闭枚举声明在节点定义里（ADR-0014），执行期的临时产物（计划草稿、进度）归事件流，禁止晋升为长期文档，否则快照层会重新膨胀。
7. **群聊侧的唯一职责是捕获**：翻译层把群内输入解析为结构化事件（向下）、把 session 状态以摘要/选择题推回群里（向上）。解析不确定时反问，不猜（ADR-0004）。
8. **本 ADR 不决定物理格式细节**：存储形态、事件入不入 git、合并冲突处理、frontmatter 字段级规范由 ADR-0010 决定；事件模型与 IM 适配由 ADR-0012 决定。
