# ADR-0055 ｜ 默认 Goal 驱动的自主 Draft 交付

- 状态：accepted（产品与架构基线，完整执行闭环待实现）
- 日期：2026-10-09
- 关联：ADR-0001（人工职责与 Draft-only）、ADR-0002（默认轻量与触发式升级）、ADR-0017（ACP）、ADR-0023（节点执行与唯一恢复语义）、ADR-0025（任务重试）、ADR-0030（版本化审批）、ADR-0040/0041/0045（验证事实、源码身份与证据一致性）
- 来源：用户提出“默认 Goal 模式，交付自测后的代码与 human review 指南，happy path 无中途人工干预”；现有实现核对与 agent-optimizer 设计评价；[核心 feature](../core-features.md)

## 背景

现有 ACP/headless driver 按任务运行，coordinator 将任务成功和 artifact 写回作为节点执行结果；`run.retry` 对任务失败重试。默认离线 SDLC 不挂 agent 执行体，独立 Context Session Agent 只生成一次 Draft 提议，推进需人工采用。以上机制尚不保证自主交付通过自测的代码及 review 指南。

如果每次 agent 回复结束、测试失败或节点切换都需要人继续指挥，人会成为执行循环的调度器，与 ADR-0001 消除不必要介入、ADR-0002 默认轻量的方向相冲突。

## 备选方案

1. 保持单次任务为默认，交付整理与后续修复由人逐步驱动。
2. 在 ACP driver 内部续发 prompt，直到 agent 自称完成，依赖各 CLI 自有模式。
3. 宿主定义 Goal 生命周期与交付契约，ACP/headless 提供执行能力，在现有 workflow/NodeRunner 生命周期内完成验证、修复与完成审计。

## 决策

采用方案 3。**真实 agent 开发流程默认围绕交付目标自主执行，交付代码 Draft、当前版本的实际自测证据和 human review 指南。happy path 从启动到交付就绪不需要中途人工干预。**

明确以下规则：

- 目标的验收条件、输入身份、权限、验证要求、资源边界与交付产物必须可识别；已有约定从 PRD/仓库规范/SDLC 派生。
- ACP 是通信协议；默认 Goal 是宿主执行语义，统一覆盖 ACP、headless 和自定义 agent，不依赖供应商原生模式名称。
- driver 回合结束、退出码 0 与 `agent.task.completed=ok` 均不是目标完成证明。宿主必须核验当前代码、实际验证结果和完整交付包；未知或过期证据 fail-closed。
- 可修复的测试失败、缺交付项和常规执行错误，在预算与权限内自动反馈、修复和再验证；不得删除必需检查或降低目标来制造成功。
- 缺必要事实/授权、不可恢复的外部依赖、持续无进展和预算耗尽才升级人工。问题携带实际证据、已尝试措施及最小所需决定；等待不视为授权。
- 最终 review、合入、发布、契约冻结和关键 gate 继续人工完成。交付就绪与人审通过分离，人审绑定具体版本。用户可取消或纠偏。
- 事件流仍是唯一执行事实来源。目标跨会话持续，恢复使用最新输入与 checkpoint；不引入第二套推进状态机，不伪造或回滚退出事实。

本 ADR 补充 ADR-0001/0002 的执行默认与验收口径，保留其人工最终控制边界。ADR-0023 的零外部依赖默认流程保留；接入真实 agent 后，Goal 成为开发流程的设计默认。本次仅采纳设计，不改运行时配置或现有审批语义。

## 理由（第一性原理推导）

1. 用户需要的是可审查结果，执行单位应覆盖实现、验证与修复，单次回复不是交付单位。
2. 机器可恢复错误已有客观信号，把每次恢复交给人会重复制造交互成本；人应只在事实、权限和不可机判决策边界出现。
3. 各 agent 的退出语义不同，完成条件必须由平台统一审计；ACP/headless 都只是承载执行的渠道。
4. 自动测试可提供外部行为信号，但模型可能自述错误、使用旧代码或漏测；实际执行、输入身份与产物完整性共同约束完成判定。
5. 自主执行降低中途负担，版本绑定的最终 review 保留责任边界；review 指南把人工注意力集中到变化、证据和风险。

## 被否方案的否决理由（逐一）

- 方案 1：人持续承担执行调度与失败恢复，无法满足正常路径零中途干预的交付目标。
- 方案 2：把业务完成语义绑定到通信层与模型自述；无法统一审计、预算和恢复，容易把一次调用成功误判成目标达成。
- 无限续跑或自动扩预算：资源无上限，无法解释持续无进展；预算耗尽必须保留部分产物并停止新增尝试。
- 自动跳过人工 gate 或自动合入：违反 Draft-only 与人工最终控制；零中途干预只适用于明确授权的执行范围。

## 关键实现注意点

1. 完成交付包的产物协议、目标级事件/端口与预算契约后续先写 ADR，再改 `schema.ts`/`ports.ts`；本次不定义已可使用的新 YAML 字段、事件或 API。
2. 修复循环应位于尚未退出的目标执行范围内，或以明确的新执行版本重新核验；不能向既有 DAG 偷加回边、重新解释历史退出事实。
3. 验证命令、退出状态、日志定位与输入身份由宿主采集。已有验证 REST 记录和模型报告不自动获得可信执行证明；实现需说明隔离、命令授权和证据完整性范围。
4. 目标资源边界独立于单次 driver timeout 和 `run.retry`。无进展应结合失败集合、验收推进与产物变化判断，阈值声明并通过真实样本校准。
5. ACP permission 请求使用宿主已有授权策略，超范围/未知请求拒绝或升级；不能以 Goal 默认为由全量批准权限。
6. 恢复重检需求、工作流、agent 配置、源码/依赖与产物身份；旧测试和旧 review 不能批准新代码，未知副作用先对账。
7. 验收覆盖正常交付、自动修复、提前停机、缺/伪造证据、版本变化、预算/无进展、权限/外部阻塞及冷恢复；最终 review 单列统计。

## 证据来源

1. 用户本轮明确的产品原则与交付期望（2026-10-09）；“大多数是 happy path”作为待实际样本验证的假设。
2. `src/driver/acp.ts`：一次 `session/prompt` 返回后产出 result 并结束子进程；stop reason 是通信回执。
3. `src/coordinator/coordinator.ts`：`runNode` 按 `run.retry` 重试失败任务，成功后返回，未包含机器验证失败后的实现修复循环。
4. [当前架构](../current-architecture.md)、ADR-0001/0002/0023 与 ADR-0040/0041/0045：人工边界、唯一恢复语义及输入绑定验证的现有基础。
