# ADR-0012 ｜ 事件与通信：事件流为唯一事实，IM 用官方 SDK 薄适配器

- 状态：accepted（设计定稿，代码未实现）
- 日期：2026-09-24
- 关联：ADR-0003（共识载体与三层架构）、ADR-0004（单机器人路由）、ADR-0010（事件流入 git 与合并策略）、ADR-0011（运行时）
- 来源：本方案技术选型调研（2026-09，内部调研纪要）——事件与通信机制 + IM 适配器层

## 背景

结合已定型的设计，本决策点要回答三个收窄后的问题：

1. **SSOT 是 git 版本化的快照文件夹，事件往哪写、按什么顺序流转？** 工作分解中已定为「事件溯源存储」+「事件路由总线」，因此真正要选的是事件的**持久化载体与分发机制**（watcher / 进程内总线 / 外部消息队列 / webhook 服务）。
2. **飞书 / Slack / Discord / 纯 CLI 四种入口，如何以最小成本统一成同一事件模型？** 约束是单机器人路由、不绑定厂商、agent 只产 Draft。
3. **解析置信度与兜底怎么工程化？** 「解析不确定时反问」已有实证先例，需要落到接口与机制上，而不是停在提示词。

负载特征先明确（第一性原理的输入）：这是**单团队、单部署单元、每需求一个 session** 的人机协作工具，事件量级是「每条群消息 / 每次状态迁移一条事件」，每秒个位数；但事件是**审计与回放的唯一依据**，所以可靠性要求落在「不丢、可重放、可核对」，而不是「高吞吐」。

## 备选方案

本决策点有两个相对独立的维度（事件机制与 IM 适配器），分别列出备选（每个：是什么 / 优点 / 缺点）。

### 一、事件机制

#### 备选 A：纯文件 watcher（监听快照文件夹与事件文件）

- **是什么**：用文件系统监听库监听 SSOT 文件夹，文件变动即触发处理。
- **优点**：零依赖；与「git 天然版本化」同构；本地开发体验最好。
- **缺点**：watcher 本身**不可靠**——它是「通知」而非「事实」：事件会丢（重启窗口、缓冲溢出）、会乱序、无法回答「我错过了什么」；自己写文件的进程还要自己 watch 自己，回路怪异。它只能告诉你「可能变了」，不能作为事件源。
- **契合度**：低。适合做**检测器**，不适合做事件机制本体。

#### 备选 B：本地消息总线（进程内事件分发）

- **是什么**：单进程内 pub/sub，IM 适配器、coordinator、CLI 驱动都作为模块挂载在同一进程，经内存队列通信。
- **优点**：零运维；单二进制可交付；延迟最低；与「驱动子进程」的同进程模型匹配。
- **缺点**：**重启即失**——纯内存总线不持久化，崩溃恢复、事后审计都无从谈起；测试与调试时事件不可见。
- **契合度**：中。作为**分发层**是正确答案，作为**唯一载体**不满足事件溯源要求。

#### 备选 C：外部消息队列（NATS / Redis Streams / Kafka）

- **是什么**：独立中间件承担持久化、订阅、重放。
- **优点**：工业级持久化与重放；多机扩展；生态成熟。
- **缺点**：引入第二个有状态基础设施，部署从「一个二进制 + git 仓库」变成「二进制 + MQ + git 仓库」；对每秒个位数事件量、首要用例是 dogfooding 单团队的项目，运维成本与收益严重倒挂；事件跨系统存放也破坏「文件夹即 SSOT」的单一事实性。
- **契合度**：低。这是「流行度出发」而非「痛点出发」的典型选择。

#### 备选 D：webhook 服务（自建 HTTP 服务接收事件）

- **是什么**：平台暴露 HTTP endpoint，事件以 POST 推入。
- **优点**：天然适配 IM 平台的事件订阅形态；验签、delivery id 去重、快速 ACK + 异步处理、容忍乱序重投等最佳实践成熟。
- **缺点**：**要求公网可达地址**，本地开发/CLI 场景需内网穿透；它解决的是 ingress 而不是事件模型，进程内部通信用它反而徒增序列化开销。
- **契合度**：中。只应出现在**部署形态需要公网 ingress** 的位置，且 ingress 收到后第一步仍是写本地事件流。

**对比小结**

| 维度 | A watcher | B 进程内总线 | C 外部 MQ | D webhook 服务 |
|---|---|---|---|---|
| 持久化 / 可回放 | ✗ | ✗（除非外挂） | ✓ | ✗（依赖下游） |
| 顺序保证 | ✗ | 进程内可 | ✓ | 平台不保证（有平台明确声明不保证顺序） |
| 幂等 | 无概念 | 需自建 | ✓ | 需按 delivery id 自建 |
| 部署成本 | 零 | 零 | 高（第二个有状态组件） | 中（公网地址 / 穿透） |
| 与「文件夹即 SSOT」同构 | ✓ | ✗ | ✗ | ✗ |

### 二、IM 适配器

#### 备选 1：各 IM 官方 SDK 直连（薄适配器 + 统一归一化接口）

- **是什么**：飞书用官方 SDK、Slack 用 Bolt、Discord 用官方 JS 库，各接一个薄适配器，向上暴露统一 `NormalizedEvent`。
- **优点**：能力上限最高——三家 2025–2026 年都已收敛到「长连接优先」的接入方式，本地开发零公网依赖（飞书长连接模式官方主推、无需公网 IP；Slack Socket Mode 与 Events API 能力等价、专为无公网 ingress 场景设计；Discord Gateway 长连接收消息）。单机器人路由 + 「推回摘要/选择题」需要的是**交互卡片能力上限**（飞书卡片回调、Slack Block Kit、Discord 交互组件），这正是官方 SDK 的长项。
- **缺点**：要维护 N 个适配器，每家鉴权/重试/限流细节不同（业界复盘的结论是「不是填一个通用 Token 就全部接通」）。
- **契合度**：高。

#### 备选 2：统一 webhook 网关模式（自研归一化层）

- **是什么**：自建 HTTP 服务，各 IM 的 webhook 都打到它，归一化为内部事件。
- **优点**：单一边界做验签、去重、归一化，安全面收敛；是备选 1 的自然组成部分。
- **缺点**：单独看不完整——飞书长连接、Slack Socket Mode、Discord Gateway 都不是 webhook，「统一 webhook 网关」覆盖不了三家主推的接入方式；且仍要公网地址。
- **契合度**：中。作为备选 1 中「webhook 形态部署」的子模块存在，不独立成选。

#### 备选 3：复用成熟桥接框架（多平台机器人框架）

- **是什么**：直接嵌入现成的多平台机器人框架。
- **优点**：接入成本最低（一条容器命令覆盖 20+ IM）。
- **缺点**：对本项目是致命的——桥接框架输出的是**能力最小公分母**。以某框架官方特性矩阵实测为例：飞书**收不到非 @ 机器人的群消息**、拿不到发送者名称；Discord 无流式；Slack 一节为空。而本项目恰恰需要：解析群**全量**消息（单机器人路由的输入）、卡片回调选择题（核心交互）、以及「事件写回 SSOT」这种非对话语义——这些都不在框架的抽象里，绕开框架等于重写。另外框架自带的 LLM 对话/RAG/插件能力与本平台职责重叠且更弱，引入即包袱。
- **契合度**：低。但其**分层经验值得借用**：「统一事件对象 + 平台适配器」的两层结构，正是本项目适配器层应采用的接口形态。

**纯 CLI 模式（无 IM）如何保持同一事件模型**：把 CLI 也实现为一个适配器，实现与其他 IM 适配器**完全相同的 ingress / 归一化接口**——stdin 一行消息 → `NormalizedEvent`（actor=human，source=cli），选择题渲染为编号选项 + 输入循环。这样「同一事件模型」不是靠纪律维持，而是靠**类型系统强制**：coordinator 只认 `NormalizedEvent`，不认平台。

## 决策

**事件机制：分层归位，四者不互斥**

- **快照文件夹内 append-only JSONL 事件流（`events.jsonl`）= 唯一事实与顺序来源**（承载持久化、单调序、可回放）；
- **进程内 dispatcher = 分发层**（订阅与路由；本身不持久化）；
- **文件 watcher = 仅对账探针**（检测有人或 agent 绕过 API 直接改文档，触发 reconcile）；
- **webhook = 仅公网 ingress 前端**（部署形态需要时使用；收到即落盘）。

事件 envelope 统一为：`{event_id, seq, type, schema_version, timestamp, actor, session_id, correlation_id, payload, source}`。

**IM 适配器：薄适配器层 + 官方 SDK**（飞书长连接 / Slack Socket Mode / Discord Gateway + Interactions），自研统一 `NormalizedEvent` 归一化接口；**不依赖桥接框架运行时**（只借用其分层经验）。

**CLI 也是一个适配器**，实现同一接口。

## 理由（第一性原理推导）

1. **从痛点反推**：本项目的痛点是「共识可审计、可回放、防幻觉」，不是吞吐量；约束是「文件夹即 SSOT、单部署单元、git 版本化」。由此推出事件必须满足三条：落盘（审计/回放）、单调序（防错位——多 agent 失败模式中「错位」类的直接防御）、与 git 同构（可 diff、可 code review）。三条同时满足的载体只有「文件夹内追加的事件流」；MQ 满足前两条但破坏第三条且引入第二个有状态组件；纯 watcher 与内存总线连第一条都不满足。
2. **从「四者关系」反推**：四个备选其实问错了问题——既然事件溯源已经是既定设计，事件就该追加写入 session 文件夹内的 JSONL 事件流，它天然持久、天然有序（事件流内单调 seq）、可 diff、可 replay；在此之上，进程内总线只做**分发**，watcher 只做**对账**，webhook 只做 **ingress 前端**。这是分层归位，不是四选一。
3. **从交互需求反推**：单机器人路由的核心交互是「群消息解析 + 卡片选择题 + 回调写回 SSOT」。桥接框架提供的是最小公分母（收不到非 @ 消息就无法解析全量群输入），而官方 SDK 提供的是各家最强能力。三家 2025–2026 年都收敛到「长连接优先、本地开发零公网依赖」，官方直连的接入成本已降到可接受（飞书官方口径：接入周期从一周降到分钟级）。因此选官方 SDK。
4. **从「不绑定 IM」反推**：不绑定不是靠承诺，而是靠**接口**。把 CLI 也做成适配器、coordinator 只认 `NormalizedEvent`，使「换平台」的成本收敛在一个适配器文件内，且「同一事件模型」由类型系统强制——这同时是防「按平台写 if-else 怪兽」的正面解法。
5. **从「顺序与幂等」反推**：IM 平台不保证投递顺序，且会乱序重投。若以到达时间排序，就会产生错位类失败。因此顺序必须以**事件流内单调 seq** 为准，幂等键取平台消息 id / delivery id，消费端按 `event_id` 去重——这套组合使「至少一次投递」成为可接受的语义。
6. **从「解析错误的最小后果」反推**：路由机器人是单点，其权限已被收窄为「只读路由 + 白名单代写」。在这个前提下，解析错误的最大后果是「说错话 / 记错账」，而账本机制天然容忍并可纠正（推翻流程）。因此解析置信度的工程化应该做的是**降低错误概率并留痕**（受限分类 + 反问 + 全量入账），而不是堆无限多的兜底分支。

## 被否方案的否决理由（逐一）

| 被否方案 | 否决理由 |
|---|---|
| 纯文件 watcher 作为事件机制 | 通知 ≠ 事实：丢事件、乱序、重启不可恢复；无法满足事件溯源的审计/回放硬要求。降级为对账探针。 |
| 进程内事件分发作为唯一载体 | 重启即失，事件不可审计不可回放，与「决策落状态、可回放」的业界收敛方向相悖。降级为分发层。 |
| 外部消息队列（NATS / Redis / Kafka） | 为每秒个位数事件量引入第二个有状态基础设施，部署与运维成本倒挂；跨系统存放反而破坏「文件夹即 SSOT」的单一事实性。属流行度驱动选型。 |
| webhook 服务作为通用事件层 | 只解决 ingress 不解决持久化与顺序，且强制公网依赖；在「长连接优先」的现状下应收窄为可选部署形态的前端。 |
| 桥接框架运行时依赖 | 能力最小公分母：收不到非 @ 群消息（单机器人路由的输入直接缺失）、卡片回调与「写回 SSOT」语义不在其抽象内；自带 LLM 对话能力与平台职责重叠。借用其分层经验，不引入其运行时。 |
| 自研统一 webhook 网关独立成层 | 覆盖不了长连接三种接入方式，退化为官方 SDK 方案的子模块。 |
| 「事件流 gitignore + 定期 checkpoint 入 git」 | 与 ADR-0010 的定稿冲突并已被否决：可审计与「clone 即拥有 SSOT」是核心卖点，事件量在千行级、成本可接受。本 ADR 采用 ADR-0010 的口径——事件流随仓库入 git，用 union merge driver + 分片防丢事件。 |

## 关键实现注意点

1. **顺序保证以事件流 seq 为准，不以到达时间为准**：ingress 收到事件 → 立刻 ACK（飞书要求 3 秒内处理完成，所以必须「先 ACK、后异步」）→ 按平台消息 id 去重 → 写入事件流（`events.jsonl`）拿单调 seq → dispatcher 消费。**幂等键 = 平台 message id / delivery id**；消费端全部按 `event_id` 去重，天然支持至少一次投递。
2. **事件流与 git 的关系**：按 ADR-0010 执行——事件流入 git，配 union merge driver 与分片；派生 checkpoint 作为回放优化，不作为替代品。
3. **schema 版本化**：envelope 带 `schema_version`，`type` 用点分层命名（如 `im.message.received`、`gate.passed`、`vote.completed`）；事件即 API，改 schema 走 ADR。
4. **各平台的接入细节**：飞书卡片回调与消息事件共用一套验签，卡片回传需注册 card action 事件；Discord 若要读非命令消息需申请 Message Content Intent（slash command 不需要）；Slack Socket Mode 下部分集成方式不可用，应选其官方框架而非纯 HTTP 封装。
5. **CLI 适配器与 IM 适配器实现同一接口**：选择题统一为结构化 Choice 事件（选项 id + 超时 + 默认兜底），渲染层各自翻译（卡片 vs 编号输入）——「推回选择题不给论述题」由此获得单一实现点。
6. **解析置信度工程化**：① 意图枚举收敛为有限集合（路由目标 = 已注册角色/门禁），LLM 只做受限分类（结构化输出约束），不自由生成；② 低置信度或 top-2 概率接近时**强制走反问卡片**（列出候选理解让人点选，反问本身也是事件，留痕）；③ 全部解析决策（原文 → 结构化结果 → 置信度）作为事件入账，可回放、可被回放实验直接消费；④ 与权限收窄叠加后，解析错误的最大后果被压在「说错话 / 记错账」。
7. **多 session 并发**：每需求一文件夹一事件流，dispatcher 按 `session_id` 分区顺序消费，天然无跨需求锁；watcher 对账探针要做防抖与 hash 比对，避免「agent 自己写文件触发自己」的回路风暴。
8. **对账探针的语义边界**：watcher 发现文件被直接修改时，只触发 reconcile（比较事件流投影与实际状态并告警/补齐），**不把文件变动本身当作事件来源**——否则等于把 watcher 重新变成事件机制。
9. **ingress 前端的边界**：webhook 收到的 payload 必须先落盘再 ACK 之外的处理；验签失败与重复投递的处置要留痕（拒绝原因写入事件流），否则「为什么这条消息没进系统」无法回答。
10. **事件类型的封闭枚举**：事件类型是协议的一部分，新增类型走 ADR 评审；不允许适配器自造类型（否则不同入口的事件语义会漂移）。
