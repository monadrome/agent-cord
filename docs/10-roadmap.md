# 10 · MVP 边界与路线图

> 状态：**设计定稿、代码未实现**。本章描述的是计划与验收口径，不代表任何功能已可用。
> 术语以术语表章为准（共识快照、全局 session、门禁、校验器、盲评投票等）。

## 本章回答什么问题

本项目最终要做的东西很多，但**第一个可交付物到哪里为止**？本章回答四个问题：

1. MVP 包含哪六件事，明确不包含哪四件事，以及为什么这么切；
2. 全部工作项（W1–W4，20 项）分别归属于**开源基座**还是**内部 SDLC 示例**；
3. 四个里程碑（M1–M4）各自的时间盒与退出标准；
4. 什么情况下算"做完了"（DoD），以及为什么平台要拿自己的开发当第一个用户。

---

## 1. MVP 边界

### 1.1 做什么：W1 六件套是 MVP 核心

MVP = **开源基座的六个通用能力**可运行，并在一个真实需求上跑通一次端到端流程。这六件事共同构成"共识可被物化、可被独立复核"的最小闭环：

| 编号 | 能力 | 为什么必须在 MVP 里 | 对应的已定稿决策 |
|---|---|---|---|
| W1.1 | Agent 定义框架 | 角色 agent 是执行单元；没有注册式定义就没有"零代码新增 agent"这个验收点 | [ADR-0011](./adr/ADR-0011-agent-runtime.md)（agent 运行时） |
| W1.2 | Gate 节点定义与编排 | 门禁是"角色×时机×校验×放行"的挂载点；没有它，流程只是一串脚本 | [ADR-0014](./adr/ADR-0014-workflow-gate-dsl.md)（工作流/门禁定义） |
| W1.3 | 全局 session 存储 | 共识快照（`cord/<req-id>/`）是 SSOT 的物化形态；没有它一切结论只存在于会话里 | [ADR-0010](./adr/ADR-0010-ssot-storage.md)（SSOT 存储） |
| W1.4 | 事件路由总线 | 群消息→结构化事件→agent 的唯一通路；也是"事件流永不进 LLM 上下文"的实现处 | [ADR-0012](./adr/ADR-0012-events-im-adapters.md)（事件与 IM 适配） |
| W1.5 | 通用投票机制 | 机器参与共识的协议本体（盲评、难度门、锚点独立度、判定异构） | [ADR-0006](./adr/ADR-0006-blind-voting.md)（盲评投票）+ [ADR-0007](./adr/ADR-0007-asymmetric-model-allocation.md)（非对称分配）+ [ADR-0013](./adr/ADR-0013-vote-executor.md)（投票执行器） |
| W1.6 | 上下文剪裁 | 产出上下文包（前置高信号层 + 定位符层），决定 agent 看什么、不看什么 | [ADR-0003](./adr/ADR-0003-consensus-carrier.md)（剪裁的输入来自快照与账本，而非群聊） |

MVP 的可运行定义（对应 M2）：

- `cord` 可被一条命令拉起（常驻 daemon + 薄 CLI 客户端，见 `./adr/ADR-0009-language-runtime.md`）；
- 仓库内出现一个 `cord/<req-id>/` 文件夹，含快照文档（`prd.md`/`adr.md`/`plan.md`/`findings.md`）、`ledger.yaml`（共识账本）、`events.jsonl`（append-only 事件流），且三者随流程推进被真实写入；
- 能对一条决策点发起一次 k=2 的盲评投票，并落到判定三态之一（`confirmed` / `needs_verification` / `escalated_anchor_overlap`）；
- **新增一个 agent、新增一个 gate 均只改配置，不改代码**（DoD 第一条的前半）。

其中共识账本（`ledger.yaml`）不是额外工作项——它是 W1.3 + W1.5 的必然产物：没有账本，投票结果与证据锚点无处落盘。因此账本随 MVP 一起出现，而 W3.1 的工作是把它从"够用"做到"完整状态机 + 推翻流程"。

### 1.2 不做什么：四项明确排除

| 排除项 | 归属版本 | 为什么不在 MVP |
|---|---|---|
| 多需求编排 | MVP 之后 | 作用域已锁定"单个需求"（全局 session 的锚定单位 = 单个需求）。跨需求调度会在共识机制本身被证明有效之前，先把变量个数翻倍 |
| L3 防腐（自动更新文档） | MVP 之后（M3 起做 L1/L2） | L1（commit 关联需求 id）近乎零成本、L2（diff 与证据锚点求交）是核心价值；L3 还要多一道人审，且其收益未被验证。先做 L1/L2，用实验四校准误伤率 |
| embedding 检索 | 后置可插拔增强 | 知识库起步走符号/词法检索（可审计性优先）：能指认"这条结论为什么被检索到"，比召回率重要。embedding 作为可插拔增强，不进 MVP |
| IDE 插件 | 不进 MVP，也不在当前分发规划内 | 本体形态是常驻 daemon + 薄 CLI，IDE 集成是一条额外的分发通道，属于生态成熟后的话题 |

> 上述四条排除项都写在已定稿决策里（单需求作用域、触发式升级、知识库检索路线、运行形态），不是本章新增的边界。

### 1.3 MVP 之外仍在第一轮内的事

以下三件事不在 MVP 边界内，但属于第一轮范围（M3/M4），不要误读为"以后再说"：

- **dogfooding 闭环**：平台管理自身开发（W2.4），M3 必须跑通；
- **L2 防腐钩子**：在真实仓库上线一周并采集分布（W4.5 / 实验四）；
- **自进化一轮**：至少一轮 bad case 回流入知识库，并被后续需求实际引用（DoD 第四条）。

## 2. 工作分解（W1–W4，20 项）

归属分三类：**开源基座**（通用机制，进开源仓库）、**官方插件/示例**（与第三方同协议的实现样例）、**项目自身**（验证与度量，不进开源仓库）。

### W1 · 可扩展基础架构（开源基座）

| 编号 | 工作项 | 说明 | 归属 |
|---|---|---|---|
| W1.1 | Agent 定义框架 | 注册式：知识源/能力声明/联系人；新增 agent 零代码 | 开源基座 |
| W1.2 | Gate 节点定义与编排 | gate schema（角色×校验×放行）、触发器、依赖序；新增 gate 零代码 | 开源基座 |
| W1.3 | 全局 Session 存储 | 事件溯源、按需求生命周期、可中断恢复 | 开源基座 |
| W1.4 | 事件路由总线 | 群消息→结构化事件→agent；单机器人入口路由 | 开源基座 |
| W1.5 | 通用投票机制 | 盲评独立投票；k=2~3 初值；2/2 一致→confirmed（仅限带可机验锚点）；2:1→needs_verification + 少数派理由留痕；锚点独立度检查；难度门 | 开源基座 |
| W1.6 | 上下文剪裁 | 仓库文档→最小上下文包（相关性排序 + 格式定义） | 开源基座 |

### W2 · 内部 SDLC 打通（示例实现）

> 目标：先把本项目团队自己的 SDLC 打通作为参考示例；其他团队可参考或热插拔自己的工作流。首个用例 = 本项目协作群（共享统一上下文）。

| 编号 | 工作项 | 说明 | 归属 |
|---|---|---|---|
| W2.1 | 群机器人路由落地 | 单 bot 入口；解析群内输入为结构化事件；推回摘要/选择题 | 基座内核（翻译层）+ 官方 IM 插件（长连接适配） |
| W2.2 | 需求-会话关联 | 对接内部需求单体系（需求 id ↔ 全局 session） | 内部示例（旁路汇聚接入） |
| W2.3 | 门禁接现有工具链 | 单测/截图比对/CI/Code Review 作为放行信号源 | 官方插件集（checker）+ 内部工具链侧参数 |
| W2.4 | 自举（dogfooding） | 本平台自身的开发管理跑在本平台上 | 内部示例（同时是冷启动第一步） |

### W3 · 共识与知识

| 编号 | 工作项 | 说明 | 归属 |
|---|---|---|---|
| W3.1 | 共识账本实现 | 条目 schema + 状态机 + 推翻流程 | 开源基座 |
| W3.2 | 文档防腐钩子 | 提交前置校验；三级：关联→影响检查→自动更新 | 基座机制 + 官方 git 校验插件（L2 属核心，L3 后置） |
| W3.3 | 知识库与回流 | 归档抽取、bad case 回流、术语/踩坑沉淀 | 开源基座 |
| W3.4 | 自进化最小闭环 | Issue 密度衰减作为飞轮证据；规则自动抽取入知识库 | 基座机制 + 内部示例（密度数据采集） |

### W4 · 验证与度量

| 编号 | 工作项 | 说明 | 归属 |
|---|---|---|---|
| W4.1 | 现状计时基线 | 一周自我计时（共识/协调实际耗时）——对照组，最先启动 | 项目自身 |
| W4.2 | 实验一：共识机制回放 | 人工确认过的历史决策集盲跑投票，验证指标有效性（最高优先级实验） | 项目自身（协议见 `./12-experiments.md`） |
| W4.3 | 实验二：粒度-模型曲线 | 同一需求"强模型整体执行"vs"弱模型细粒度编排"对照 | 项目自身 |
| W4.4 | 实验三：非对称分配 A/B | 验证侧不变换生成侧，顺带采集 token 成本 | 项目自身 |
| W4.5 | 实验四：防腐钩子误伤率 | 真实仓库跑一周，统计命中-放行/拦截分布 | 项目自身 |
| W4.6 | 指标仪表盘 | 证据覆盖率 / 独立一致度 / 推翻率 / 人工介入负担 | 项目自身（基座提供指标采集接口） |

**执行顺序上的两条硬约束**：

1. **W4.1 最先启动**。它是所有"效率提升"论证的对照组，成本是一周自我计时，收益最高；不启动则后续所有对比都缺基线。
2. **实验一与平台实现解耦**。回放实验用的是外部历史决策集，不需要平台代码；因此它可以与 W1 并行推进——这也是它在"代码未实现"阶段就能先出数的原因。

## 3. 里程碑（相对时间）

时间以**方案定稿**为原点，不写死日历日期（原排期含假期窗口，仅作参考标注）。

### M1 · 方案定稿 + 基线开始（方案定稿后一周内）

| 项 | 内容 |
|---|---|
| 交付 | 方案文档集评审通过；16 条 ADR 与待拍板清单收敛到可开工状态；仓库骨架与 License 拍板 |
| 退出标准 | ① 全部 ADR 状态为 accepted；② 待拍板清单中"影响开工"的条目全部有结论（含不可逆动作清单）；③ W4.1 计时表已开始填写；④ 插件协议 v1 草案冻结（check/capabilities/health） |
| 风险 | 待拍板条目堆积会导致 M2 返工；本章 §11-risks 的待拍板清单就是给这一步用的 |

### M2 · 最小闭环可运行 Demo（方案定稿后第 2–3 周，原计划落在假期窗口）

| 项 | 内容 |
|---|---|
| 交付 | W1 六件套最小闭环：agent/gate 配置、全局 session、事件路由、通用投票 |
| 退出标准 | ① 一条命令拉起 daemon + CLI；② 新增 agent、新增 gate 各只改配置；③ 一次 k=2 盲评投票从发起到达成终态，全过程落盘；④ 投票记录含少数派理由字段与证据锚点；⑤ Demo 可脚本化复现（不是手工演示） |
| 明确不含 | 真实 IM 群、内部工具链接入、知识库自进化 |

### M3 · 自举跑通真实需求（方案定稿后约一个月）

| 项 | 内容 |
|---|---|
| 交付 | W2 自举：本项目的一个真实需求全程在本项目协作群内驱动完成 |
| 退出标准 | ① 工作流图七个节点（即工作流定义里的七个阶段：进入 → 对齐/共识 → 计划 → 执行 → 验证 → 防腐 → 上线回流，节点定义见 [06 章 §1.2](./06-gates-workflow.md)）全部走完；② 所有决策可回溯到证据锚点；③ L2 防腐钩子在自身仓库上线并开始采集命中分布（实验四起点）；④ 至少一次"统一上下文"生效的可指认证据（同一需求内变更被同步到所有相关 agent） |
| 风险 | 自举样本量小、参与者知道自己被观测（霍桑效应）。因此实验一**不得**用自举数据，必须用外部历史决策集 |

### M4 · 实验出数 + 仪表盘 + 自进化一轮（方案定稿后约六周）

| 项 | 内容 |
|---|---|
| 交付 | 实验一/二数据；指标仪表盘首版；自进化闭环演示一轮 |
| 退出标准 | ① 实验一完成（N≥100），给出证据覆盖率、独立一致度（含同构/异构/单 agent 三组对照与"一致但错率"）、人机一致度，并按阈值表逐条判绿/黄/红；② 实验二给出粒度-模型曲线（完成度/返工轮次/介入次数）；③ 仪表盘呈现四指标；④ 至少一轮 bad case 回流入知识库，且被后续需求实际引用 |

**里程碑依赖速览**：M1 → M2（W1）→ M3（W2 自举）→ M4（W4 出数）；W4.1 从 M1 起并行；实验一只依赖 E1（外部历史决策集），可与 M2 并行。

## 4. 验收标准（Definition of Done）

| # | 验收项 | 具体判据 |
|---|---|---|
| DoD-1 | **基座** | 新增一个 agent、一个 gate 均只需配置不需改代码；一个真实需求走完工作流图的七个节点（阶段）"进入 → 对齐/共识 → 计划 → 执行 → 验证 → 防腐 → 上线回流"（节点定义见 [06 章 §1.2](./06-gates-workflow.md)） |
| DoD-2 | **SDLC 示例** | 本项目自己的一个需求全程在协作群内驱动完成，所有决策可回溯到证据锚点 |
| DoD-3 | **实验** | 实验一完成，给出指标与人工结论的相关性数据 |
| DoD-4 | **自进化** | 至少一轮 bad case 回流入知识库，并被后续需求实际引用 |

两点口径说明（避免验收时争议）：

- DoD-1 的"七步"指 [06 章 §1.2](./06-gates-workflow.md) 的工作流图七个节点（阶段），是流程层面的判据，不要求每个节点都用上全部机制（例如小需求可以走默认轻量通道、不触发升级）；
- DoD-3 的"相关性"落在实验一的**人机一致度（Cohen's κ）**与**一致但错率**两个数上，具体阈值见 `./12-experiments.md`。

## 5. dogfooding 策略

### 5.1 为什么平台要先管自己

- **它是现成的环境**：本项目有一个真实协作群、一批真实需求（就是本项目自身）、一批真实决策记录。不需要为 Demo 造场景。
- **它天然验证"统一上下文"**：本项目的讨论、决策、调研本来就散落在群聊与文档里——这正是平台要解决的问题本体。
- **它是开源冷启动的第一步**：平台管理自身开发所需的全部校验器与 IM 适配器，就是官方插件集的第一版，且必须按第三方插件同等协议实现（不许官方开后门）。

### 5.2 具体形态

| 维度 | 做法 |
|---|---|
| 平台第一个需求 | "管理本平台自己的开发"——需求 id 指向本项目的一条真实工作项，其全局 session 就落在本仓库的 `cord/<req-id>/` |
| 交互捕获层 | 本项目协作群 = 圆桌；群内的决策、变更、文档链接被解析为事件写入事件流 |
| 门禁 | 本项目的方案评审、代码合入等节点用 gate schema 配置，校验器复用单测/CI/评审 |
| 度量 | 本项目自身成为"Issue 密度随需求序号衰减"的观测序列之一；L2 防腐钩子在自身仓库上线 |

### 5.3 自举的边界（防止自证）

自举能证明"机制跑得通"，**不能**证明"机制判断得准"。因此：

- 实验一使用**外部**已人工确认的历史决策集，不能使用本项目自举产生的结果（避免用平台自己的输出验证平台自己）；
- 实验二/三使用一个真实的中等规模业务需求（需求选型为待拍板项 QD-1 的组成部分）；
- 自举的产出（命中分布、Issue 密度）作为**过程证据**入仪表盘，不作为结论性证据。
