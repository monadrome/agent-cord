## 本章回答什么问题

平台每跑完一个需求，「变得更聪明」这件事具体发生在哪里？知识以什么数据结构承载、存到哪、怎么被检索到、怎么保证进来的知识是可信的、又怎么在它失效时体面退场？更重要的是——我们凭什么说它真的在变聪明，而不是在给自己收一笔看不见的税？

本章给出：自进化的定义与不变量（8.1）、知识条目实体与 frontmatter schema（8.2）、存储与检索选型落地（8.3）、生命周期与门禁复用（8.4）、复述检验协议（8.5）、四个最小机制集的闭环与指标（8.6）、知识进入上下文的方式（8.7）、飞轮证据的读数纪律（8.8）。

## 8.1 自进化：定义、原则与它要防的那件事

> **本节回答**：什么叫「平台自己变得更好」，以及为什么它必须带一条硬性的准入检验。

### 8.1.1 定义

**自进化**：平台每完成一个需求，除了产出可合入的代码，还必须产出**下一次可复用的东西**；这些东西能反过来降低后续需求的成本，并可被度量。

它有三个可观测的落点：

1. 知识条目增加、被检索命中的比例上升；
2. 同一业务线的**人工介入密度下降**（Issue 密度随需求序号衰减，见 8.8）；
3. 同类错误与同类澄清重复出现的比例下降（8.6 的 bad case 回流与介入学习）。

需求归档时，共识账本里的条目**不会**自动变成知识——账本条目是「这个需求上的结论」，知识条目是「跨需求可复用的规则」。两者的区别见下表：

| | 共识条目（ledger.yaml 内） | 知识条目（KB-xxxx） |
|---|---|---|
| 作用域 | 单个需求（全局 session 的锚定单位） | 跨需求复用 |
| 形态 | 机判层条目，随快照文件夹 git 版本化 | 每条目一个 Markdown 文件，与快照文件夹同属一个 SSOT |
| 生成方式 | 探索/实现/验证 agent 产出 + 投票/人工确认 | 由账本条目、推翻记录、Issue 记录**抽取**而来（8.6） |
| 失效方式 | 状态机单向流转，走推翻流程 | 生命周期门禁，过期/废止（8.4） |
| 交互方式 | 账本引用 KB 作为证据；KB 引用代码/用例作为证据（双向可审计） | 同左 |

**两者不合并**：把知识塞进全局 session 会让 session 无限膨胀，违反「上下文窗口是稀缺资源」这一前提；把账本条目直接当知识又会把「一次性的结论」误升为「永久规则」。两个仓库、两套生命周期、以证据锚点互链是已定型的实体关系。

### 8.1.2 它要防的那件事：上下文腐化

**上下文腐化**：错误或过期的信息被反复引用，从而在实际效果上获得了权威——引用次数变成可信度，可信度又带来更多引用。

三类典型成因：

- **来源丢失**：条目是「某人说过的判断」，但记不清是谁在什么证据上说的；
- **边界丢失**：条目本身没错，但适用条件被忘掉，被套用到不适用的场景；
- **永不过期**：结论依赖的代码/契约已经变了，条目还留在检索结果里，且检索时看不出它已经过期。

因为「检索到即注入上下文、注入即获得权威」，腐化的传播路径就是检索路径。所以防线必须建在**入库那一刻**，而不是等腐化之后治理。

### 8.1.3 三条不变量（不可让渡）

**原则：知识条目入库必须过复述检验**——能被另一个 agent 用自己的话讲清来源与边界，并检索到证据。讲不清来源与边界的知识不许获得权威。

由此导出三条不变量，后文所有机制都是它们的工程化：

| # | 不变量 | 工程形态 | 对应机制 |
|---|---|---|---|
| I1 | 知识必须有来源 | `source_anchors` 必填，无锚点不入库（与共识账本「无证据不入账」同规则） | 8.2 schema、8.4 生效条件 (b) |
| I2 | 知识必须能被独立复述 | 复述检验门禁，异构 agent 盲写 + 固定问卷比对 | 8.5 复述检验协议 |
| I3 | 知识必须会退场 | 生命周期状态机 + `review_due` + 失效信号双触发 | 8.4 过期/废止 |

## 8.2 知识条目：实体与 frontmatter schema

> **本节回答**：一条知识长什么样？哪些字段是硬门槛？删除一条知识意味着什么？

### 8.2.1 四种类型

| type | 语义 | 典型句式 | 典型来源 |
|---|---|---|---|
| `rule` | 可判定的规则/约束 | 「X 场景下必须 Y」「A 先于 B」 | 账本中的 confirmed 结论、被推翻后修正的结论 |
| `term` | 术语与领域词典 | 「『共识快照』指……」 | 需求澄清过程中反复出现的词汇歧义 |
| `pitfall` | 踩坑与失败模式 | 「做了 X 会踩到 Y」 | bad case 回流、推翻记录、线上问题归因 |
| `convention` | 约定与流程规范 | 「提交前必须 Z」「改动触碰契约需要人工确认」 | 门禁配置的稳定化、重复出现的评审意见 |

类型是**检索过滤维度**，不是层级（`pitfall` 不依附于 `rule`）。条目之间的关系用 `supersedes` / `contradicts` 表达，不引入图数据库（8.3）。

### 8.2.2 frontmatter schema

```yaml
---
schema_version: kb/v1            # 版本化；变更走 ADR，解析器容忍字段缺省
id: KB-0017                      # 终身不变，见 8.2.3
type: pitfall                    # rule | term | pitfall | convention
title: 先派发后落盘会丢事件         # 文件名可含标题，但解析一律以 id 为准
status: active                   # candidate | active | deprecated | retired
confidence: 0.8                  # 0.0-1.0；参与检索排序加权，不做硬过滤
tags: [事件流, 写路径]
source_anchors:                  # 硬门槛：至少一个，无锚点不入库；锚点字段统一 {kind, anchor}
  - {kind: symbol, anchor: "src/daemon/event-store.ts#appendEvent"}   # 结论成立处的符号锚点（活）
  - {kind: commit, anchor: "9f3c1ab"}    # 存档快照：该结论成立时的代码状态
  - {kind: kb,     anchor: "KB-0009"}    # 依赖的术语条目（「共识快照」）
  # 行号只作显示层，不写入 source_anchors（会漂移）
verified_by:                     # 复述检验留档，见 8.5
  - {role: reteller, role_of_peer: extractor, model: "<vendor>/<model>@<version>",
     session_id: "<cli session id>", result: pass, answers_hash: "<hash>", at: "<commit>#<req-id>"}
supersedes: []                   # 本条替代的旧条目（单向）
contradicts: []                  # 与本条冲突的条目 id（冲突本身是信号，见 8.6）
applies_to: [event-store]        # 适用域标签，供前置高信号层做域过滤
created: 2026-09-24
last_reviewed: 2026-09-24
review_due: 2027-03-24           # 到期触发保鲜门禁，见 8.4
---
```

字段责任表：

| 字段 | 谁写 | 何时写 | 备注 |
|---|---|---|---|
| `id` / `type` / `created` | 抽取器 | 候选条目生成时 | `id` 一经发放终身不变 |
| `source_anchors` | 抽取器 | 候选条目生成时 | 缺省即不合格，门禁直接拦下 |
| `confidence` | 平台 | 生效时给初值（默认 0.5）；推翻/引用后调整 | 只由机制调整，不允许人手工拔高 |
| `status` | 平台（门禁写入器） | 生命周期迁移时 | 唯一写路径，见 8.3.2 |
| `verified_by` | 复述检验门禁 | 每次通过检验时追加 | 追加而非覆盖，保留检验史 |
| `supersedes` / `contradicts` | 抽取器 + 保鲜门禁 | 抽取时、冲突检测时 | 由确定性脚本解析成内存图，不落图库 |
| `last_reviewed` / `review_due` | 保鲜门禁 | 每次复核、每次续期 | 到期只是触发信号，不等价于废止 |

### 8.2.3 ID 稳定终身不改

- 格式 `KB-xxxx`（四位起，用满进位），**只增不复用**：废止条目的 ID 不再分配给新条目，防止历史引用指向另一条知识。
- 文件名可以带标题（`KB-0017-dispatch-after-append.md`）方便人阅读，但**一切解析以 ID 为准**；重命名不改 ID，断链因此不可能发生。
- 其他条目引用 KB 时只用 ID（`{kind: kb, anchor: "KB-0017"}`），这与共识账本条目的证据锚点是同一套机制。

### 8.2.4 软删除：`status: retired`

知识条目不物理删除（文件一旦被删，历史引用、推翻链路、审计全部断掉）。

| 状态 | 参与检索 | 可进上下文包 | 语义 |
|---|---|---|---|
| `candidate` | 是（仅经工具 JIT 检索） | 否 | 已抽取，未通过完整生效门禁 |
| `active` | 是 | 是（只有它可进前置高信号层） | 生效，可被引用为证据 |
| `deprecated` | 需显式参数（`include_deprecated=true`） | 否 | 已过期但保留：澄清「我们曾经这么想过」 |
| `retired` | 否（默认全部排除） | 否（永不） | 已废止：被证伪或随能力/契约消失 |

**软删除 = `status: retired` + 检索默认排除 + 注入永不允许**。全文保留——被推翻的结论本身也是知识（与共识账本同一原则），它解释了「为什么现在的写法是这样」。

`confidence` 不参与硬过滤，只参与排序加权。理由：把低置信条目直接从检索里删掉，会让团队重新踩一遍已经踩过的坑；正确做法是让它在排序中靠后、并在展示时标注置信度。

## 8.3 存储与检索落地（ADR-0015）

> **本节回答**：知识存在哪、用什么检索、为什么起步不用 embedding、以后要换怎么换。

### 8.3.1 唯一 SSOT：Markdown + frontmatter，一条目一文件

知识库不是另一个系统，它是与本项目 SSOT（共识快照文件夹）**同一棵树上的第二个目录**。完整布局以 [03-architecture.md](./03-architecture.md) §5.1 为权威，此处摘录知识库相关的部分：

```text
<repo>/
  cord/
    <req-id>/                # 全局 session 的物化形态：快照文档 + ledger.yaml + events.jsonl
    knowledge/               # 知识库：每条目一个文件
      KB-0009-term-snapshot.md
      KB-0017-dispatch-after-append.md
    .index/
      kb.sqlite              # 派生索引（FTS5）；不进 git，可随时删除重建
      session.sqlite         # 后置可插拔增强：会话侧全文索引（ADR-0010）
    cord.toml                # 布局版本、事件 schema 版本、索引与工作流配置
```

选它的理由是四条约束的同向推导：SSOT 只能有一个（多一个数据库就多一次双写与漂移）；SSOT 必须人可读可改（`git diff` 就是知识变更评审）；知识条目要能被 LLM 直接读写（Markdown + frontmatter 是 LLM 最稳的读写格式）；本项目已有一套 git 版本化 + 人工合入的流程，知识库无需自建一套。

### 8.3.2 派生索引：SQLite FTS5

```text
文件（SSOT，进 git）  ──确定性生成──►  SQLite FTS5 索引（缓存，可删）
      ▲                                      │
      └────────── 唯一写入路径：门禁钩子 ◄─────┘
```

- **FTS5 负责 BM25 排序的全文检索，普通表负责 frontmatter 字段的结构化过滤**（如 `status='active' AND type='rule'`）。这两类需求恰好覆盖了「按状态/类型过滤 + 按内容排序」的生命周期检索。
- **索引是派生产物**：`kb reindex` 全量重建必须是一条**秒级命令**并进 CI；索引与文件漂移后静默劣化是这类架构唯一的死法，用「CI 里跑一次重建」直接堵掉。
- **中文分词是真实的坑**：FTS5 默认 `unicode61` 分词器不切中文，需要用 `trigram` 分词器（SQLite 3.34+）；跨平台发布时需实测上游编译选项（FTS5 默认启用，trigram 需验证）。若召回质量仍不满意，可换外挂分词器——这是**索引层内部替换**，不动文件层，正是「文件为源」架构的容错红利。
- **索引新鲜度不成为问题**：通用 RAG 的索引保鲜之所以难，是因为文档从任意入口变更；本方案的知识条目**只经门禁写入**，写入钩子里同步更新索引即可准实时，不需要轮询，也不需要 Merkle 树增量同步。

### 8.3.3 为什么起步走符号/词法，不走 embedding

| 理由 | 说明 |
|---|---|
| 可审计性优先 | 条目一旦进入上下文就等于获得权威，因此「为什么注入这条」必须可解释。BM25 分数 + 命中词高亮是确定性、可向人展示的；向量相似度不是 |
| 规模不匹配 | dogfooding 估算是百级到千级条目，用向量库属于杀鸡用牛刀，且自带一套分块/嵌入/增量同步的基建与固定成本 |
| 写入路径保鲜成本 | 条目由 agent 高频写入时，embedding 流水线（分块、模型、增量同步）会成为写入路径的拖累；门禁单写路径 + 词法索引没有这个问题 |
| 腐化放大 | 错误条目的向量与其「同源错误」语义相近，会被一起召回——恰好放大 8.1 要防的腐化。词法检索至少让错误条目与正确条目在关键词命中上分开 |
| 检索意图是「过滤 + 精确召回」 | agent 查知识库的典型意图是「这个接口的约定是什么」「上次类似的坑怎么踩的」——意图明确、关键词明确，BM25 + 字段过滤即可高质量满足；「我说不清但你知道我要什么」的场景在本项目占比低（需求已由协调 agent 解析为结构化事件） |

### 8.3.4 升级路径：embedding 作为可插拔增强

**触发条件**（满足其一即评估）：条目数超过约 5k，或 FTS5 trigram 的召回质量实测不足。

**做法**：同一个 SQLite 库里加一列向量 + RRF（Reciprocal Rank Fusion）混合排序——词法结果与语义结果各出一份排名，融合后排序。升级**只动索引层**：frontmatter schema 与文件布局不变，检索接口（`kb_search` / `kb_get`）不变。

**版本兼容纪律**：SQLite 文件格式跨版本稳定，但 FTS5 索引内容不可跨大版本直接迁移。因此 v1 就把 `kb reindex` 做成独立命令，任何迁移路径都是「删库重建」而不是「转换索引」。

### 8.3.5 检索意图 → 手段对照

| 检索意图 | 手段 |
|---|---|
| 「这个接口/术语的约定是什么」 | frontmatter 过滤（`type` / `status` / `tags`）+ FTS5 BM25 |
| 「上次类似的坑怎么踩的」 | BM25 关键词 + `type: pitfall` 过滤 + 关联条目展开 |
| 「这条规则现在还成立吗」 | `status` / `confidence` 过滤 + `source_anchors` 机验（符号锚点是否仍存在） |
| 「这条替代了谁、和谁冲突」 | 解析 `supersedes` / `contradicts` 成内存图做遍历（不引入图数据库） |
| 「谁引用了这条」 | 反向索引：账本条目证据锚点中的 `{kind: kb}` 引用 |

## 8.4 生命周期工程化：状态机 + 门禁复用

> **本节回答**：候选条目怎么变成生效条目、生效条目怎么退场，以及为什么不需要为此新造一套机制。

### 8.4.1 状态机

```text
                  (a) 复述检验通过
                  (b) 证据锚点机验有效
抽取/回流 ──► candidate ──(c) 人在 IM 侧点确认──► active
                  ▲                                │
                  │  (f) 锚点失效 → 降级（唯一机器降级例外）
                  └────────────────────────────────┘
                  │                                │ (d) review_due 到期
                  │ 被证伪 / 长期无人处理            │ (e) 失效信号命中
                  ▼                                ▼
               retired ◄──── 保鲜门禁 + 人工确认 ── deprecated
```

- `(d)` 是时间触发，`(e)` 是信号触发（锚点失效 / 推翻记录命中 / 关联代码删除），两者都只**触发复核**，不等价于自动废止（详见 8.4.4）。其中「锚点失效」这一形态先由 `(f)` 即时生效。

- 方向是**单向**的（与共识条目状态机同构）：`retired` 不复活，重新启用要走新条目并 `supersedes` 旧条目，历史因此完整。
- **唯一例外是 `(f)`：锚点失效 → 机器把 `active` 降回 `candidate`**（8.4.4 形态 1）——这是本章唯一的机器降级路径：由机器检测、必然留痕、只挂起结论的效力而不修改结论内容。它与共识账本条目「锚点漂移降回临时（`provisional`）」是同构的一条例外（[04-consensus-ledger.md](./04-consensus-ledger.md) §3.2 的唯一降级路径）。
- `deprecated` 与 `retired` 的区别只在「是否还值得让人看到」：前者是过期但可能仍被检索到（显式参数），后者是已废止、默认彻底排除。

### 8.4.2 候选 → 生效：三个条件同时满足

| # | 条件 | 执行者 | 说明 |
|---|---|---|---|
| (a) | 复述检验通过 | 异构复述 agent（8.5） | 机器侧的独立复现 |
| (b) | 证据锚点机验有效 | 内置校验器 | 符号锚点指向的符号仍存在；commit 锚点可解析；引用的 KB 条目存在且非 `retired` |
| (c) | 人在 IM 侧点确认 | 人 | 复用单机器人路由的「选择题推回」通道，合入永远人工的总边界在此自然落地 |

三个条件缺一不可。**机器侧的检验永远只是"给人出一道什么难度的题"的依据，不是放行权**——这与 ADR-0001 的边界一致。

### 8.4.3 「双人确认」落地为「异构复述 agent + 人」

原始口径是「双人确认」。落地时改为**异构复述 agent + 人**，理由是权衡后的选择：

| 方案 | 独立性来源 | 成本 | 采用的场景 |
|---|---|---|---|
| 真人双签 | 两个独立的人 | 高：人工介入负担是平台的隐性死法（选择题疲劳），双人真审会变成收税点 | 高风险域条目（安全、资金、合规相关）**可配置升格** |
| 异构复述 agent + 人 | agent 提供机器侧独立性，人提供权威背书 | 低：人只点一次确认 | 默认 |

这不是把「双人」打折，而是把独立性的两个来源拆开：**机器侧的独立性靠异构与盲写保证**（8.5），**权威背书靠人**。默认轻、风险升格重，与 ADR-0002「默认轻量通道 + 触发式升级」一致。需要真双签的团队只需在门禁配置里换成真人双签校验器——同一门禁、零代码。

### 8.4.4 生效 → 过期/废止：双触发

| 触发 | 形态 | 处理 |
|---|---|---|
| **时间** | `review_due` 到期 | 保鲜门禁把条目挂到 IM 侧选择题：「仍成立 / 需修订 / 废止」，附最近的引用记录与锚点机验结果 |
| **信号** | 被引用时锚点失效 / 推翻记录命中 / 关联代码删除 | 不等时间到，立即触发复核 |

信号触发的三种具体形态：

1. **锚点失效**：符号锚点指向的符号被删除或改名 → 条目自动降级为 `candidate`（失去注入资格），即 8.4.1 图中的边 `(f)`——本章唯一的机器降级例外——并触发复核；
2. **推翻命中**：共识账本出现 `overturned` 条目，其证据锚点与某 KB 条目重合 → 该 KB 条目 `confidence` 下调并强制复核；
3. **代码删除**：`source_anchors` 中的符号锚点全部消失且无替代 → 走废止流程。

废止留痕、全文保留（`status: retired`），并在事件流中记录原因与依据。

### 8.4.5 机制复用：知识生命周期就是第三种门禁消费者

不新造机制。本方案已有两处「状态机 + 门禁 + 人工确认」的组合（共识条目状态机、流程节点门禁），知识条目是**第三个消费者**，直接复用 ADR-0014 的双注册表结构：

```yaml
apiVersion: agent-cord.dev/gates/v1        # 引擎同时接受 vN 与 vN-1
kind: Gate
metadata: { id: kb-promotion, name: 知识条目晋升 }
spec:
  role: { initiators: [coordinator], approvers: [architect] }   # prevent self-review：提议晋升者不自批
  attach:
    node: upturn                        # 上线回流节点（artifact: kb_entry）
    when: post
    triggers: [kb.candidate.extracted]  # 规则抽取产出候选条目
  checks:
    - ref: kb-recite-check@official     # (a) 复述检验：内置校验器（内部是 k=2 异构盲评，见 8.5）
    - ref: kb-anchor-validity@official  # (b) 证据锚点机验：内置校验器
  pass: { require: all, human_confirm: true }   # (c) 人在 IM 侧点确认
  on_fail: escalate                     # 未过 → 条目维持 candidate；分歧升格为风险仲裁型选择题
  write_back: [knowledge_entry, session_event]  # 写回目标用封闭枚举
  link_entry: auto                      # 写回必须回链共识条目 id
  escalate: { to: risk-arbitration, approve_by: [architect] }
  permissions: { write: [knowledge_entry, session_event] }   # 最小写权限
  timeout: { after: 72h, on_timeout: escalate_human }
```

两个结构性好处：

- **新增一种保鲜策略零代码**：轻量条件（如「`confidence < 0.6` 且 90 天未被引用」）用 CEL 表达式写在 gate 里；重型校验（跨系统查证）注册成 IPC 插件（ADR-0016），gate 只写 `check.ref`；
- **知识库的写权限被门禁收窄**：`permissions` 声明这个 gate 能写什么，运行期按声明最小化（详见 [09-security.md](./09-security.md)）。

## 8.5 复述检验协议

> **本节回答**：怎么把「讲不清来源与边界的知识不许获得权威」变成一条可执行、可审计、可校准的检查？

这是本项目的**原创设计**（材料中无直接先例），因此协议写得细一些。它的本质是 8.1 不变量 I2 的工程化：**让另一条独立路径重新走一遍「从证据到结论」的推理，再比对两条路径是否收敛**。

### 8.5.1 六步协议

| 步骤 | 执行者 | 输入 | 产物 | 失败处理 |
|---|---|---|---|---|
| 1 触发 | 平台 | 规则抽取门禁 / 条目重大修订 | 一次复述检验任务 | — |
| 2 隔离取材 | 平台 | `source_anchors` 指向的**原始材料** | 两份互不可见的材料快照 | 锚点不可解析 → 直接判不通过 |
| 3 盲写 | 复述 agent | 只有原始材料（**不含抽取 agent 的结论文本**） | 用自己的话写出的条目草案 | 无法成文 → 不通过并留痕 |
| 4 固定问卷 | 复述 agent + 抽取 agent 各自独立作答 | 同一份问卷 | 两组答案 | — |
| 5 逐项比对 | 平台（确定性比对）+ 判定 | 两组答案 + 双方证据锚点 | pass / 分歧（附少数派理由） | 分歧 → 升级人工 |
| 6 留档 | 平台（门禁写入器） | 全部产物 | 写入 `verified_by` | — |

### 8.5.2 隔离要求（决定这条检验有没有效）

1. **异构**：复述 agent 与抽取 agent 必须使用不同模型（ADR-0007：判定与生成必异构）。同模型复述只会复现同一个盲区，检验退化为形式。
2. **盲写**：复述 agent 只拿**原始证据锚点指向的材料**，不拿抽取 agent 写的条目文本、不拿它的中间推理。否则它做的是「改写」而不是「独立复现」，改写无法区分「结论正确」与「表述清晰」。
3. **进程与工作区隔离**：复述任务使用独立子进程与独立临时工作区（ADR-0011：每任务 subprocess），两侧的会话记录分目录保存，**禁止把抽取 agent 的 transcript 提供给复述 agent**（协议强制项）。
4. **不辩论**：不允许两个 agent 互相看见对方答案后修改自己的答案（ADR-0006：独立盲评，不辩论）。分歧本身就是有价值的信息。

### 8.5.3 固定问卷（四问）

固定问卷的作用是把「讲清楚」这个模糊要求变成可逐项比对的检查项。四问覆盖两类**入库时**能检出的腐化成因（来源丢失、边界丢失）；第三类「永不过期」不靠问卷，由生命周期机制处理（8.4）：

| # | 问题 | 检验什么 | 对应的腐化成因 |
|---|---|---|---|
| Q1 | 这条知识**在什么条件下**适用？ | 适用条件是否被双方一致表述 | 边界丢失 |
| Q2 | 它在**什么时候失效**/边界在哪？ | 边界与失效条件 | 边界丢失 |
| Q3 | 有哪些**例外**？（已知反例、例外场景） | 知识的粗粒度陷阱 | 边界丢失 |
| Q4 | **证据在哪**？请给出锚点 | 来源是否可独立定位 | 来源丢失 |

Q4 的答案要落成**可机验的锚点**（符号/commit/KB id），而不是「我记得在哪看过」。

### 8.5.4 与投票机制的关系：k=2 盲评投票的特例

复述检验**就是** k=2 的异构盲评投票（见 [05-voting.md](./05-voting.md)），只是在「投什么」上做了特化：投票的选项是「适用条件 / 边界 / 例外 / 证据」四项是否一致，票源是「抽取 agent 的原始判断」与「复述 agent 的独立复现」。

但它**不占用投票队列名额**：投票队列的准入硬条件是「非重点 + 可机验（锚点类型 ∈ {code, case}）+ 可逆」，语义类（不可机验）决策点本就进不去（见下表），复述检验因此是一条独立的调用路径，只复用同一套盲评判定规则。

因此以下既有规则**原样适用**：

| 既有规则（ADR-0006 / 投票机制） | 在复述检验中的形态 |
|---|---|
| 不辩论、不共享中间推理 | 两侧独立作答，互不可见 |
| 判定 agent 与生成 agent 必异构 | 复述 agent ≠ 抽取 agent（模型不同） |
| 锚点独立度检查：结论一致但锚点重合（Jaccard ≥ 0.5）→ 疑似同源错误 → 判定 `escalated_anchor_overlap`，强制升级人工 | 双方答案一致且证据锚点高度重合 → **不是通过，而是升级人工**（说明两条路径其实同源） |
| 语义类（不可机验）决策点不进投票队列，直接落 `needs_verification` / 人工 | 纯语义条目（`term`）从不出现在投票队列，直接落「待人工确认」档，不获得机器免审通道 |
| 难度门：只投非重点 + 可机验（锚点类型 ∈ {code, case}）+ 可逆的决策点 | 复述检验只对可机验锚点的规则类条目给「普通确认」通道；高风险域条目直接升级为真人双签（8.4.3） |

**一致性通过不直接放行，它决定"给人出一道什么题"**：

- 2/2 一致 + 锚点可机验 + 锚点不重合 → 判定 `confirmed`，推一道**普通确认题**（人在 IM 侧点一下）；
- 2:1 分歧、或双方锚点重合（疑似同源错误）→ 判定 `escalated_anchor_overlap`，升格为**风险仲裁型选择题**：并列双方结论与证据，附少数派理由，人选边；
- 语义类条目（锚点类型不在 {code, case} 内，不可机验）→ **不进投票队列**，直接判 `needs_verification`：落「待人工确认」档、不给机器免审通道，按风险仲裁题推给人；
- 判不通过 → 条目维持 `candidate`，退回抽取环节（也可能是本条知识本身不成立，此时走废止或改写）。

### 8.5.5 产物留档：`verified_by`

复述产物（双方问卷答案、模型身份、会话 id、锚点集）写入条目 frontmatter 的 `verified_by` 字段并留档，**追加而非覆盖**。这样「这条知识当初怎么通过检验的」本身可审计——将来它被推翻时，能定位到是复述环节漏检、还是证据本身在那之后变了。

投票执行器的复用见 ADR-0013：直连模型 API（锁定模型版本、`temperature=0`、结构化输出、逐次采集 usage），**不复用 coding CLI 做投票**；采集到的 `model@version` 与 `prompt_hash`、`session_id` 一并写入 `verified_by`。

### 8.5.6 校准项（试点期实测）

这条协议没有文献先例，通过率与误放率都是未知数，必须在 dogfooding 中实测（顺带采集 token 成本）：

| 指标 | 含义 | 不达标的读法 |
|---|---|---|
| 复述通过率 | 候选条目一次通过的比例 | 过低 → 抽取质量差或问卷过严，条目会积压 |
| 误放率 | 通过但后续被推翻/证伪的比例 | 过高 → 异构或盲写没做扎实，检验退化为形式 |
| 单次检验成本 | token 与时长 | 与条目价值比较，决定是否只对高价值条目跑完整检验 |

**边界认知**：复述检验防的是「讲不清来源与边界」，**不防「两个 agent 一起错」**——LLM 错误跨架构、跨供应商依然高度相关。因此生效条件里始终保留「锚点机验」与「人在 IM 侧确认」两道独立信号，复述检验只是其中一道。

## 8.6 四个最小机制集：闭环与验证指标

> **本节回答**：让平台越用越好的最小机制集是哪四个？每个怎么算闭环、用什么指标验？

| 机制 | 触发 | 输入 | 产出 | 闭环验证指标 | 不达标的读法 |
|---|---|---|---|---|---|
| **bad case 回流** | 条目被推翻 / 线上问题归因 | 推翻记录（含原因分类与新证据） | `confidence` 下调、同类结论强制投票、必要时新增 `pitfall` 条目 | 推翻原因分类分布；同类结论的下次一致率是否变化 | 推翻率高但知识库无变化 → 回路断了，只记了账没改机制 |
| **规则抽取** | 需求归档 / 门禁判定重复出现 | 归档时的账本条目、评审意见 | 知识库候选条目（`candidate`） | 候选→生效转化率；新条目在下一次需求被检索命中的比例；生效条目被后续需求引用的次数 | 抽取量大但零引用 → 抽的是噪音不是知识 |
| **介入学习** | 每次人工介入结束 | Issue 类型 / 耗时 / 人的答案 | 澄清标准库扩充（把重复出现的澄清问题变成标准问句）、门禁触发器校准 | **Issue 密度随需求序号衰减**（8.8）；同类型 Issue 的重复出现率下降 | 密度不衰减 → 流程在收税 |
| **知识保鲜** | `review_due` 到期 / 失效信号命中 | 条目 + 锚点机验结果 + 引用记录 | 续期 / `deprecated` / `retired`（均留痕） | 过期条目被引用次数趋零；锚点失效到条目被降级的时延；`deprecated` 条目被显式查询的次数 | 过期条目仍高频命中 → 检索层没执行状态过滤 |

展开两点：

**bad case 回流的关键在「同类强制投票」**。单条被推翻只下调它自己的置信度，价值有限；真正的自进化发生在「同类型结论下次自动强制投票」——即把一次推翻的教训转成下一次的机制参数（提高判定强度），这与 ADR-0002「触发式升级」是同一套思路。

**知识保鲜的指标必须包含时延**。一个条目在锚点失效后还能存活多久（被检索到多少次之后才被标记），直接反映检索层有没有执行状态过滤——这个数字比「过期条目数量」更能说明机制是否活着。

四个机制共用一条写入路径（门禁写入器），所有状态变化写入 `events.jsonl`，因此每个指标都可从事件流重算，不依赖额外的埋点。

## 8.7 知识如何进入上下文

> **本节回答**：生效的知识和候选的知识分别以什么形态、在什么时机进入 agent 的上下文？为什么不允许预载全库？

复用最小上下文包的两层结构（前置高信号层 + 定位符层），不新造注入协议：

| 条目状态 | 进入哪一层 | 形态 | 上限 |
|---|---|---|---|
| `active` | 前置高信号层 | 一行一条：一句话结论 + KB-id + 证据锚点 | 硬上限 ≤ 8 条（初值，待校准），计入层 1 的 2–4k token 预算 |
| `candidate` | 定位符层 | 只有 id + 标题 + 适用域标签，agent 用工具 JIT 拉取正文 | 不限条数（但只给地址） |
| `deprecated` | 不进上下文包 | 仅 `kb_search` 显式参数可取 | — |
| `retired` | 永不注入 | 不可注入，不可检索 | — |

进入前置高信号层意味着「获得权威」，因此必须满足三条：`status: active`、锚点机验通过、语句自带边界（否则它进不了前置层，只能留在定位符层）。

**投票/探索 agent 一律用工具检索，不预载全库**（`kb_search` / `kb_get`，只读）。三个理由：

1. **上下文预算**：全库预载会稀释注意力，上下文越长表现越差；
2. **防污染**：预载会把与本决策点无关的条目一起塞进盲评上下文，干扰独立性；
3. **保护锚点独立度**：如果多个投票 agent 都从同一份预载内容里挑证据，它们的证据锚点会人为同化，锚点独立度检查（Jaccard ≥ 0.5）就失去意义——工具检索让每个 agent 的检索路径与命中集各自独立，这正是 ADR-0006 所需的独立性前提。

检索命中率（哪些定位符被实际拉取）与注入记录写入事件流（`events.jsonl`），这两份数据同时服务于三处：知识条目的验收指标（8.6）、上下文包的配比校准、以及「为什么这条知识被注入」的可解释性。

工具权限对应 [09-security.md](./09-security.md) 的角色权限表：投票/评审 agent 有知识库**只读**权限，无写入凭证；知识库的写只能经门禁写入器。

## 8.8 飞轮证据：Issue 密度随需求序号衰减

> **本节回答**：怎么证明知识沉淀真的在起作用，而不是我们在自我感觉良好？

**Issue 密度** = 每个需求上人工介入的 Issue 数（给人做的选择题数量，见人工介入点设计）。**读数规则：同一业务线第 10 个需求的人工介入密度应显著低于第 1 个。** 这是知识沉淀生效的直接证据：同样类型的业务，第一次要问的很多问题，第十次应该已经由知识库回答。

**密度不衰减，说明流程在收税**——平台消耗了人的注意力，却没有把注意力换成可复用资产。这时要按 8.6 的四条线索排查：抽取没做（规则没沉淀）、检索没命中（沉了但用不上）、介入学习没回流（澄清问题没变成标准问句）、保鲜没执行（命中的是过期知识）。

### 8.8.1 读数纪律

密度衰减有多个混杂因素，必须在读数前预注册口径，避免事后解释：

| 混杂因素 | 处理方式 |
|---|---|
| 需求难度分布变化 | 按难度分桶（难度桶定义与投票难度门复用同一套分类），桶内比较 |
| 需求来源/类型变化 | 按业务线与需求类型分组；跨组比较不成立 |
| 人员变化 | 只读密度，不读「某人被问了几次」 |
| 观察期过短 | 与推翻率联合解读（推翻率需要观察期，短窗口下零推翻率是警报而非满分） |

**与推翻率联合解读**：密度下降 + 推翻率正常 = 飞轮在转；密度下降 + 推翻率异常低 = 可能是验证信号太弱（知识变「安静」，不是变对）；密度不降 + 推翻率高 = 知识没沉淀，同类错误在重复。

### 8.8.2 反向指标

- **条目数增长但引用率为零**：知识库在制造噪音，不是资产。条目数不是目标，「被后续需求实际引用」才是。
- **候选条目长期积压不晋升**：门禁太重（复述检验或人工确认成了新卡点），需要放宽或换更轻的检验档位——自进化机制自己也会变成流程税，必须一起度量。
- **复述检验通过率异常高（接近 100%）**：检验退化为形式的信号，检查异构与盲写是否真的执行。

### 8.8.3 最小可验证闭环

验收标准（DoD）里自进化的唯一硬指标：**至少一轮 bad case 回流入知识库，并被后续需求实际引用**，目标在 M4（方案定稿后约六周）的演示中跑通一轮完整闭环：

```text
需求归档 → 规则抽取（candidate） → 复述检验 + 锚点机验 + 人确认（active）
   → 下一个需求的前置高信号层命中该条目 → 该需求少了一道人工选择题（Issue 密度下降）
```

这条链跑通一次，即可证明四个机制不是四段各自成立的描述，而是一个闭合环。
