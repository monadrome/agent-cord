# 12 · 验证实验设计

> 状态：**协议已设计定稿，实验尚未执行**。本章的阈值、样本量、脚本清单均为可执行口径，但没有任何数字来自本项目的实测。

## 本章回答什么问题

本方案的几个关键机制都建立在"假设"上——假设独立投票能提高可靠判断的比例、假设弱模型细粒度编排能跑通、假设非对称模型分配省钱、假设防腐钩子不会变成流程税。本章回答：

1. 每个假设用**什么实验**来证伪，实验怎么设计才能给出可解释的数据？
2. 实验一（最高优先级）的完整可执行协议是什么——决策集长什么样、投票怎么隔离、指标怎么算、阈值定在哪？
3. 实验需要哪些**外部输入**，拿不到时怎么降级？
4. 上线后用什么**仪表盘**持续观察，四个指标的采集点与口径是什么？

**共同约定**（四个实验都适用）：

- 可复现：锁定模型版本、temperature=0、记录每次调用的 prompt hash 与 usage；
- 呈现顺序与选项顺序随机化（存在 option-position prior，会污染结果）；
- 脱敏：不导出代码正文与业务实体，只导出锚点 + commit 快照（见 §1.2）；
- 成本采集：每次调用逐条记录 token 用量与单价，供实验三与验收参考项使用。

## 1. 实验一 · 共识机制回放

### 1.1 要回答的证伪问题

> agent 投票的"一致"里，有多少是真的对（支撑"独立一致度"作为 confirmed 依据），有多少是同一个盲区的相关错误？

这是本方案最核心的风险（R-1）的直接检验。实验一的结论决定：`2/2 一致 → confirmed` 这条免人工通道能开多大、异构投票是否必须、锚点独立度检查值多少。

### 1.2 决策集 schema（导出为 JSONL，每行一个决策点）

```yaml
decision_id: D-0001
需求id: <内部需求主键>
题目: <一句话决策问题，如"某分支条件下是否跳过该规则">
选项集:                       # 预结构化为 A/B/C，选项顺序对每个 agent 单独随机化
  A: <选项描述>
  B: <选项描述>
  C: insufficient_evidence    # 固定兜底项：证据不足，不许强行二选一
人工结论: A                    # 金标准，盲跑期对 agent 不可见
人工确认人: <工号>
确认时间: <ISO 日期>
分类标签: [契约|求值顺序|跨模块语义|其他]   # 用于难度/类型分桶；答案不可从标签推出
最终状态: confirmed | overturned            # 回放前从项目档案回填
推翻原因: 证据不足|语义理解错|需求变更|外部依赖变化   # overturned 时必填
证据锚点:
  - {类型: code, 符号: "path/File.ext#Class.method", 快照: {commit: "<git rev>", content_hash: "<sha256>"}}   # 行号（文件:行号）只作显示层，不进实验包、不参与判定
  - {类型: knowledge, 符号: "KB-0017"}
脱敏状态: 已脱敏（业务实体占位符化；不含凭证、内部域名、内部主键）
```

**脱敏要求**（硬性）：

- 代码不导出，只导出 `符号锚点 + 锁定 commit 的内容快照`；agent 在隔离环境 checkout 该 commit 自行读码；
- 业务实体用占位符映射（如具体白名单名 → `W1 白名单`），映射表单独保管、不进实验包；
- 确认人只留工号，剔除姓名与联系方式；不得包含任何凭证、内部域名、密钥。

### 1.3 盲跑协议

**主配置 k=3**。理由：机会校正一致度（Fleiss' κ）需要 ≥3 个 rater；3 票还能实测"2:1 分裂 → needs_verification + 少数派理由留痕"这条放行规则。k=2 留作成本对照。

**三组对照（2+1 设计）**：

| 组 | 配置 | 测什么 |
|---|---|---|
| G1 同构 | 同模型 × 3，异角色提示词（代码考古 / 测试视角 / 架构审查） | 默认方案的成本基线 |
| G2 异构 | 跨模型家族 × 3（至少 2 个不同家族） | 异构投票的实际收益 |
| G3 单 agent | 1 个强模型独立判断 | 投票增益 = G1/G2 指标 − G3 指标；同时提供"无投票基线" |

**隔离与禁止项**（每个投票 agent）：

- 独立进程 / 独立上下文窗口；**禁止共享中间推理、禁止互读输出**（协议强制项，不是建议）；
- 禁止看到：人工结论、其他 agent 输出、`最终状态` / `推翻原因` 字段、确认人信息；
- 选项顺序 per-agent 随机置换，决策点呈现顺序也随机化；
- 每个 agent 的输出必须带证据锚点；无锚点则只能选 C。

**提示词模板要点**（每个角色一份，结构相同、视角不同）：

1. 角色设定一句话；
2. 任务：checkout 指定 commit，读证据锚点周边代码，从选项集选一项；
3. 必须给出证据锚点（文件 + 符号/位置），无锚点则选 C；
4. 严格 JSON 输出：`{"选项": "A|B|C", "证据锚点": [...], "置信度": 0-1}`，多余文本视为解析失败并重试一次；
5. 禁止选项外语术（"以上都对""需要更多上下文"等）。

### 1.4 指标口径

**指标 1 · 证据覆盖率**（硬门槛，机械可查）

```
证据覆盖率 = |{决策点 : 结论 ≠ C 且给出 ≥1 个有效证据锚点}| / |{结论 ≠ C 的决策点}|
回放中对人工决策集直接计算：|{条目带 ≥1 个有效锚点}| / |{全部决策点}|
```

有效锚点定义：checkout 锁定 commit 的内容快照后，`code` / `case` 类锚点的符号（`文件/包#符号路径` 或用例 id）能解析到对应内容、或 commit SHA 存在（对齐 [`./04-consensus-ledger.md`](./04-consensus-ledger.md) §4 的「活锚点 + 快照」结构）。**行号只作显示层，不作为有效性判据**；行号漂移率另行统计，为 CP-18 提供数据。目标 100%。

**指标 2 · 独立一致度**（三层口径，一次实验全出）

| 口径 | 定义 | 角色 |
|---|---|---|
| 原始一致率 | k 个 agent 全票一致（或多数成立）的决策点比例 | 辅指标（不校正随机一致，选项分布倾斜时虚高） |
| 机会校正一致度 | k=3 用 **Fleiss' κ**；报 **Gwet's AC1** 防 prevalence paradox；个别条目缺票时用 Krippendorff's α | **主指标** |
| **一致但错率** | `|{投票一致 且 多数选项 ≠ 人工结论}| / |{投票一致的决策点}|` | **本次实验最重要的产出**（R-1 的直接度量） |

两个必须写进报告的方法学事实：

1. **Prevalence paradox**：当多数 rater 把多数条目判进同一个类别（本场景必然如此——多数决策点的正确答案是同一个高频选项），原始一致率接近 100% 而 κ 被压到接近 0。因此 κ 与 AC1 **并报而非替代**（Zec 2017, PMC5712640；PMC10205778）。
2. **一致 ≠ 正确**：跨 runner 大样本研究显示一致度对正确性仅"正但弱"（rho 0.20–0.59），agreement≥0.8 的条目中 48% 是错的（arXiv:2607.08065）。

**核心相关统计**：把 G1/G2 的多数结论当 rater 1、人工金标准当 rater 2，算 **Cohen's κ（人机一致度）**——即"投票结论与人工结论的相关性"的落地形态。

**指标 3 · 推翻率（口径限制，必须写进报告）**

推翻率是**纵向**指标（观察期内 confirmed → overturned），回放实验测不了真正的推翻率。回放只出替代口径：决策集中 `最终状态 = overturned` 的占比及原因分布——这是**历史数据构成比，不是平台运行指标**，不得与上线后的推翻率混用。正式口径待观察期定义（CP-16）。

### 1.5 证据锚点重合度统计（锚点独立度的实测）

对每个"投票一致"的决策点：

1. 取两两 agent 的证据锚点集合，计算 **Jaccard 系数**；
2. 输出重合度分布，并统计 `Jaccard ≥ 0.5` 的决策点占比（0.5 即机制中"疑似同源错误"的判定线）；
3. 与"一致但错率"做交叉列联：**重合且错** = 同源错误的直接证据；**重合且对** = 锚点收敛到同一处代码（健康，说明证据是硬信号）；
4. 同时统计"一致但不重合"的比例——它衡量锚点独立度检查的**误伤面**（结论对但锚点因视角不同而不重合）。

这一节的产出直接决定锚点独立度检查是"运行时前移的验证"还是"额外噪声"。

### 1.6 阈值与样本量

**样本量**：决策点 **N ≥ 100**。依据：kappa 类研究经验法则 50–100 subjects 起步（PMC12935580）；检测 κ≈0.4 的小效应约需 n≈120（弱来源，仅作量级参考）。成本量级：N=100 × k=3 × 2 组 = 600 次强模型调用（与 CP-30 一并采集）。

**判定阈值**：

| 判据 | 阈值 | 含义 |
|---|---|---|
| 证据覆盖率 | = 100% | 硬门槛；达不到说明锚点机制有洞 |
| 原始一致率 | 不作健康判据 | 仅描述性统计、按难度分桶呈现；固定健康区间（如 70–90%）已废弃（无文献依据），须与推翻率联合解读（口径见 [`./05-voting.md`](./05-voting.md) §7.2、§7.3） |
| Fleiss' κ | ≥0.61 有效；0.41–0.60 勉强；<0.40 机制需重设计 | 0.61 为 Landis–Koch "substantial" 下限 |
| **一致但错率** | ≤10% 绿；10–20% 黄；>20% 红 | **红 = 独立一致度不能单独支撑 confirmed**，必须异构投票 + 人确认兜底 |
| 人机 Cohen's κ | ≥0.60 | 投票结论可作为"人认可"的代理信号 |
| 推翻率替代口径 | 仅描述性统计，不设阈值 | 口径限制见 §1.4 |

参照系：通用推理基准实测是"agreement ≥ 0.8 时 48% 错"。本方案设 ≤10% 的绿线比它严格近 5 倍——实验的意义正在于实测业务代码理解场景是否显著好于通用推理基准；若落在 10–48% 之间，说明场景优势有限，R-1 需升级应对（提高人确认比例）。

## 2. 实验二 · 粒度-模型能力曲线

**问题**：同一需求，"强模型整体执行"与"弱模型细粒度编排"哪种路线更有效？粒度与模型能力之间是什么关系？

**分组**：

| 组 | 配置 |
|---|---|
| 甲 · 强模型整体执行 | 强模型单 agent 端到端执行，不切任务图 |
| 乙 · 弱模型细粒度编排 | 探索/编排用强模型，实现用弱模型细粒度任务图（只传接口面上下文），验证用强模型且与生成异构 |

**控制变量**：同一需求、同一仓库快照、同一验收用例集；两组执行顺序随机化或交叉执行（对抗仓库状态与学习效应）。

**观测量**：

| 观测 | 口径 |
|---|---|
| 完成度 | 验收用例通过率（分母固定为冻结的用例集） |
| 返工轮次 | 单任务平均返工次数（P-10 的上限来源） |
| 人工介入次数 | 本需求触发的介入点（选择题）数量与总耗时 |
| 耗时 | 墙钟时间（含等待与重试） |
| **token 放大系数 m** | 乙组总 token / 甲组总 token（初值预期 2.5，告警阈值 5） |

**判定方向**：在"人工介入次数不显著上升"的前提下，若乙组完成度不低于甲组，则"粒度自适应 + 认知负荷分配"的方向成立；若乙组完成度显著更低或 m>5，则细粒度编排的收益被开销吃掉，需要重新设计任务粒度（而不是放弃弱模型）。

**局限声明**：样本量是"一个需求的两次执行"，属探索性观察，不做统计推断；结论用于参数初值（P-9 / P-10），不作为普遍结论。

## 3. 实验三 · 非对称模型分配 A/B

**问题**：生成侧用弱模型、判定侧用强模型，能否在质量不降的前提下省钱？（验证非对称分配的成本假设。）

**设计**：**验证侧固定不变**（同一组强模型盲评 + 锚点独立度检查 + 判定与生成异构），只替换生成侧模型档位：

| 组 | 生成侧 | 验证侧 |
|---|---|---|
| A | 强模型 | 固定（强模型 + 异构盲评） |
| B | 弱模型 | 同 A |

另加一组"**编排侧模型对照**"：把编排/探索侧的模型也换档，用来检验"模型分配应按认知负荷走，而不是套固定公式"这一修正意见——开销相对小，但能防止把非对称分配简化为口号。

**观测量**：质量（验收通过率、判定侧拦截率）、耗时、每次调用的 token 用量与单价（逐次 usage 采集）。

**判定（成本侧）**：成本假设成立的条件已形式化为不等式

```
C_verdict < (1 − r · m) × C_gen_strong
其中 r = 弱模型单价 / 强模型单价（现值 ≈ 0.13）
      m = 弱模型编排的 token 放大系数
```

代入 r≈0.13、m≈2.5 时阈值为 `0.675 × C_gen_strong`，即判定侧成本不超过"全用强模型生成"成本的 67% 即成立（典型配置下判定侧约占 20%，余量约 3 倍）。**成立区间：r < 0.2 且 m < 5 且判定侧上下文不膨胀**。因此本实验实际只需实测 r 与 m 两个系数。

**失效边界**（三条，需在报告中显式核对）：m > ~5（任务切太碎、上下文反复重传）；弱模型返工率 > 2 轮（生成侧 token 与等待时间双升）；判定侧上下文膨胀（每票从约 30K 涨到约 300K，余量消失——这正说明"证据锚点 + 盲评选题"的设计本身是成本控制的一部分）。

## 4. 实验四 · 防腐钩子误伤率

**问题**：L2 影响检查（diff 与账本证据锚点求交）在真实仓库中会不会变成流程税？

**设计**：L2 在一个真实业务仓库运行一周，采集：

| 观测 | 口径 |
|---|---|
| 命中数 | diff 与锚点求交命中的提交/条目数 |
| 命中的处置 | 确认仍成立（放行）/ 需更新文档（块级更新）/ 拦截 / 升级人工 |
| **误伤率** | `命中但无需处理的比例 / 全部命中` |
| 漏检信号 | 锚点失效（符号解析失败 / 快照内容 hash 不匹配）导致的条目降级次数；行号漂移单列观测（仅显示层，不作为失效判据） |
| 锚点分布 | 按 `type`（`code` / `case` / `contract` / `knowledge` / `doc` / `report`）统计各类锚点的占比与有效率；另记符号解析成功率 |

**三个降误伤手段**（同时验证效果，而非只统计）：符号级求交、格式化提交豁免清单、blame-ignore 类标记（纯格式化/大规模重命名提交不触发命中）。

**产出**：误伤率分布与阈值建议（关闭 CP-19 / P-7）。若误伤率过高，回退路径是:收窄命中条件（例如只在符号锚点命中时触发）+ 提高豁免覆盖，而不是取消 L2。

## 6. 度量仪表盘设计

仪表盘是**只读派生视图**：全部数据从共识账本与事件流聚合得到，不新增埋点；聚合统计可以重建，事件流本身永不进入 LLM 上下文。

### 6.1 四个指标

| 指标 | 定义（口径） | 采集点 | 呈现方式 | 健康判据 |
|---|---|---|---|---|
| **证据覆盖率** | 带 ≥1 个**有效**证据锚点的条目 / 全部应入库条目；有效 = 锁定 commit 的内容快照中符号锚点可解析（`code` / `case` 类）或 commit SHA 存在，**行号只作显示层、不参与判据** | 条目入账写入校验（实时）+ 每日对全量账本重算（发现锚点失效） | 单需求 + 累计趋势 | 100% 为达标；下降即说明入账口径放松或锚点在失效 |
| **独立一致度** | 三层口径：原始一致率（辅）、机会校正一致度（主，k≥3 用 Fleiss' κ / k=2 用 Cohen's κ，并报 Gwet's AC1）、一致但错率；**按决策点难度分桶**统计，并与推翻率联合解读 | 投票记录落盘时（含少数派理由、锚点重合度 Jaccard） | 分桶柱状 + κ 与一致但错率并列 | 不设固定区间；难题桶中 100% 一致是警报；一致但错率 >20% 红 |
| **推翻率** | 观察期内 confirmed → overturned 的比例，按原因分类（证据不足 / 语义理解错 / 需求变更 / 外部依赖变化） | 三个自动来源：测试失败反查来源条目、线上问题归因关联需求、后续需求探索提交推翻申请（均回链条目 id） | 按原因分类的趋势 + 高推翻条目清单 | **零推翻率是警报而非满分**（验证信号太弱或观察期太短） |
| **人工介入负担** | ① 单需求介入次数（Issue 密度）；② 单次介入耗时；③ 跨角色每人每日收到的选择题数量；④ **密度随需求序号衰减曲线** | 介入点（选择题）生成与答复事件 | 曲线（按需求序号）+ 分角色分布 | 密度不衰减说明流程在收税；③ 超阈值触发告警（阈值待校准，P-8） |

### 6.2 设计要点

- **成对解读，禁止单看**：独立一致度必须与推翻率、难度分桶一起看；证据覆盖率必须与锚点有效率一起看（覆盖率 100% 但锚点大量失效是假健康）。
- **衰减曲线是自进化唯一的"外部证据"**：知识沉淀生效的直接证据是同一业务线的第 10 个需求显著低于第 1 个。衰减也可能来自"需求变简单"，因此需要与需求复杂度标签作对照（这也是 P-14 复述检验通过率的观测场景）。
- **指标不追责**（R-3）：仪表盘用于改进机制，不用于评价个人或 agent；对"应推翻而未被发现"的条目做抽查审计，审计结果作为机制改进输入单列。
