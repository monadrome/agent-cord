# 13 · 开源运营

> 状态：**设计定稿、代码未实现**。本章的方案与仓库结构均为计划；License 与仓库骨架属"首次公开发布前必须拍板"的事项。

## 本章回答什么问题

一个开源基座不只是代码，还要回答：用什么许可证、仓库怎么摆、别人怎么贡献、和 DevMaster（某公司内部平台）是什么关系、最开始没人用的时候靠什么起步。本章回答这五个问题，原则是**只开源机制与协议，不含任何业务数据**。

---

## 1. License 建议

**主推荐：Apache-2.0**；**备选：MIT**。决策留给首次公开发布前拍板。

| 维度 | Apache-2.0（推荐） | MIT（备选） |
|---|---|---|
| 专利授权 | 含显式专利授权与专利报复条款 | 无专利条款 |
| 企业采用 | 企业法务接受度高，基础设施类项目主流选择 | 同样宽松，但专利风险需自行评估 |
| 商标与署名 | 明确商标不随许可授予；要求保留 NOTICE | 仅需保留版权声明 |
| 贡献者路径 | 可与 DCO 或 CLA 组合 | 同 |
| 与插件生态的兼容性 | 插件可采用任意宽松许可，不产生传染 | 同 |

**推荐理由**：本项目的使用者是开发者团队与 CI 流水线，采用决策往往经过企业法务；专利授权条款是这类"会被企业内嵌进研发流程"的项目最常被追问的一项。MIT 更宽松、更短，如果社区反馈认为 Apache-2.0 的 NOTICE 与变更声明要求构成摩擦，可降级为 MIT——两者不影响本方案任何技术设计。

**首次发布前需一并拍板的事项**（都不能事后补）：

1. 许可证与版权归属主体（组织 / 个人 / 基金会）；
2. 贡献者协议形式（DCO 签名 vs CLA）；
3. 仓库根目录的 LICENSE、NOTICE、CONTRIBUTING、CODE_OF_CONDUCT、SECURITY 等基础文件。

## 2. 仓库结构与 monorepo 建议

### 2.1 建议结构

```
<repo-root>/
├── packages/
│   ├── core/                    # 常驻 daemon + 薄 CLI 客户端；同时以库形式导出
│   ├── plugins-im-feishu/       # 官方 IM 适配：飞书长连接
│   ├── plugins-im-slack/        # 官方 IM 适配：Slack Socket Mode
│   ├── plugins-im-discord/      # 官方 IM 适配：Discord Gateway
│   ├── plugins-verify-git/      # 官方校验器：锚点求交、符号解析
│   └── plugins-verify-ci/       # 官方校验器：CI / 检查状态查询
├── docs/                        # 设计文档集（本章所在目录）
├── examples/                    # 内部 SDLC 示例的脱敏版（可热插拔替换的工作流样例）
└── conclave/                    # SSOT：共识快照文件夹，与用户代码同仓
    ├── <req-id>/
    │   ├── prd.md adr.md plan.md findings.md   # 快照文档（最新层，允许人工编辑+主动清理）
    │   ├── ledger.yaml                          # 共识账本：机判层（事件流的确定性投影）
    │   ├── votes/                               # 投票记录全文（VoteRecord 落盘，V-xxxx.yaml；与账本内嵌记录以 vote_id 对齐）
    │   └── events.jsonl                         # 事件流（历史层，append-only，永不清理）
    ├── knowledge/                               # 跨需求知识库（KB-xxxx，每条目一文件）
    ├── .index/                                  # 派生索引（如 SQLite FTS5）：写进 .gitignore，可随时删除重建
    └── conclave.toml                            # 布局版本、事件 schema 版本、索引与工作流配置
```

### 2.2 五条结构约定的理由

1. **`conclave/` 与用户代码同仓**：SSOT 的物理形态就是仓库内的普通文件夹——快照文档 + `ledger.yaml` + `events.jsonl`，版本化权威交给 `git`（[ADR-0010](./adr/ADR-0010-ssot-storage.md)）。不引入外部服务、不依赖平台即可阅读与迁移（这是回退设计的结构性保证，见 `./11-risks.md` R-9）。
2. **`events.jsonl` 随 git 版本化**：需要 `union merge driver`（写在 `.gitattributes`）防止分支合并丢事件。事件流是唯一的事实与顺序来源，丢事件等于丢历史。
3. **monorepo 承载 core + 官方插件**：官方插件与第三方插件必须**同协议、同实现路径**——放在同一仓库、走同一套 IPC 协议，是"官方没有后门"最直接的证明（[ADR-0016](./adr/ADR-0016-distribution-plugins.md)）；同时 core 与官方插件的协议演进天然同步。
4. **插件包独立发布**：monorepo 只是源码组织方式；每个插件仍作为独立包发布，用户可单独安装、固定版本。
5. **派生索引不进仓库**：全文检索索引（如 SQLite FTS5）是**派生**产物，可随时重建，不提交、不作事实来源。它属于后置可插拔增强，不进 MVP。

工具选择建议（非决策，M1 建仓库时拍板）：Node 生态常规做法——包管理用 workspaces（pnpm），版本发布用 changesets 之类工具，`engines.node` 声明最低版本并在 CLI 启动自检，避免 `postinstall` 脚本（CI 安全扫描常拦截），提供 `npx` 与容器镜像两条 CI 通道。

**不放进出仓库的东西**：业务数据、凭证、内部主键、脱敏映射表。`examples/` 只含脱敏版工作流样例。

## 3. 贡献模型

### 3.1 双轨贡献：配置与代码

| 轨道 | 贡献物 | 需要写代码吗 | 面向谁 |
|---|---|---|---|
| 配置贡献 | gate / agent 的 YAML 定义、声明式 markdown 资产（提示词、检查清单、模板、知识条目） | 不需要 | 使用平台的团队、流程 owner |
| 代码贡献 | IPC 进程插件（新增校验器或适配器） | 需要（任意语言） | 平台工程师、工具链 owner |

对应的插件三层（这是"配置即插件"能覆盖多少的边界）：

| 层 | 能力 | 边界 |
|---|---|---|
| 纯配置组合 | 用已有校验器/适配器组合出新的 agent 与 gate | **只能组合已有能力，不能提供新能力** |
| 声明式 markdown | 提示词、检查清单、知识条目模板 | 同上（数据，不是代码） |
| IPC 进程插件 | 提供新的校验信号源与新的平台适配器 | 唯一能提供新能力的一层 |

"新增一个 agent / 新增一个 gate 零代码"之所以成立，正是因为前两层能覆盖编排需求：定义本质是数据，插件才供能。

### 3.2 插件协议 v1（冻结）

> 协议与三层插件体系已定稿于 [ADR-0016](./adr/ADR-0016-distribution-plugins.md)；本节只展开对贡献者直接可见的部分。

- 握手先交换 `protocolVersion`，宿主与插件按版本声明兼容；
- v1 只承诺三类消息：**check**（入：产物描述 + 锚点；出：`{result: pass | block | warn, anchors, reason, confidence}`）、**capabilities**（能力清单，供配置引用）、**health**；
- 长连接类能力（IM 适配器的 stream）单列语义，不与门禁校验复用同一超时口径；
- **能力清单是配置与插件之间的唯一接缝**：配置只写 `validator: ci-status@my-plugin` + 参数，宿主在加载期按 manifest 校验能力是否存在、参数是否匹配——加载期报错，而非运行期炸；
- 强制超时（默认如 60 秒，gate 可覆盖），**超时按"升级人工"处理而不是放行**（与"默认轻量、触发式升级"一致）；
- 门禁结果三态（`pass` / `block` / `warn-and-continue`，warn 强制留痕；升级人工不是第四种结果，而是 `on_fail: escalate` 的后续动作，见 [06 章 §2](./06-gates-workflow.md)）；
- **不允许插件注册自由命令**：插件只能挂在"校验器"与"适配器"两类能力上，否则插件机制会把平台拖回脚本集合。

### 3.3 插件市场与上架门槛

- **形式**：一个**模板仓库** + 清单文件（`marketplace.json` 类），登记"插件名 + git 源 + 版本 + 能力摘要"。不自建注册中心——GitHub 就是注册中心。
- **门槛设计**：第一个外部贡献者应能只做两件事——fork 模板仓库、在清单里加一条 JSON 条目。要写代码的插件也只需实现三类消息并用 fixture 测试（JSON 进、JSON 出），回放测试与门禁校验共用同一机制。
- **安全底线**：清单只做**发现**，不做**执行**；安装必须由用户显式添加并锁定 commit / tag。第三方插件与官方插件同协议、同权限模型（子进程只拿到宿主显式注入的内容）。
- **官方插件集**：IM 三适配 + git/CI 校验，随版本内置并测试，但**构建方式仍走同一 IPC 协议**，不开后门。

## 4. 与 DevMaster 的关系边界

本项目的存在前提之一是：公司与团队内部已经有一套研发平台 **DevMaster（某公司内部平台）**，后文以该平台指代。开源基座与它是**分层关系，不是竞争关系**。

### 4.1 分层判据

| 层 | 内容 | 判据 |
|---|---|---|
| **通用层**（本开源基座） | 共识快照的存储形态与版本化、共识账本与状态机、事件流协议、盲评投票与锚点独立度、门禁/校验器协议、上下文剪裁、知识库条目与复述检验、插件协议 | **凡与具体系统无关的机制模式**，都可抽象进通用层 |
| **特化层**（该平台及其连接器） | 需求单系统、内部 CI 与检测流水线、截图比对与云模拟器、内部代码评审、内部设计稿与契约系统 | **凡数据源或执行环境绑定某公司内部系统的**，都属特化层 |

对外叙事由此收敛为一句：**通用层定义协议与机制，特化层提供业务工具链接入；接入而非重造。**

### 4.2 接入形态：旁路汇聚（不侵入）

- 全局 session 独立存储，位于代码仓库内的 `conclave/`；
- 通过**读该平台的结构化落盘产物**（需求结构化文档、契约文件、任务清单、验证报告）+ 用**内部需求主键**关联来汇聚，不改其 session 存储；
- 挂载形态是 hub-leaf：该平台的单开发者会话作为工作单元会话（leaf）挂到全局 session（hub）；账本条目、投票记录、门禁状态写在 hub 层，不侵入 leaf；
- 需要该平台侧的只有两件事：落盘产物的读取（低依赖），以及可选的 session 读写 API（唯一硬依赖，属待外部输入项 E3）。

### 4.3 两条对外口径必须精确（否则被现成能力证伪）

1. **防腐**：该平台已有"Spec 级巡检"（事后比对 + 自动 PR）。本方案的差异必须写成**账本级防腐**——对象是带证据锚点的共识条目而非统一 Spec，手段是状态机单向流转 + commit 前的**事前**拦截。二者机制同构、对象升级。
2. **非对称模型分配**：该平台已规划"按任务难度分档调度模型"。本方案的差异点是**判定侧强模型 + 独立盲评投票协议**（含判定与生成异构、锚点独立度检查），而不是泛泛的"按任务分档"。

### 4.4 脱敏原则

- 开源仓库**不含业务数据**：只开源机制与 schema，账本内容、知识库内容、内部主键、内部链接一律不出内网；
- 示例以脱敏版形式提供（`examples/`），业务实体用占位符；
- **脱敏策略的完整界定属暂缓项（非关闭）**：原型阶段后再重启。在此之前，公开发布的材料采用"最小暴露"策略——只讲机制与数据模型，不举真实业务例子。

### 4.5 尚未确认的外部前提

以下两条不阻塞开工，但决定"接入而非重造"叙事能否成立：该平台团队是否认同上述分层；其路线图（云端全流程闭环）的时间窗口。处理顺序是"先拿自举与实验数据说话，再谈对接"。

## 5. 生态冷启动

### 5.1 三步走

| 阶段 | 动作 | 成功信号 |
|---|---|---|
| M2 起 | **官方先当最大的插件作者**：IM 三适配 + git/CI 校验构成官方插件集 v1，全部按第三方同等协议实现 | 官方插件集能覆盖一个真实需求的全部落盘与放行需求 |
| M3 起 | **dogfooding 即冷启动第一步**：平台管理本项目自身开发，所用校验器/适配器就是 v1 插件集；公开自举过程（决策可回溯到证据锚点） | 平台自己的开发流程完全跑在平台上 |
| M4 起 | **模板市场开张 + 数据公开**：模板仓库开源；实验一/二的指标数据公开 | 出现第一个外部贡献者提交的配置或插件 |

### 5.2 叙事定位

> harness 类工具解决的是"**单 agent 任务上的校验闭环**"；Conclave 解决的是"**多 agent + 多角色在同一个需求上的共识与流转**"。

差异点落在两处：**协作协议**（盲评投票、证据锚点、锚点独立度、门禁与升级）与**自进化**（知识条目回流、Issue 密度衰减）。也就是说，本项目的目标不是"更聪明的单个 agent"，而是"可审计的共识"。

### 5.3 冷启动的不确定性（如实标注）

"官方插件集 + 模板市场"的组合是推理产物，**没有同构新平台的直接实证**——可参照的插件市场（如某些 AI CLI 的插件市场）都是在已有庞大用户基数之后形成的生态，不可直接类比。因此这一节的判定时点是 M3：若自举阶段官方插件集无法覆盖自身需求，说明协议的能力面设计有缺口，应先补协议而不是催生态。
