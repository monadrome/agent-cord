## 本章回答什么问题

agent 能读什么、能写什么、手里握着什么凭证？在没人盯着的时候（跑一整晚、进 CI、被一段恶意文本牵着走），凭什么相信它不会写坏仓库、不会把凭证漏出去、不会被注入攻击驱使？出了事之后，怎么复盘到「谁、用什么模型、基于哪份上下文、做了哪个决定」？

## 9.1 安全总原则：Draft-only 是默认答案，但它只回答三分之一

> **本节回答**：整个安全模型的基线是什么？这条基线覆盖了什么、又漏掉了什么？

### 9.1.1 基线：agent 全程只产 Draft，合入永远人工

**平台的权限最简模型**：任何 agent 都不具备把产物推进主干的能力——它产出 diff、草稿、投票结论、账本条目，合入与放行永远由人完成。

这不是保守折中，而是业界四家主流 coding agent 的**共同默认形态**（表格按各家官方文档整理；其中 OpenAI Codex 分云端与 CLI/IDE 两个执行形态，故列五行）：

| 产品 | 执行环境 | 写权限边界 | 凭证 / secrets | 合入权 |
|---|---|---|---|---|
| GitHub Copilot cloud agent | 临时、默认防火墙的隔离 Actions 环境 | 只访问所在仓库；只能 push 到单个 `copilot/*` 分支，**不能 push 默认分支** | 无权访问 Actions secrets；只有显式加入专用 environment 的 secrets 才注入 | 无。开 PR 后人 review / merge |
| OpenAI Codex（cloud） | 托管隔离容器 | 工作区内写；`.git`/`.codex`/`.agents` 强制只读 | **两阶段：setup 阶段可联网装依赖、secrets 仅 setup 可用，agent 阶段开始前移除**；agent 阶段默认断网，可配域名白名单代理（含 DNS rebinding 防护） | 无合入概念；产出 patch/diff 由人处理 |
| OpenAI Codex（CLI/IDE） | OS 级沙箱（macOS Seatbelt / Linux bwrap+seccomp） | 默认无网络 + 写限工作区；非 git 目录默认只读 | 同沙箱边界 | 无 |
| Claude Code | 本地 + 可选 OS 级沙箱 | 分级：Read 默认放行；Bash/Edit/Write/WebFetch/WebSearch 默认逐次问人；allow/deny 规则可入版本库共享 | 不主动持有业务凭证 | 无合入概念 |
| Devin | 容器化沙箱 VM + 出站白名单 | 会话内写分支 | 企业版 RBAC 两级（org/account），secrets 管理是独立权限项；官方建议专用 service account + secrets manager，**不接触生产凭证** | 无 |

四家收敛到同一个模型：**agent 在沙箱里跑、写权限压到单分支、secrets 默认不可见且短时效、合入永远是人**。业界唯一谨慎试点的「把判定权交给 agent」（Copilot code review 可 approve PR 的预览）也不碰合入权——这与本方案「判定用强模型、合入人工」的方向一致。

因此 ADR-0001 的边界在本章落成一条硬规则：**agent 全程只产 Draft，合入永远人工**。

### 9.1.2 但它只覆盖「写」这一根轴

必须同时说清这条基线**不**覆盖什么，否则等于把三分之二的风险留在空白里。权限模型有三根轴：

| 轴 | 问题 | Draft-only 覆盖了吗 | 本章回答位置 |
|---|---|---|---|
| **写 / 合入** | agent 能把什么推进主干？ | 覆盖：不能 | 9.1、9.2 |
| **读** | agent 能读哪些仓库、文档、消息、账本？ | **未覆盖**：只读也可能造成泄密与越权决策 | 9.2 |
| **凭证** | agent 运行期握有什么身份与 token，活多久？ | **未覆盖**：Draft-only 管不到 agent 手里的钥匙 | 9.3 |

**为什么读权限也要单独管**：prompt injection 让「agent 读到的任何内容」都成为潜在攻击载荷，而 agent 的读权限决定了它能被喂进什么、又能把什么带出去。一个能读全库、能联网的只读 agent，同样可以是一个数据外泄通道。

**为什么凭证要单独管**：agent 持有的任何凭证都处在潜在的注入泄露面内。凭证最小化不是洁癖，是对注入攻击的纵深防御。

配套原则（贯穿全章）：本方案不做激进全自动（ADR-0001），人只做兜底、补充事实与上下文、决策、纠偏；所有需要人判断的安全请求以**选择题**形态推回 IM（不给论述题），并由人在事件流中留痕答复。

## 9.2 agent 权限分级表

> **本节回答**：平台里每一类 agent 分别能读什么、写什么、触发什么、持有什么凭证？

按角色定义权限，而不是按 agent 实例定义。7 类角色如下（`读 / 写 / 触发执行 / 凭证` 四列）：

| # | agent 角色 | 读 | 写 | 触发 / 执行 | 凭证 |
|---|---|---|---|---|---|
| 1 | **单机器人路由**（翻译层） | 群消息全量、全局 session 全量 | 群消息（摘要 / 选择题）；session 事件写入 | 把群内输入路由给后端 worker | IM 机器人 token；**无仓库凭证、无外部系统凭证** |
| 2 | **探索 agent** | 代码只读、仓库文档、共识账本 | 临时账本条目（待确认态） | 只读分析命令（沙箱内） | 无仓库凭证；网络默认断 |
| 3 | **投票 agent** | 代码只读、上下文包、知识库只读 | 投票记录 | — | 无写凭证 |
| 4 | **实现 agent** | 最小上下文包（按需求剪裁） | **单特性分支**（类比 `copilot/*`，碰不到主干）；草稿文档 | 沙箱内跑测试 / 构建 | 短时效、限单分支的仓库 token |
| 5 | **验证 / 审查 agent** | 代码只读、diff、用例、证据锚点 | review 意见、投票记录 | 只读校验命令 | 无写凭证 |
| 6 | **协调 agent**（coordinator） | 全局 session 全量 | 任务派发、文档草案、选择题 | **升级提议（发起，不执行）** | 无 git 凭证 |
| 7 | **合入 / 发版** | — | — | — | **永远人工，无任何 agent 持有** |

三条针对上表的读法说明：

- **路由机器人 = 只读路由 + 白名单代写**：它可以读一切（要解析事件就必须读）、可以写 session 与群消息（这是它的本职工作），但**不能碰代码仓库与外部系统**、不能发群外消息、不能代表人回私聊。这样它的最大事故从「写坏仓库」降为「说错话 / 记错账」，而后者有天然兜底——账本条目可被推翻、一切写入留痕（解析不确定时反问，不猜）。
- **协调 agent（coordinator）只提议不执行**：升级流程、变更流程由它发起，执行权在人（ADR-0002）。它只持有最新快照上下文，事件流永不进它的 LLM 上下文；其隔离由三层防御构成——注入层剪裁（主）、文件层只读副本（纵深）、协议层写操作必经路由（兜底）。
- **workflow engine 不在本表内**：跑工作流图、做 gate 求值与状态迁移的是 daemon 侧的 **workflow engine**（模块，不是 agent；[03-architecture.md](./03-architecture.md) §2.5）。它只写状态迁移事件，同样不持有 git 凭证。表里的「触发 / 执行」列指的是 agent 能自主发起什么，gate 校验器的实际执行由 workflow engine 调度。

### 9.2.1 三条硬规则

| # | 规则 | 具体形态 |
|---|---|---|
| 1 | **凭证规则** | 任何 agent 不持生产凭证与长期凭证；仓库操作用短时效、限单分支的 token；外部服务凭证若必须给，仅 setup 阶段注入、执行阶段前移除（9.3） |
| 2 | **环境规则** | 实现 agent 与所有无人值守任务默认断网或域名白名单代理；多 agent 并发时相互隔离（独立 worktree / 独立进程）；**临时工作区一律视为不可信输入**（9.4） |
| 3 | **溯源规则** | 一切 agent 产出（commit、账本条目、文档草稿、知识条目）必须可回链到全局 session。**无 session 回链的 agent 产出不得进入 `confirmed`**——这是显式规则，不是建议 |

### 9.2.2 门禁权限按 gate 声明最小化

权限不集中在「agent 身份」上，而进一步下压到**每一次门禁执行**：

- gate 定义里有 `permissions` 字段，运行期按该 gate 的声明给子进程分配最小写权限（ADR-0014）；
- **同一插件在不同 gate 下拿到不同凭证**（ADR-0016）：插件进程按 gate 声明的最小权限集起进程，而不是按插件身份给一套凭证；
- **prevent self-review**：改动流程定义（`gates/*.yaml`）的变更本身命中敏感路径，自动挂重型 gate，且改 gate 的人不能自批——防止 agent 自改流程自放行；
- 插件不允许注册自由命令（只能挂在「校验器 / 适配器」两类能力上），避免权限面随插件数量自由扩张。

## 9.3 凭证策略

> **本节回答**：agent 手里到底握着什么、握多久、怎么拿到、怎么保证它不会被写进永久记录？

### 9.3.1 三原则

1. **禁生产凭证**：agent 与插件都不持有生产环境凭证、不用共享 bot 账号、不用长期 PAT；
2. **短时效 token**：需要身份时签发短时效、限定范围的凭证（仓库侧用限单分支的短时效 token；跨系统用 workload identity / OIDC 类短时效换取，而不是把长期密钥复制一份给它）；
3. **setup 期注入**：执行阶段开始前把凭证移除（参照 Codex 的两阶段 secret 生命周期）——安装依赖需要联网与凭证，跑任务不需要。

### 9.3.2 各类凭证的生命周期

| 凭证 | 谁用 | 生命周期与范围 | 落盘要求 |
|---|---|---|---|
| 模型 API key | 平台侧（投票执行器直连 API，ADR-0013）与生成侧 CLI 子进程 | 平台按任务/角色注入到子进程环境；进程退出即失效（ADR-0011 每任务 subprocess，无常驻会话复用） | **不写入任何落盘文件**；不写进快照文件夹、不写进事件流 |
| 仓库 token | 实现 agent（推单特性分支） | 短时效、限单分支、限单仓库；主干与合入路径不可达 | 不入 git，不写事件流 |
| 外部服务凭证（CI、需求单、截图比对工具） | 协调 agent / 校验器插件 | 仅 setup 阶段注入；插件按 gate 声明最小集获取 | 脱敏后事件流只记「用了哪个凭证的引用名」，不记值 |
| IM 机器人 token | 单机器人路由 | 平台持有；只给 IM 收发与 session 写权限 | 平台侧密钥管理，不进仓库 |

**平台形态带来的额外约束**：本方案的核心是常驻 daemon（ADR-0009，见 [adr/ADR-0009-language-runtime.md](./adr/ADR-0009-language-runtime.md)），key 常驻在一个进程里。因此密钥管理集中在 daemon 侧统一收口——**不把 key 复制进每个子进程的配置文件**，也不允许子进程从项目内配置文件读出凭证（9.4 的注入切断正是为这条服务）。

### 9.3.3 事件流入 git 的凭证脱敏：默认开启

事件流（`events.jsonl`）是唯一事实与顺序来源，且按 ADR-0010 **进 git**（`union merge driver` 防合并丢事件）。这带来一个必须显式处理的后果：**一旦某个 secret 被写进事件，它就进入了不可改写的历史**（要清理只能重写历史）。因此：

- **凭证脱敏默认开启**：写入前对事件字段做规则化脱敏（token/私钥/连接串/口令等高危模式，规则集可扩展），命中的**位置与数量**留痕（记「已脱敏 N 处」），**原值不落盘**；
- **写路径统一收敛**：所有事件只能经唯一的写入器进入事件流（`events.jsonl`）与账本（ADR-0012：文件夹内 append-only 事件流 + 进程内 dispatcher），脱敏、schema 校验、引用解析都在这一处以同步方式完成——不存在第二条写路径，也就没有「忘了脱敏」的旁路；
- **快照文档与知识条目同样适用**：任何把外部文本抄进 SSOT 的动作（账本条目、findings、KB 条目）都走同一个写入器，因此同一套脱敏规则自动生效；
- **脱敏不是权限控制的替代品**：脱敏是最后一道防线（防「不该落盘的落盘了」），前提仍是凭证本身就不该给到 agent（9.3.1）。

### 9.3.4 凭证与知识库的边界

- 知识条目 `source_anchors` 只允许符号 / commit / 用例 / KB 引用，**不允许凭证或任何密文形态的内容**（无锚点不入库的硬门槛同时起了这个作用）；
- 知识条目、快照文档、投票记录都不进模型厂商的长期记忆；投票执行器按 ADR-0013 逐次采集 usage，采集的是 token 计数与模型版本，不是内容留存策略的例外通道；
- 事件流永不进入 LLM 上下文，因此事件流里的任何残留内容不会经协调 agent 二次扩散。

## 9.4 执行沙箱

> **本节回答**：agent 在什么环境里跑？为什么「被审查的仓库」本身要当作攻击载荷对待？

### 9.4.1 核心命题：临时工作区视为不可信输入

**教训（CVE-2025-61260）**：某 coding CLI 自动加载项目内配置文件（`.env` / `config.toml`）导致 RCE——攻击载荷不需要 agent 主动执行恶意代码，只要 agent 进入这个仓库并加载它的配置就够了。

对本方案的直接推论：平台会不断把 agent 放进**别人的仓库**（历史包袱重的大型单体、外部贡献的 PR、被注入过的分支）。因此：

- **被审查/被修改的仓库是输入数据，不是可信执行环境**；
- 任何「进入工作区就自动生效」的机制（项目级配置文件、hooks、MCP 自动发现、包安装脚本）都是注入面，必须在无人值守路径上被切断。

### 9.4.2 隔离与注入切断

| 措施 | 落地形态 | 防的是什么 |
|---|---|---|
| 独立工作区 | 每任务一个 `git worktree` 或一次性临时目录；用完即弃（ADR-0011 每任务 subprocess） | 任务间状态污染、并发写冲突 |
| 只读工作区 | 评审/投票/验证任务的 worktree 只读挂载，工具白名单里没有写类工具 | 只读角色意外写坏代码 |
| 切断项目级配置注入 | `--bare`（跳过项目内 CLAUDE.md / hooks / MCP 自动发现）、`--setting-sources` / 独立 `--settings`（注入平台自己的配置） | CVE-2025-61260 类攻击：被审查仓库里的配置反过来指挥平台起出来的 agent |
| 不落凭证到工作区 | 不放 `.env`，不把任何 key 写进工作区；`--no-session-persistence` 类开关避免把会话与临时材料留在工作区 | 凭证被后续任务或后续提交带走 |
| 沙箱档位 | 各家 CLI 的 OS 级沙箱：Codex seatbelt（macOS）/ bwrap+seccomp（Linux）+ 可写根白名单；Gemini CLI sandbox 档位；Claude Code `--permission-mode plan` 等权限模式 + 可选 OS 级沙箱 | 越出工作区的文件读写 |
| 网络隔离 | 默认断网；需要联网时走域名白名单代理（含 DNS rebinding 防护），且只在 setup 阶段联网——实现 agent 阶段不联网 | 数据外泄、从公网拉入载荷 |
| 盲评隔离 | 每个投票任务 = 独立 worktree + 独立进程 + 独立环境变量与独立配置；两侧 transcript 分目录保存，**禁止把 A 的 transcript 喂给 B**（协议强制项） | 「禁止互见中间推理」的独立性保证（ADR-0006）在运行时被绕过 |

**版本纪律**：各家 CLI 的沙箱与权限参数演进很快，「哪一档在哪个版本可用」必须钉版本 + 在 CI 里跑冒烟探针（每个适配器跑一个 `--max-turns 1` 的探针任务），并让适配器对「flag 不存在」优雅降级而不是崩溃——**降级必须 fail-closed**（拿不到期望的隔离档位时，不允许静默以更宽的权限继续跑）。

### 9.4.3 工具白名单按角色裁剪

工具白名单是权限表（9.2）在运行时最直接的一层执行：

| 角色 | 工具白名单（初值） | 说明 |
|---|---|---|
| 投票 / 评审 agent | `Read` + `Bash(git diff *)` / `Bash(git log *)` 等只读命令模式 | 精确到命令模式，不给写类工具 |
| 探索 agent | 只读文件工具 + 检索工具（含知识库只读） | 网络默认断 |
| 实现 agent | 写类工具（限工作区内）+ 构建 / 测试命令 | 不联网；推分支用限单分支 token |
| 协调 agent（coordinator） | 无代码工具，只有 session / 账本读写与派发能力 | 不持有 git 凭证 |

要点：

- 白名单**精确到命令模式**（如 `Bash(git diff *)`），而不是「给不给 Bash」这种粗粒度开关；同时用显式的禁用清单清空默认放行的危险工具（`--disallowedTools "*"` 类的清空式配置）；
- 评审与投票任务不给写权限，**不是靠自觉**，而是工具集里就没有写工具；
- 无人值守时把交互式审批关掉（`dontAsk` / `ask-for-approval never`）并把兜底交给白名单，避免进程挂在等审批上（9.5）。

## 9.5 无人值守防线：超时与预算

> **本节回答**：没人看着的时候，怎么保证一个跑飞的 agent 会被拦住，而不是烧一整夜或永远挂着？

### 9.5.1 超时与预算三层

| 层 | 机制 | 拦什么 | 归属 |
|---|---|---|---|
| L1 | CLI 内建熔断：`--max-turns`（轮次上限）、`--max-budget-usd`（硬预算熔断） | 单次任务内的失控循环与花费失控 | 驱动层（ADR-0011 参数拼装） |
| L2 | 平台调度器 wall-clock 超时：读 stream-json 心跳，无事件 N 分钟即杀 | 卡死、挂起在等待、静默 | 调度器 |
| L3 | 每需求 token 预算（全局配额） | 一个需求整体跑飞 | 编排层 |

三层的分工要说清：L3 的目的**不是省钱**——中等需求上的 token 成本量级很小（相对人力成本占比很低），预算是「防止跑飞」的熔断器；真正的成本是人工介入时间与弱模型返工。因此预算触顶时的默认动作是**停下来升级给人**，而不是静默降级继续跑。

**Fail-closed 是统一方向**：门禁校验器插件子进程必须强制超时（默认 60s，gate 可覆盖），超时按「升级人工」处理而非放行；沙箱档位、隔离参数拿不到预期值时同样不放行。

**进程被杀 ≠ 任务失败**：要求 agent 周期性把中间产物写到工作区文件，被杀后可续跑重试（这也是「独立工作区」的额外收益）。

### 9.5.2 需要人审的权限请求 → 选择题事件

无人值守路径上不允许出现「停下来等人点确认」的交互式阻塞。做法是把审批请求从 CLI 里导出来，变成平台事件：

1. CLI 的权限提示转发给平台（Claude Code 的 `--permission-prompt-tool` 就是这类钩子：把「能不能执行这条 bash」的审批转给一个 MCP 工具，编排程序可以用代码回答）；
2. 平台把请求包装成**选择题事件**推回 IM：并列「要做什么 / 为什么 / 影响面 / 选项（放行 / 拒绝 / 只放行这一次）」；
3. 人的答复写入事件流，任务按答复继续或被阻断。

**分档处理**（由低到高，参照「低风险自动放行、中风险机器预审、高风险找人」的结构）：

| 风险档 | 处理 | 依据 |
|---|---|---|
| 低（白名单内、只读、工作区内） | 自动放行 | 工具白名单已声明 |
| 中（提权、联网、写工作区外） | 可选的机器预审：用一个独立评审 agent 预审，**评审失败则拒绝（fail-closed）** | 与「机器审机器的提权请求」已被工程验证的结构同构（Codex 的 auto_review 模式），本方案作为远期演进 |
| 高（合入、发版、触碰契约、外部系统写） | 永远找人，且永远不自动放行 | ADR-0001；权限最简模型（agent 只产 Draft、合入永远人工） |

中风险档在本方案中是**可选增强**而非默认：默认的中间档是「挂起等待人的选择题」，不是「机器代批」。理由是机器预审的误放会直接扩大权限面，需要先有误放率数据再开。

### 9.5.3 并发与限流

- 按供应商做令牌桶 + 队列调度：多 agent 并发撞供应商 rate limit 是真实瓶颈，**不能假设供应商帮我们扛**；
- 异构投票恰好可以错峰调度（不同供应商配额天然分担）；
- 并发 worktree 数量设上限（实践参考 8–10 个），既是资源保护也是审计可行性的保护。

## 9.6 供应链与插件安全

> **本节回答**：第三方插件、模板市场、npm 依赖这三条供应链分别怎么防？

### 9.6.1 插件装载：IPC 进程而非进程内

插件一律以**外部进程 IPC** 形态装载（ADR-0016），这是安全选择而非性能选择：

| 维度 | IPC 进程插件 | 进程内动态加载（被否决） |
|---|---|---|
| 崩溃影响 | 只死插件，平台不受影响 | 一次插件崩溃 = 平台崩溃 |
| 权限面 | 只拿到宿主显式注入的输入与环境变量，不共享 session 内存 | 直接坐在 session 写权限上 |
| 超时 | 可强制超时并 fail-closed | 难以可靠中断 |
| 版本耦合 | 按协议版本声明兼容，宿主升级不炸插件 | 宿主升级即插件全坏 |
| 凭证 | 按 gate 声明的最小权限集起进程 | 凭证面失控 |

协议 v1 冻结三种消息：`check`（入：产物描述 + 锚点；出：`{result: pass|block|warn, anchors, reason, confidence}`，即三态结果 + 证据锚点 + 机器可读理由 + 置信度）、`capabilities`（能力清单，供配置引用）、`health`。**能力清单是配置与插件之间唯一的接缝**：配置只能组合已声明的能力，加载期校验引用与参数，避免运行期炸；插件不允许注册自由命令。

### 9.6.2 官方插件与第三方同一协议

**官方插件集也走同一 IPC 协议，不允许走后门调进程内 API**。这不是洁癖，而是让协议接受真实检验：

- 若官方插件能用私有通道，第三方插件就会被迫达成「官方级」信任才能被采用，协议本身就变成装饰；
- dogfooding 阶段的全部校验器与适配器（IM、CI、git 校验）都以第三方同等接口实现，等于用平台自己的日常运行给协议做压力测试。

### 9.6.3 marketplace：清单只做发现，不做执行

- `marketplace.json` 类清单只登记「插件名 + git 源 + 版本 + 能力摘要」，**不携带可执行内容、不预置安装脚本**；
- 安装需要用户**显式 add 并锁定 commit / tag**，不允许「跟随上游最新」的隐式安装（防 tag 漂移与投毒）；
- 清单被发现 ≠ 被信任：安装前的能力清单展示是人的决策依据，安装后的权限仍受 gate 声明约束（9.2.2）。

### 9.6.4 npm 分发的供应链面

分发形态为 npm CLI（ADR-0016），相应纪律：

- 提交 lockfile，保证依赖可重现；
- 声明 `engines.node` 并在 CLI 启动时自检（避免裸机上版本错配导致的行为差异）；
- 避免 `postinstall` 脚本（CI 安全扫描常拦截，也是常见投毒载体）；
- 提供 `npx` 与 Docker 镜像两条 CI 通道，让「跑平台」不需要在生产机上装全局包。

## 9.7 审计与可回溯

> **本节回答**：一切安全相关的动作怎么留痕，事后怎么复盘到「谁、用什么模型、基于什么上下文、做了什么决定」？

### 9.7.1 唯一留痕机制：事件流

**判定一律查事件流（`events.jsonl`）与共识账本（`ledger.yaml`）**，frontmatter 与文档只是显示层——这条 SSOT 纪律同时是审计纪律。

必须留痕的类别：

| 类别 | 具体事件 |
|---|---|
| 状态变化 | 条目状态迁移、门禁放行 / 拦截 / 升级、任务派发与完成、知识条目生命周期迁移 |
| 安全动作 | 权限请求与人的答复、提权被拒绝、超时被杀、沙箱档位降级被拦、脱敏命中（记位置与数量，不记原值） |
| 上下文 | 上下文包 id 与版本、注入了哪些前置条目、哪些定位符被实际拉取 |
| 产出 | agent 产出与其回链的全局 session（溯源规则 9.2.1） |

事件流 append-only，且**进 git**（ADR-0010，`union merge driver` 防合并丢事件）——于是审计记录获得与代码同级的不可改写语义与版本对应关系：任意一条审计记录都能定位到「当时的仓库状态」。

### 9.7.2 投票记录的最小可回溯字段

投票与复述检验记录的字段（ADR-0013 + ADR-0011）必须能回答「这一票是在什么条件下投的」：

| 字段 | 作用 |
|---|---|
| `model@version` | 锁定模型版本：模型静默升级后结论漂移时，能定位到是哪一版 |
| `prompt_hash` | 提示词指纹：同一决策点的多次投票是否真的同题 |
| `temperature=0` 与结构化输出 | 可复现性的前提 |
| `session_id` + CLI 版本 | 生成侧的可回溯锚点（哪次会话、哪个 CLI 版本产出的） |
| 上下文包 id | 这一票看到的是哪份剪裁后的上下文 |
| 证据锚点列表 | 结论与符号 / commit / KB 的对应关系；锚点独立度检查的输入 |
| `usage`（逐次采集） | 成本归因 |

这套记录同时服务三件事：安全复盘、指标统计、以及回放实验（实验一 / 共识机制回放）——审计数据与实验数据是同一份，不需要额外埋点。

### 9.7.3 审计的边界

- **审计内容本身受脱敏约束**（9.3.3）：脱敏发生在写入器，因此审计记录里不会出现原值；
- **权限沿用宿主仓库的权限模型**，不自建第二套账号体系：能读仓库的人才能读它的事件流与快照文件夹。本方案不自造权限体系，一是避免两套权限的漂移，二是让「账本数据可导出、平台不好用时可退回原工作方式」这条回退路径成立；
- **事件流永不进 LLM 上下文**：既防腐化（历史偶然性被「认知洗白」为正式需求），也防注入内容经协调 agent 二次扩散——协调 agent 只看最新快照上下文；
- **审计不是绩效工具**：推翻不追责是既定文化约定，指标用于改进机制而非评价个人或 agent；否则指标会被博弈（条目被标低置信度逃责），审计就只剩形式。
