## 1. 根本性风险

十条风险来自方案提案的风险章与不确定点全景清单的收敛去重（原 7 + 10 条归并为 10 条）。

### R-1 相关错误：一致不等于正确

- **为什么重要**：整个投票机制建立在"多个 agent 独立判断，一致就更可信"之上。但大规模实证表明模型的错误是**系统性相关**的：跨架构、跨供应商依然存在，且模型越大越准相关性越强；两个模型都答错时约 60% 错在同一个答案上（ICML 2025）。同一份跨 runner 研究（53 runners × 50 采样 × 26.5 万样本）显示一致度对正确性只是"正但弱"的预测（rho 0.20–0.59），最一致的模型在 agreement≥0.8 的条目中 48% 是错的（arXiv:2607.08065）。若这条不成立，`2/2 一致 → confirmed` 就是"同一个盲区被盖章"。
- **现状**：**已缓解**（残留风险**开放**）。两项机制已落定：判定 agent 与生成 agent 必须异构（抑制 self-preference bias）；锚点独立度检查（两票结论一致但证据锚点重合度 Jaccard≥0.5 → 视为疑似同源错误 → 强制升级人工）。但异构是**必要非充分**条件——它降低、不消除相关性。
- **验证或缓解方式**：实验一直测"一致但错率"（一致的决策点中多数选项与人工金标准不符的比例）与锚点重合度分布，并按阈值表判绿/黄/红（见 `./12-experiments.md`）。红线的兜底规则：一致但错率 > 20% 时，独立一致度不能单独支撑 confirmed，一律转人确认。最终兜底是**独立于共识的验证信号源**（R-2）。

### R-2 共识-测试循环：测试验证的是共识，不是现实

- **为什么重要**：用例来自共识条目。共识错则"测试全绿"是**更强**的幻觉——它比没有测试更危险，因为自动化验证给错误盖了合格章。集成测试全自动（协作协议第三类）会把这个循环放大。
- **现状**：**开放**。唯一解是引入**独立于共识的验证信号源**——真实流量回放、灰度对比、线上指标等不经过共识生成路径的信号。
- **验证或缓解方式**：把"独立验证信号源接入"列为必做项（而非可选优化），并在第一轮内落地至少一条（如灰度对比）；同时把"零推翻率"视为警报而非满分——推翻率长期为零说明验证信号太弱或观察期太短。

### R-3 指标博弈：仪表盘全绿而机制已死

- **为什么重要**：推翻率一旦成为被考核的指标，最省力的应对是"把条目标低置信度"或"不记录可疑结论"，而不是提升共识质量。半年后的典型形态是仪表盘全绿、机制已死。
- **现状**：**已缓解**。两条对冲：对抗性设计（定期抽查"应被推翻而未被发现"的条目，作为审计项而非个人评价）；**推翻不追责**的文化约定（指标用于改进机制，不用于评价个人或 agent）。
- **验证或缓解方式**：审计抽查的执行记录与"应推翻未推翻"检出率进仪表盘；被推翻的结论全文保留（被推翻的结论本身也是知识），降低记录的抵触感。

### R-4 基线缺失：没有对照组，"效率提升"无法证明

- **为什么重要**：如果不知道现状下协调/共识实际花了多少时间，所有收益论证都缺对照，M4 的实验数据也失去解释力。
- **现状**：**开放**，但成本最低、优先级最高。做法是一周自我计时（共识/协调实际耗时），**最先启动**（W4.1），不依赖任何代码。
- **验证或缓解方式**：计时表在 M1 启动，作为全部对比的基线；实验一内的单 agent 组（G3）另行提供"无投票基线"，两者互补不冲突。

### R-5 权限与安全模型：agent 的写权限边界未定义

- **为什么重要**：架构级缺口，后期补代价大。涉及三条轴：写权限（能否合入）、读权限面（能读多少内部资产）、凭证与网络。若不做限制，agent 就是拿着生产凭证的自动提交者。
- **现状**：**已缓解**（第一阶段边界）。最简模型：**agent 全程只产 Draft，合入永远人工**——这是 Copilot/Codex/Claude Code/Devin 的共同默认，业界无反例。配套分级：路由机器人"只读路由 + 白名单代写"（可读群与 session、可写 session，禁碰 git 与外部系统）；门禁权限按 gate 声明最小化；凭证禁生产、短时效、setup 期注入。残余开放项：**读权限面**与**凭证/网络隔离**两轴尚未逐项定义。
- **验证或缓解方式**：先以最简模型上线（Draft-only），安全模型单列设计；IPC 插件形态天然给出权限结构保证（子进程只拿到宿主显式注入的内容，不共享 session 内存）。

### R-6 成本：真正的大头不是 token

- **为什么重要**："平台做得出但用不起"是这类系统的典型死法。
- **现状**：**已缓解**（token 维度），**开放**（建设成本与介入负担维度）。按典型中等需求（约 3 人日）测算，三种模式（强模型整体执行 / 弱模型细粒度编排 / 弱模型 + 投票）的 token 成本约为 ¥96 / ¥40 / ¥49，占人力基线 < 2%；每需求净省 15 分钟人工即回本。结论：**token 是噪声级成本，降为监控项**。真正的成本是固定建设成本摊销与人工介入负担（选择题疲劳，见 R-8）。
- **验证或缓解方式**：实验三顺带采集 token 与用量数据；实验二/三显式观测**弱模型 token 放大系数 m**（初值 2.5，告警阈值 5）与返工率；平台层面的回收期以"人工介入分钟数 + 节省人时"为主项核算，token 仅作参考项列报。

### R-7 行为改变假设：方案假设人愿意对机器人说话

- **为什么重要**：流程平台最常见的死因不是技术，而是"要求人配合"。如果产品/测试不愿意把变更说给机器人听，变更捕获就断在源头。
- **现状**：**开放**。缓解方向是**降低配合依赖**：不要求人主动上报，而是从可观测信号反推变更——契约 diff、测试突变、代码结构变化本身即可触发"共识是否仍成立"的确认。
- **验证或缓解方式**：在自举阶段统计"主动投喂 vs 信号反推"两类来源的比例；若主动投喂占比长期极低而机制仍能运转，说明反推路径有效（这比"说服人改变习惯"更可控）。

### R-8 跨角色介入负担：选择题疲劳

- **为什么重要**：门禁让产品/设计/测试直接介入，介入次数会上升。"给人选择题"降低了单次成本，但次数增加同样致命——介入次数上升是平台的隐性死法。
- **现状**：**开放**。告警阈值未定（待拍板项）；介入点三分类（事实补充型/价值判断型/风险仲裁型）的覆盖性也需在试点中统计验证（可能出第四类）。
- **验证或缓解方式**：以**跨角色介入总负担**（每人每天收到的选择题数量）为仪表盘指标之一，M3 试点期间统计真实分布后再定阈值；配套"默认轻量 + 触发式升级"（升级才找人，降级不需要理由）。

### R-9 回退设计：平台不好用时退得回去吗

- **为什么重要**：如果退回原有工作方式（无流程的手动/ vibe coding）的成本很高，平台的推广就不是"值的比较"而是"绑架"——这会直接触发组织层面的抵制。
- **现状**：**开放**。核心是**数据可导出性承诺**：共识快照本身是仓库内的普通 Markdown 文件 + YAML + JSONL + git 历史（SSOT 存储=纯文件 + git），不依赖平台即可阅读、检索、迁移；平台停用不导致资产丢失。这条在存储选型上已结构性成立（见 [ADR-0010](./adr/ADR-0010-ssot-storage.md) 与 [ADR-0009](./adr/ADR-0009-language-runtime.md)），但需要写成对外的明确承诺并测试"无平台也能读懂"的极端情况。
- **验证或缓解方式**：自举阶段做一次"刻意不用平台"的演练——只用 `git` 与文本编辑器读账本与事件流，确认流程可被人工接手。

### R-10 组织阻力：动的是协作枢纽地位

- **为什么重要**：产品直接改需求不经开发中转，改变了开发在流程中的枢纽位置；推广很大程度依赖 TL 的支持度，不是技术问题。
- **现状**：**已接受**（自觉取舍）。唯一的应对方向是**降低感知成本**：默认轻量通道，让"走流程"比"手动协调"更省事；门禁由平台提供分档模板，团队可覆盖，组织只在必要时强制最低集。
- **验证或缓解方式**：以 Issue 密度随需求序号衰减作为感知成本下降的证据；不设"推广覆盖率"类指标（强制推广与 ADR-0002 的原则相斥）。
