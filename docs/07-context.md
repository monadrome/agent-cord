## 本章回答什么问题

多 agent 协作最容易烂掉的地方不是模型能力，而是**上下文**：同一个需求，人、协调 agent、各角色 agent 各自持有一份越来越不一样的理解，历史信息越积越多，最后谁的记忆都不能信。本章回答四件事：

1. **谁维护唯一的那份上下文**——共识快照的三层结构（快照文档 / 共识账本 / 事件流）分别负责什么，"主动清理历史"到底清的是哪一层，为什么清了不丢信息，以及"文档支持版本"落在工程上是什么。
2. **协调 agent 为什么只能看最新快照**，它被允许做什么、绝对不许做什么，靠什么强制而不是靠自觉。
3. **每次派任务时给 agent 看什么**——最小上下文包的两层 schema、token 预算、以及为什么人不需要审这个包。
4. **代码变了文档怎么办**——三级防腐钩子、行号漂移的工程解、需求中途变更时的完整处理流。

## 1. 共识快照的维护机制

> 这一节对应一句来源明确的判断：**"对于共享上下文，核心可能是 SSOT 的维护，这里的机制需要定义清楚"**（2026-09-24 项目协作群讨论）。共识不是靠"大家多聊聊"达成的，而是靠一份被持续维护、人人可见的唯一上下文。

### 1.1 一个需求一份文件夹

全局 session 是逻辑概念（一个需求全生命周期的结构化上下文），**共识快照**是它的物化形态：仓库里的一个文件夹，含四份快照文档 + 账本 + 投票记录 + 事件流，与代码同仓、同 PR 流程。完整布局与三层共存原理见 [`./03-architecture.md`](./03-architecture.md) §5；账本与事件流的分工见 [`./04-consensus-ledger.md`](./04-consensus-ledger.md) §6。本节只讲**维护动作**：谁来清、清什么、版本怎么表达、写坏了怎么办。

```
conclave/<req-id>/
├── prd.md / adr.md / plan.md / findings.md    # 快照文档（最新层，人可编辑、可主动清理）
├── ledger.yaml                                # 共识账本（机判层）
├── votes/                                     # 投票记录全文（V-xxxx.yaml，与账本内嵌记录以 vote_id 对齐）
└── events.jsonl                               # 事件流（历史层，append-only，永不清理）
```

### 1.2 三层各管什么（关键：不要让一层同时当历史和现状）

| 层 | 载体 | 内容 | 生命周期 | 谁来写 |
|---|---|---|---|---|
| **历史层** | `events.jsonl` | 每一个决策、变更、门禁结论、投票、升级动作 | **append-only，永不清理** | 所有写入路径统一经 `append_event`（机器） |
| **机判层** | `ledger.yaml` | 共识条目、证据锚点、状态机、投票记录、推翻记录 | 随事件流同步投影；条目状态可流转 | 机器投影为主；人的改动同样必须产生事件 |
| **最新层** | `prd.md` / `adr.md` / `plan.md` / `findings.md` | 人读的现状视图 | **允许人工直接编辑 + 主动清理** | 人 + agent 起草（Draft） |

**判定一律查事件流 / 账本，frontmatter 只是显示层。** 这条规则和"行号不参与锚点判定"是同一条原则在不同对象上的应用：任何可能漂移的双写字段都不许进入判定路径。

"主动清理历史信息"能放心的原因就在这里——**清理清的是最新层（快照文档），历史在事件流 + git 里**。"我上个月说过什么"永远查得到，但人不需要在每次对话里背着它；agent 更不该背。

边界必须守住：状态机流转（`confirmed` → `overturned`）、投票、门禁判定**只能**经 `append_event` 写事件流，再投影进账本。如果直接改账本而事件流没记录，审计链就断了。防漂移的办法是一个确定性检查命令：把事件流 fold 一遍得到期望状态，与账本实际状态比对，不一致即告警。

### 1.3 文档版本：git 为权威，frontmatter 为显示

群讨论里提到"为了避免隐性上下文的问题，需要文档支持版本"。落地方式是两层：

- **权威 = git**。快照文件夹与代码同仓、同 PR 流程，所以"这份 prd 什么时候因为什么改的"由提交历史回答，不需要自造版本号体系。
- **显示 = frontmatter**。`prd.md` 顶部的 `{id, status, 版本戳}` 是给 agent 和人的第一眼信息（agent 打开文件就看到"此文档 v3、confirmed 条目 12 条"），不必去跑 `git log`。**frontmatter 不参与判定**——它与 git 真实历史可能漂移，所以禁止放机判字段；可加一条 CI 告警"frontmatter 与账本状态不一致"，允许漂移可见，不允许漂移生效。
- **版本语义按文档类型约定，写进 `conclave.toml`**：
  - `prd.md` / `adr.md` 用 **living**（现状即真相，历史在事件流；允许原地更新 + 主动瘦身）；
  - 里程碑类归档记录可用 **flow-forward**（归档即不可变历史记录，不再回改）。

  这个三分法（living / flow-forward / flow-back）的来源是 spec-kit 的《Spec Persistence Models》官方文档，该文档明确"没有无副作用的默认值，策略留给团队约定"——所以我们把选择权显式写进配置，而不是替团队决定。`conclave.toml` 同时记录布局版本、事件 schema 版本、`apiVersion` 与索引配置，任何迁移由 `conclave doctor` / `conclave upgrade` 执行。

### 1.4 写入纪律与合并（两个必须提前处理的坑）

1. **所有写入汇聚到单一 `append_event` 函数。** CLI、git 钩子、IM 路由、agent 工具调用四类入口全部经它写事件，才能保证时间戳规范化、字段校验、脱敏不被某个入口绕过。脱敏默认开启——事件流会进 git，一次误粘贴的凭证会永久留在历史里。
2. **append-only 日志在 git 分支合并时会丢事件。** 两个分支各自追加事件后合并，git 按散文三路合并必出内容冲突，而任取一侧都会永久丢事件（已有开源项目在生产中踩过：合并后状态板显示 0/N）。解法是注册 union merge driver（按 `event_id` 去重、按 `(seq, event_id)` 排序做并集）+ 事件分片，保留"每事件一文件"作为备选形态。这是 [ADR-0010](./adr/ADR-0010-ssot-storage.md) 明确记录的选择：**事件流进 git 且必须用合并驱动保护，不接受"事件流 gitignore + 定期 checkpoint"**（那会丢掉 PR 上可评审的语义留痕）。工程细节见 [`./03-architecture.md`](./03-architecture.md) §5.3。

## 2. 协调 agent（coordinator）

### 2.1 定位

**协调 agent = 只持有最新快照上下文的协调者。** 它的存在理由来自一个具体担忧：如果协调者像人一样积累长会话历史，它迟早会基于过时信息做路由——而它做的每个路由都会影响所有下游 agent，幻觉会被放大。

职责边界（只做四件事，别的一律不做）：

| 职责 | 具体动作 |
|---|---|
| **路由** | 解析群内输入（一句话变更、截图标注、文档链接），定位到需求与节点，转成结构化事件交出去 |
| **派任务** | 按当前节点与任务图，为每个工作单元生成并挂载上下文包，派给对应角色 agent |
| **回收结论** | 收齐 agent 产出，校验"带证据锚点"后经写路径落成事件，把摘要或选择题推回群里 |
| **提议升级** | 命中触发器时生成升级提议（携带触发器 id 与命中证据），交人确认（见 [`./06-gates-workflow.md`](./06-gates-workflow.md) §4.3） |

它**不做**的事：不裁决技术分歧（那是人）、不改共识（那是推翻流程）、不写代码、不做审查判定、不替任何角色发言。

### 2.2 为什么不持长会话

每一次路由都是一个独立动作：**取快照 → 生成上下文包 → 派任务 → 收回结论 → 落盘**。它不需要"记得"上一轮发生了什么，因为需要的状态全在快照与账本里。三个好处：

- 协调 agent 的状态是**可从快照完全重建**的，任何疑点都能复核（它给出的每个结论都能追到快照里的条目或锚点）；
- 上下文窗口里不会混入当次任务无关的历史，路由判断的噪声更低；
- 协调 agent 可以被无成本替换/重启，不承担"会话资产"的角色——这与本平台"状态在文件里，不在会话里"的总原则一致。

### 2.3 行为契约（三条硬性）

1. **只看快照。** 协调 agent 的输入是快照文档 + 账本（+ 按需的定位符拉取），不读事件流。读到过时的散文式历史，是幻觉的主要来源。
2. **推动作必经路由。** 它想改变任何状态（写条目、改状态机、挂门禁结论），都必须经协议层走 `append_event`，不能自己改文件。它只产 Draft，合入永远人工。
3. **事件流永不进 LLM 上下文。** 不只是协调 agent——所有角色 agent 都一样。事件流给人审计、给程序查询用；"我们有完整历史"不能变回"把历史全塞进 prompt"，否则上下文腐化（context rot）会以另一种形式回来。

### 2.4 契约靠什么强制：三层防御

行为契约靠自觉是靠不住的（角色 agent 由现成 CLI 驱动，文件系统对它天然开放），所以每条契约各配一层技术强制，从主机制到纵深：

| 契约 | 对应的强制层 | 手段 |
|---|---|---|
| 只看快照 | **注入层（主机制）** | 启动时只注入上下文包与只读投影；需要读文件时走白名单 JIT 拉取。**它看到什么由注入决定**，而不是由它自觉 |
| 只能只读 | **文件层（纵深）** | 工作目录指向快照文件夹的只读副本（只读挂载或只读检出）。内核级强制、无性能代价，但只是 belt-and-suspenders |
| 写必经路由 | **协议层（兜底）** | 一切状态变化走 daemon 的单一写路径；即使前两层被绕过，变更仍留下事件记录 |

这三层把"越权后果"压到最小：即使注入层被污染，协调 agent 也只能说错话、产错草案——错误以事件留痕，且必须过门禁或人才生效。进程模型、挂载方式等实现分层见 [`./03-architecture.md`](./03-architecture.md) §6；本章确立的是**行为契约本身**：实现形态可以换，这三条契约不能变。

## 3. 上下文剪裁与最小上下文包

### 3.1 为什么剪裁是硬需求

- **上下文是递减收益资源**：18 个前沿模型的实测显示输入越长性能越差（即使简单任务），"lost in the middle"是机制之一（Chroma 的 context rot 报告）；Anthropic 的上下文工程方法论同样把上下文窗口称为有限注意力预算，并明确"找最小的高信号 token 集合"是核心原则。
- **纯预检索不行**：检索是近似的、索引会漂移，而且无法预知 agent 此刻真正需要什么。
- **纯自主导航不行**：慢、容易追死胡同、把 token 烧在探索上。

业界的收敛答案是**混合**：前置一小撮高信号内容（常驻约定 + 当前需求摘要）+ 轻量定位符（路径、符号、块 id）+ agent 运行时按需拉取。上下文包即此形态。

### 3.2 两层 schema

```yaml
context_pack:
  id: "CP-<req-id>-<work-unit-id>-v<N>"
  生成: { 时间, 生成器版本, token预算: 3000 }

  层1_前置高信号:                     # 有 token 预算与条数硬上限，超出即裁剪并声明
    需求摘要: { 锚点: <req-id>, 结论: "3-5 句" }
    confirmed账本条目:                # 只收 confirmed；临时条目不前置（防"调查结论被当事实"）
      - { 条目id, 一句话结论, 证据锚点列表 }
    仓库约定摘要:                     # 复用 AGENTS.md 生态，不发明新格式
      - { 锚点: "AGENTS.md#<块id>", 摘要: "..." }
    接口契约片段: [{ 锚点: "openapi/rule-submit.yaml#<符号>", 摘要: "..." }]

  层2_定位符:                        # 只给地址不给全文；agent 用 read / grep / kb_get 即时拉取
    代码: [{ 文件, 符号, 类型, 相关度分 }]      # tree-sitter 符号图产出
    文档: [{ 块id, 标题, 证据锚点 }]
    账本: [相关条目id（含临时）]
    知识: [KB-xxxx]
    历史: [相似需求id]

  审计:
    层1: 每条必须带来源锚点
    层2: 记录命中率（哪些定位符被实际拉取、哪些从未被用）
```

预算与配比（初值，需校准）：**层 1 约 2–4k token**，且每类内容有硬上限（知识条目初值 ≤ 8 条，见 [`./08-self-evolution.md`](./08-self-evolution.md)；confirmed 条目上限待校准，超出按相关度截断并在包尾声明截断数）。层 2 不占预算——它只是地址。参考量级：aider 的 repo map 默认预算约 1k token，说明"前置层"可以非常小。包本体默认只在进程内构造，事件里记录 pack 的清单与 hash（可审计、可复现，且不让派生数据污染仓库）。

### 3.3 消费方式：agent 直读，人审账本条目而非审包

这是"最小上下文包由谁消费、以什么格式提供"的定论：

- **包由消费方 agent 直读**，全自动生成。理由三条：(a) 业界主流方案的上下文构建都是全自动的，没有一家让人审检索结果；(b) 人审下发等于在人与 agent 之间加一个中转环节，正是本项目要消灭的上下文切换成本；(c) 可审计性换了位置实现——**包内层 1 的每一条都必须带来源锚点，agent 的结论必须回链锚点**，审计发生在结论侧，不发生在输入侧。
- **人审的对象是账本条目，不是上下文包。** 包只是"账本 + 文档 + 代码"的派生视图，视图错了重新生成即可，不会污染共识；而账本条目是共识本身，必须有人背书。
- 包是**派生视图**，因此永远可重建：不需要为它做备份、迁移、冲突解决——大幅降低运维面。

### 3.4 相关性排序与生成机制

- **代码侧**：tree-sitter 符号图 + PageRank 排序（aider 路线：确定性计算、无 embedding 成本、无索引漂移）。相关度种子 = **账本条目证据锚点 ∩ 需求关键词 ∩ 历史 diff 触碰文件**。
- **文档侧**：按块级锚点索引切分后取相关块（与 §4 防腐共用索引）。
- **知识侧**：走知识库检索（`kb_search` / `kb_get` 工具），起步用符号 / 词法检索（可审计性优先），embedding 作为后置可插拔增强（[ADR-0015](./adr/ADR-0015-knowledge-base.md)）。
- **一份基建两个消费者**：L2 防腐钩子做的是"diff ∩ 证据锚点求交"，上下文剪裁做的是"需求 ∩ 证据锚点求交"——**同一套证据锚点索引同时服务两者**。这是本方案的结构性优势，也是把剪裁做便宜的原因。
- **与模型能力配平**：任务粒度越细、使用的模型越弱，层 1 的占比越高。依据是编码 agent 架构研究的分野（scaffold 驱动的 agent 倾向预建检索基建、LLM 驱动的倾向自主导航）——弱模型自主导航能力弱，就多给前置信号；强模型做探索时，给定位符即可。这与生成弱 / 判定强的非对称分配（ADR-0007）是同一条配平逻辑的两种表现。

### 3.5 prompt cache 复用：让"同一份上下文"变成成本优势

上下文包的层 1 在各 agent 之间高度共享（同一需求、同一节点、同一批 confirmed 条目），因此可以组织成**稳定的静态前缀**：

- 排列顺序：**慢变内容在前**（仓库约定、需求摘要、已 confirmed 条目），**快变内容在后**（当次任务的定位符、临时条目）。这样大多数调用命中同一前缀缓存。
- 收益量级：按主流 provider 的缓存命中价（例如某家的缓存命中 input 价为未命中价的 2%）估算，共享前缀可把单需求 token 成本再压一个数量级——"session 架构本身即成本优化架构"。

这条不是可选优化，而是**上下文包生成器的排序约束**：包生成器必须先排稳定内容、后排易变内容，否则缓存收益消失。指标上可直接观测（缓存命中率）。

## 4. 文档防腐钩子（三级）

### 4.1 本质：强制确认共识仍有效，文档更新是副产品

防腐的目标不是"让文档跟上代码"，而是**在代码触碰某条共识时强制确认该共识是否仍然成立**。文档的块级更新是确认动作的副产品，不是目的。想清楚这一点，机制才不会滑向"到处催人改文档"。

块级粒度为什么可行？**因为共识账本自带证据锚点**——锚点天然把文档切成块。改动命中某条目的锚点区域，就只触发那一条的确认，而不是整篇文档重审（文档级粒度太粗，改一行触发全文评审，那是流程税）。

### 4.2 三级

| 级别 | 拦什么 | 交互成本 | 上线顺序 |
|---|---|---|---|
| **L1 关联** | commit 必须关联需求 id（无法关联则要求填 id 或标记 `no-req`） | 近乎零 | 第一个版本 |
| **L2 影响检查（核心）** | diff 与账本证据锚点求交，命中即要求确认该共识仍成立，或走推翻流程 | 命中才确认，可异步 | 第二个版本 |
| **L3 自动更新** | agent 生成文档块级更新草稿，人确认合入 | 人审一道 | 远期 |

与门禁的关系：L2 在门禁体系里的形态就是"影响检查门"（见 [`./06-gates-workflow.md`](./06-gates-workflow.md) §7 的 `anchor-impact`）；它的结果是三态——未命中静默放行、命中且人确认则 `pass`、人认为共识已不成立则转推翻流程（`block` + 条目状态流转）。

### 4.3 与"Spec 级"防腐的差异（为什么要做账本级）

业界常见的做法是"定期巡检文档与代码的偏差，然后自动开 PR 修正文档"——那是**事后巡检、以文档为对象**。Conclave 走的是**事前拦截、以账本条目为对象**：

| 维度 | 账本级（本方案） | Spec 级（典型做法） |
|---|---|---|
| 触发时机 | 提交前（事前拦截） | 定期巡检（事后发现） |
| 判定对象 | 共识条目的证据锚点是否被动到 | 文档与代码是否不一致 |
| 人做的事 | 回答一个具体问题："这条共识还成立吗" | 审一份自动生成的文档修改 PR |
| 失效兜底 | 条目状态机回退 + 重验 | 靠下一次巡检再发现 |

这不是说 Spec 级做法无效，而是它依赖一个本项目已明确拒绝的前提（维护一份覆盖完整的统一 Spec，见 [ADR-0005](./adr/ADR-0005-ledger-over-spec.md)）。已有成熟实践（`DevMaster`（某公司内部平台）的巡检 Agent、Swimm 类 code-coupled docs）在这个维度上与我们分层互补：它们解决"文档与代码的一致性巡检"，本方案解决"共识是否仍被代码支撑"。

### 4.4 锚点失效本身是信号

代码重构导致锚点重锚定失败时，条目不报错、不静默放过，而是**自动降回"临时"状态并触发重新验证**（[`./04-consensus-ledger.md`](./04-consensus-ledger.md) §4.4）。防腐机制因此顺带解决了文档漂移检测——这是"锚点失效具有语义"的设计副产品，不需要额外机制。

## 5. 行号漂移的工程解

证据锚点的 schema（符号锚点 / commit 快照 / 行号三层的字段与判定规则）由 [`./04-consensus-ledger.md`](./04-consensus-ledger.md) §4 定义。本节回答的是**工程上怎么活下来**：重锚定怎么做、误伤怎么压。

### 5.1 求交在符号级发生

- **符号锚点（活）参与一切判定**：`文件 + 限定符号名 + 签名指纹`。求交时从 diff 提取变更符号集合，与账本的符号锚点求交——抗行号漂移与格式重排。符号引用是语言生态数十年默认实践（Javadoc / Doxygen / rustdoc 都用符号而非行号）。
- **commit 快照（存档）只用于复核**：入账时刻的 `{commit, lines, content_hash}` 让人随时回到证据现场，也能做内容比对来发现"共识被悄悄改成迁就实现"（R9）。
- **行号（显示层）不参与任何判定**：`line_hint` 只为人读方便。判定不读它的两个理由——漂移，以及巧合重合。

### 5.2 锚点重新解析（重锚定）

符号被重命名或移动时，按三条路径依次尝试，全部失败才判定锚点失效：

1. **符号重锚定（重命名 / 移动追踪）**：识别 rename / move / extract 类重构，把旧符号映射到新符号（RefactoringMiner 类工具，或"旧符号名在新 commit 中消失 + 同签名新符号出现"的启发式）。
2. **内容追踪（blame + hash）**：用 `git blame -M -C` 一类的内容相似度追踪，并用 commit 快照里的 `content_hash` 反查"锚定的那段内容挪到哪去了"（符号没变、只是行范围移动时，hash 是唯一的线索）。
3. **AST 结构比对**：用语法树级 diff（difftastic 类工具）区分"重命名 / 格式化"与"真实语义变更"。学术 benchmark 证实 AST diff 能应对多数重构类型，但精度随重构类型变化，需在本项目语言栈上实测校准。

配套一条豁免机制：**纯格式化 / 批量重构提交进豁免清单**（沿用 git 官方的 blame-ignore-revs 模式），求交时直接跳过这些提交。豁免清单必须有登记与审核责任人，否则它会变成绕过防腐钩子的后门。

### 5.3 误伤率与"流程税"警戒线

误伤率 = 命中求交但实际无需处理的比例。它是这套机制唯一的生死指标：误伤率高 → 人开始无脑点确认 → 钩子名存实亡 → 平台被绕过。三个降误伤手段已内建：**文件级粗筛 + 符号级精判**（文件命中但符号未命中则静默放行）、**格式化豁免清单**、**AST diff 过滤格式噪声**。

对照反面教材：GitHub PR 评论用"diff hunk + 行号"定位，代码一变就整 hunk 标 outdated，社区长期抱怨"没被碰的注释也被判 outdated"——那正是我们要避免的误伤形态。

误伤率的具体阈值没有先验数据，必须实测校准：在真实仓库跑一段时间，统计"命中 → 确认 → 放行 / 拦截"的分布（与 [`./12-experiments.md`](./12-experiments.md) 的实验四对应）。校准前的默认取向是**宁可漏检（靠"锚点失效降级"兜底）也不误伤**——因为被绕过的机制比偶尔漏检的机制危险得多。

## 6. 需求中途变更的处理流

需求边进行边迭代是常态，也是需求澄清最难的时刻。变更不是"把文档改一遍"，而是**一份带增量的变更提案 + 一次影响分析 + 一次人工确认**。以"执行中产品临时说某条规则要区分某个维度"为例：

1. **变更写入事件流。** 产品直接对机器人说，或从协作群捕获（保守边界：只接收主动发给机器人的内容）；机器人解析为结构化变更事件，写入 `events.jsonl`（落的是原始语义 + 解析置信度；解析不确定时反问，不猜）。
2. **影响分析 agent 读账本 + diff。** 它不需要读全部历史，只需要相关条目与本次变更涉及的代码 / 契约范围（定位符 JIT 拉取）。
3. **受影响的条目状态机回退 + 附变更来源。** 例如"求值位置"条目未被推翻，但"互斥规则"条目的适用范围被推翻 → 该条目从 `confirmed` 回退为临时，附变更来源与原因；回退是一次带留痕的状态流转（`requirement_change` 归因不计入机制失败，见 [`./04-consensus-ledger.md`](./04-consensus-ledger.md) §5.3）。
4. **给人一道选择题。** 不问"怎么办"，而是给出选项（例如：仅扩展规则维度 / 同时调整 UI 展示 / 推迟到下个迭代）+ 各选项影响。这是"给人选择题，不给论述题"的具体形态。
5. **自动列出受影响资产。** 需要更新的用例、需要扩展的测试场景、可能新增的 UI 列、需要重跑的门禁——由锚点索引反向查询得出，不靠人回忆。
6. **确认后同步所有工作单元。** 变更同步写入所有持有相关上下文的工作单元（R1）；在途任务的上下文包重建（层 1 换新、定位符更新），并命中 `requirement.mid_change` 触发器提升校验强度（见 [`./06-gates-workflow.md`](./06-gates-workflow.md) §4.2）。

对照手动模式：变更的真实成本 = 逐人通知 + 每个人回忆上下文 + 漏掉测试，最后在上线后暴露。系统的做法把这件事变成**一道选择题 + 一份自动影响清单**，且变更的可追溯性由事件流保证。

## 8. 小结

- **共识快照是共享上下文的唯一事实来源**：一个需求一个文件夹，快照文档是最新层（可人工编辑、可主动瘦身）、`ledger.yaml` 是机判层、`events.jsonl` 是永不清理的历史层，外加 git 作为版本化权威。判定一律查事件流 / 账本，frontmatter 只是显示层；写入路径收敛到单一 `append_event`，事件流进 git 必须用合并驱动保护。
- **协调 agent 只持有最新快照上下文**：它每次路由都是"取快照 → 生成包 → 派任务 → 收结论"，不背长会话；三条行为契约（只看快照、推动作必经路由、事件流永不进上下文）各配一层技术强制（注入层为主、文件层纵深、协议层兜底）。
- **最小上下文包是两层结构**：带锚点的前置高信号层（有 token 预算与条数硬上限）+ 定位符层（JIT 拉取）。agent 直读，人审账本条目而非审包；包是派生视图，永远可重建；排列成稳定静态前缀还能吃满 prompt cache。
- **防腐的本质是强制确认共识仍有效**，文档更新是副产品；三级钩子从 L1 关联起步，L2 影响检查是核心；锚点用"符号锚点参与判定 + commit 快照存档 + 行号仅显示"的三层结构，行号漂移有成熟的工程解，剩余风险是误伤率，必须实测。
- **中途变更**走"写入事件流 → 影响分析 → 条目回退并附来源 → 给人选择题 → 自动列受影响资产 → 确认后同步"六步，把逐人通知变成一道选择题加一份清单。
